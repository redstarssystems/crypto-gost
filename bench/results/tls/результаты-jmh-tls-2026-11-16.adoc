== Что измеряет этот прогон

Уровень `crypto-gost-tls13` — сам протокол, без JSSE-обёртки. Замеры идут через `TlsSession`, обмен — через `InMemoryTlsTransport` (канал в памяти). Сети и JCA нет. В `FullHandshakeBench` и `PskResumptionBench` клиент проверяет цепочку сертификата сервера; `NoVerifyHandshakeBench` — то же рукопожатие без проверки цепочки.

С чем сравнивается:

* *0.7.1* — тег `v0.7.1`, измерен 2026-11-08 на этой машине (рукопожатия `-wi 2 -i 5 -w 3s -r 10s -f 1`, компоненты и записи `-wi 2 -i 3 -f 1`). Контроль частоты: `MacBench.hmac256Bc` 16 Б в BouncyCastle — 123 021 (8 ноября) и 123 292 (сейчас), разница 0,2 %.
* *Май* — отчёт `результаты-jmh-tls.adoc` (2026-05-15, JDK 25.0.2), исторический ориентир.
* *15 ноября* — код до замены Стрибога (`a76b65ca`), чтобы выделить вклад хеша.

*Два режима JIT у скалярного умножения.* `ecdheKeygen` по запускам JVM: 1 310, 1 748, 1 861 — один запуск из трёх попал в медленный режим. `verify`: 2 038, 2 189, 2 221 — та же картина, но слабее. `sign` устойчив (1 731–1 733 во всех трёх). Это известная особенность (так же было у 0.7.1); среднее с погрешностью честно отражает разброс, быстрый режим `ecdheKeygen` — около 1 800 в секунду.

*HKDF и вывод ключей быстрее в 2,2 раза* — целиком заслуга нового Стрибога: HKDF строится на HMAC-Стрибог.

Остальные ≈2,1 мс (36 %) — разбор сертификатов, проверка открытых ключей, шифрование сообщений рукопожатия, хеш стенограммы, протокол и транспорт. В мае асимметричная часть занимала 84 %: кривая ускорилась сильнее остального, и её доля снизилась.

Разница между полным рукопожатием и рукопожатием без проверки цепочки — 0,99 мс, это стоимость проверки цепочки внутри рукопожатия (отдельный `chainOnly` — 1,38 мс, он включает и разбор сертификата).

При возобновлении по PSK (3,16 мс) подписей и сертификатов нет, но ECDHE остаётся (режим `psk_dhe_ke`, прямая секретность): 2,17 мс, 69 % времени.

=== Узкое место

Узкое место рукопожатия по-прежнему асимметричная криптография на кривой `tc26a256`, но её доля снизилась с 84 до 64 %. Следующие кандидаты:

* выделения памяти при скалярном умножении (около 1,4 МБ на подпись или ключ ECDHE, см. «Выделения памяти»);
* устойчивость JIT: медленный режим скалярного умножения отнимает до 30 % в отдельных запусках JVM;
* разбор сертификатов и проверка открытых ключей (≈2 мс неасимметричной части).

На уровне JSSE рукопожатие без проверки цепочки даёт 203 в секунду (`bench/results/jsse/результаты-jmh-jsse5.adoc`). Умножать эти числа на число ядер нельзя: блокировки, сборка мусора и планировщик влияют на масштабирование; под нагрузкой 16 потоков дают 1 470 коротких соединений TLS в секунду (`bench/results/perf-screen-2026-11-16.md`).

== Открытые вопросы

. *Два режима JIT у скалярного умножения* — причина не исследована; `ecdheKeygen`, `sign`, `verify` мерить не меньше чем тремя запусками JVM.
. *Выделения при скалярном умножении* — около 1,4 МБ на подпись или ключ ECDHE; первый кандидат на снижение нагрузки на сборщик мусора.
. *Неасимметричная часть рукопожатия* (≈2,1 мс из 5,8) — разбор сертификатов и проверка открытых ключей; профилирование не проводилось.
. *Сравнение с другой реализацией Кузнечика-MGM и с SunJSSE* на классических алгоритмах — по-прежнему нет.

== Воспроизведение прогона

[source,bash]
----
mvn -o install -DskipTests
cd bench/tls && mvn -o package
java -jar target/benchmarks.jar '(FullHandshakeBench|NoVerifyHandshakeBench|PskResumptionBench|CertValidationBench)' -wi 5 -i 5 -f 3 -w 10s -r 10s -jvmArgs -Xmx2g
java -jar target/benchmarks.jar HandshakeComponentsBench -wi 5 -i 5 -f 3 -w 10s -r 10s -jvmArgs -Xmx2g
java -jar target/benchmarks.jar '(RecordProtectBench|Streebog256Bench)' -wi 5 -i 5 -f 3 -w 10s -r 10s -jvmArgs -Xmx2g
java -jar target/benchmarks.jar '(FullHandshakeBench.handshake|PskResumptionBench.resume|RecordProtectBench.protect)' -prof gc -wi 2 -i 3 -f 1 -w 5s -r 5s -jvmArgs -Xmx2g
java -jar target/benchmarks.jar HkdfAllocationBench -prof gc -wi 1 -i 2 -f 1 -w 2s -r 3s -jvmArgs -Xmx2g
----

Перед запуском проверить, что EPP всех ядер `performance`: `cat /sys/devices/system/cpu/cpu*/cpufreq/energy_performance_preference`.
