# ADR 01

**ADR:** BigInteger arithmetic для вычисления s в ГОСТ Р 34.10-2012.  
**Контекст:** финальное вычисление подписи s = (r·d + k·e) mod n
выполняется через java.math.BigInteger.  
**Решение:** оставить BigInteger, не реализовывать CT-арифметику по
модулю n.  

**Обоснование:**

- Критическая операция k·G защищена лестницей Монтгомери — утечка k
  через скалярное умножение закрыта. Извлечение бит скаляра перед
  лестницей (ECPoint.multiply, BigInteger.testBit — O(1) индекс в mag +
  маска, без data-dependent ветвления) рассмотрено и не создаёт утечки
  сверх принятой; переход на собственную fixed-width big-num арифметику
  сознательно не делается — консистентно с отказом от CT-арифметики по n
  ниже.

- Умножение фиксированных операндов (256/512 бит по параметрам кривой) —
  length-dependent ветвления Karatsuba не создают timing-вариации. Шаг
  mod() через divideKnuth содержит ветвления по промежуточным значениям
  частного и CT-гарантии не даёт.

- k детерминирован (RFC 6979) — статистические атаки на timing k·e
  требуют нереалистичного числа наблюдений в условиях JIT-компиляции,
  GC-пауз и планировщика потоков.

- CT-арифметика по n в JVM требует собственного арифметического ядра —
  ни одно из известных мне решений, ни стандартные JCA-провайдеры этого
  не делают.

- dBytes хранится как byte\[\] и обнуляется в destroy() — heap-lifetime
  закрытого ключа минимизирован там, где это возможно.

**Принятый риск:** теоретическая timing-уязвимость на уровне
BigInteger.mod(). В модели remote attacker — неизмерима: сетевой jitter
на порядки превышает timing-сигнал (≈1 ns). Severity: LOW.

**Граница применимости:** данное решение (ADR) сделано для модели угроз
remote attacker — когда противник действует по сети, без доступа к
хосту. Это типичный сценарий для TLS-соединения. Локальный атакующий
(co-located attacker) с произвольным кодом на том же хосте имеет более
практичные пути компрометации ключа, чем извлечение d через timing
BigInteger.mod(). Требования к измерениям (`10⁶`+ подписей в
контролируемых условиях, сигнал в `20×` ниже шума L3-измерений) делают
эту атаку нереалистичной в production для любого сценария. У локального
атакующего есть более простые альтернативы.

**Пересмотреть если:** появится требование сертификации с явным
требованием CT-арифметики, или выйдет практическая атака на BigInteger
ECDSA s-value в JVM.

## Дополнение (memory-lifetime копий d)

**Контекст:** закрытый ключ хранится как byte\[\] dBytes (обнуляется в
destroy()), однако каждая операция подписи реконструирует его в
java.math.BigInteger: ECDSASigner.init() (валидация 0 &lt; d &lt; n),
generateSignature() (вычисление s), и int2octets() внутри RFC 6979
генерации k — итого до трёх временных иммутабельных копий d в куче на
одну подпись. destroy() затирает только byte\[\]-представление;
BigInteger-копии живут до сборки мусора.  

**Решение:** оставить как есть; не вводить собственную обнуляемую
big-num реализацию.  

**Обоснование:** устранение неустранимо без отказа от
java.math.BigInteger — ровно того архитектурного компромисса, который
уже принят в основном решении этого ADR (проекция timing). Здесь тот же
компромисс в проекции memory-lifetime. Промежуточное значение s = (r·d +
k·e) всё равно содержит производные от d данные в куче.  

**Принятый риск:** окно memory-scraping для d расширено до GC временными
BigInteger-копиями. В модели remote attacker — неэксплуатируемо.
Локальный атакующий с доступом к памяти процесса имеет более прямые
пути. Severity: LOW.  

**Пересмотреть если:** появится требование сертификации с явным
контролем heap-lifetime ключевого материала, либо будет внедрено
собственное обнуляемое big-num ядро (что этот ADR сознательно
отклоняет).
