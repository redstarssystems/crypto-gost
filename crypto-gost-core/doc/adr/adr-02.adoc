== ADR 02

*ADR:* Табличная (T-table) реализация Kuznyechik сохраняется; bitsliced/SIMD constant-time вариант не внедряется. +
*Контекст:* методы lsxHi/lsxLo (Kuznyechik.java:449–486) выполняют по 16 lookup'ов с индексами вида (state >>> k) & 0xFF. В первом раунде state = plaintext ^ раундовый ключ, поэтому паттерн доступа к T-таблицам секрет-зависим. Суммарный объём таблиц ≈64 КБ (T_HI_S + T_LO_S; ещё ≈64 КБ на T_INV_* при дешифровании). Это классический cache-timing вектор блочных шифров (Bernstein 2005; Osvik–Shamir–Tromer 2006). +
*Решение:* оставить табличную реализацию; строгую CT-защиту (bitsliced либо GFNI/AVX-512 vpermi2b) не внедрять. +

*Механизм утечки:*

** Каждая S-таблица — 256 long = 2048 байт = 32 кэш-линии по 64 байта, 8 записей на линию. Наблюдение затронутой линии раскрывает старшие 5 бит байтового индекса, т.е. старшие 5 бит байта (plaintext ^ ключ); при известном plaintext — старшие 5 бит байта ключа. Младшие биты добираются перебором.
** Первый раунд (при шифровании) и последний (при дешифровании, индекс зависит от известного шифртекста) дают наиболее чистый сигнал; L-слой «вшит» в T-таблицы, индексация та же.

*Ресурсы атакующего:*

** Обязателен co-located доступ: тот же физический core через SMT (для L1/L2) либо сокет (для LLC); синхронизация с операциями жертвы; желательно pinned-поток и низкий GC-шум.
** Техники: Prime+Probe по LLC. Flush+Reload практически неприменим — T-таблицы инициализируются в static-блоке и лежат на Java heap (не в mmap'нутом разделяемом файле), поэтому требует включённого memory-dedup (KSM), сливающего идентичные константные страницы разных JVM.
** Атака класса OST/Bernstein требует known-plaintext (не обязательно chosen). В штатных режимах CTR-ACPKM/MGM вход блочного шифра — счётчик/keystream, которые по конструкции режима публичны и предсказуемы, то есть known-plaintext-условие выполнено; секретность входа защиты не даёт. Мелкий нюанс: старшие байты счётчика меняются медленно, что для отдельных байтовых позиций ключа увеличивает требуемое число трасс, но не является барьером.
** Бюджет: по калибровке опубликованных cross-VM атак на AES T-tables — порядка 10⁶–10⁸ синхронизированных операций, минуты–часы наблюдения в тихой конфигурации. Для Kuznyechik требуется больше трасс: ключ 256 бит (вдвое против AES-128) и 9 раундов × 16 lookup'ов усиливают алиасинг-шум. Ключ живёт всю сессию (не меняется между блоками), что для атакующего благоприятнее, чем посекундно меняющийся секрет в MGM (см. adr-03).

Иными словами: чтобы украсть ключ таким способом, атакующему мало быть «где-то в сети». Он уже должен выполнять свой код на той же физической машине (или в соседней виртуалке на том же процессоре), что и жертва — то есть заранее проникнуть на хост. Дальше ему нужно заставить сервер зашифровать миллионы, а то и сотни миллионов блоков, и всё это время очень точно замерять, какие ячейки кэша процессора трогает чужой поток, синхронно с работой жертвы, на тихой ненагруженной машине. На реальном сервере с JIT-компиляцией, сборкой мусора и сотнями потоков этот сигнал тонет в шуме. По времени — от минут до многих часов идеальных условий, и всё это ради частичного восстановления ключа, которое потом ещё нужно достроить перебором. Если противник уже способен на всё это, у него обычно есть куда более простые способы добыть ключ — например, напрямую прочитать память процесса.

*Принятый риск / Severity:*

** В модели remote attacker (сеть, целевой сценарий TLS) — атака не реализуется в принципе: cache-timing требует локального выполнения кода. Severity: LOW.
** В модели co-located attacker риск реален независимо от режима: примитив Kuznyechik.init/processBlock (Kuznyechik.java:321, 341) публичен и может быть вызван напрямую с произвольным входом, а в CTR/MGM счётчик и так даёт known-plaintext. Ответственность за корректный режим использования лежит на потребителе API. Единственный практический ограничитель — co-location; при его наличии Severity: до P1.

*Граница применимости:* решение принято для целевой модели remote attacker и штатных режимов (CTR-ACPKM, MGM, TLS 1.3). Для сценариев с недоверенным co-located кодом требуется отдельная CT-реализация.

*Стоимость альтернативы (для справки):* bitslicing затруднён отсутствием алгебраической структуры у π (сотни гейтов на S-box), окупается только параллелизмом по 8–64 блокам; GFNI/AVX-512 vperm требует Panama Vector API (в JDK 21 — incubator) либо JNI и рантайм-диспетчинга по CPU-фичам. Оценка: ≈3–6 недель, аппаратно-зависимо, с заметным решением по perf.

*Пересмотреть если:* появится требование защиты от co-located атакующего, поддержка недоверенного multi-tenant окружения с прямым блочным API, требование сертификации с явной CT-гарантией, либо выйдет практическая cache-атака на Kuznyechik в JVM-условиях.
