== ADR 04

*ADR:* Best-effort constant-time удаление padding (PKCS#7 / ISO 7816-4); строго-CT реализация не внедряется. +
*Контекст:* Pkcs7Padding.removePadding и ISO7816d4Padding.padCount проверяют padding после расшифрования CBC. Реализация уже branchless (маски bad/isPadMask, без early-exit, фиксированное сканирование всего последнего блока фиксированной длины blockSize — не зависит от значения padLen). Остаточный тайминг-сигнал возникает только на невалидной ветке: аллокация исключения и построение стектрейса создают Java-уровневую разницу во времени между валидным и невалидным padding. +
*Решение:* оставить best-effort CT; не переходить на возврат статус-кода вместо исключения и не вводить дополнительную маскировку времени исключения. +

*Обоснование:*

** Полный constant-time в JVM недостижим в принципе: JIT, bounds-checks, GC-паузы и планировщик потоков вносят шум, на порядки превышающий целевой сигнал.
** Длина возвращаемого массива (data.length - padLen) в любом случае раскрывает padLen — это неустранимо на уровне API removePadding и не является утечкой сверх факта расшифрования.
** Основной потребитель — CBC-режим JCA. В TLS padding oracle невозможен: нарушение приводит к fail-closed fatal alert без дифференцируемого отклика (см. обработку в TLS-слое), а не к oracle-differentiable ответу.

*Механизм остаточной утечки:* только throw на invalid-ветке (создание исключения + стектрейс). Сам разбор блока — branchless и время-независим от содержимого padding.

*Граница применимости / принятый риск:* риск актуален лишь при прямом использовании Cipher API (JCA) с CBC + PKCS7/ISO7816-4 вне TLS, где вызывающий код возвращает атакующему дифференцируемый по времени/типу отклик на невалидный padding. Для TLS — не применимо (fail-closed). Severity: LOW.

*Пересмотреть если:* появится сценарий прямого JCA-CBC с oracle-differentiable откликом на padding в чувствительном к таймингу контуре, либо требование сертификации с явной CT-гарантией снятия padding.
