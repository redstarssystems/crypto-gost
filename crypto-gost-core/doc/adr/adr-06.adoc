== ADR 06

*ADR:* Сырой CTR-режим `GostCipherSpi` (Kuznyechik/CTR/NoPadding) при инициализации без параметров генерирует случайный 64-битный nonce — ограничение задокументировано, поведение не меняется. +
*Контекст:* `GostCipherSpi.generateIv` при `engineInit(..., params == null)` для CTR создаёт nonce длиной `BLOCK_SIZE/2 = 8` байт (`random.nextBytes`). По ГОСТ Р 34.13-2015 §4.4 блок счётчика = IV(8 байт) ‖ counter(8 байт); инкрементируется только младшая половина (`Ctr.incrementCTR`), IV фиксирован на всё сообщение, а `Ctr.init` жёстко требует `iv.length == 8`. Ширину nonce увеличить нельзя, не выйдя за ГОСТ CTR. Каждый новый `init()` берёт случайный 64-битный nonce. +
*Решение:* сохранить случайный 64-битный auto-nonce; ограничение по объёму на один ключ задокументировать (Javadoc класса, `generateIv`, `engineInit`, описание провайдера); не вводить детерминированный счётчик и не менять поведение. +

*Обоснование:*

** 64 бита nonce — требование стандарта, а не свободный выбор: вторая половина блока обязана быть счётчиком. «Просто сделать nonce шире» невозможно без нарушения ГОСТ CTR.
** Детерминированный auto-IV по образцу ACPKM в stateless JCA SPI не работает: разные экземпляры `Cipher` с одним ключом рестартовали бы детерминированный счётчик с одного значения -> гарантированная коллизия, хуже случайного. Персистентного key-bound состояния в JCA SPI нет.
** `engineGetIV` возвращает сгенерированный nonce вызывающему (`cipher.getIV()`), поэтому текущий авто-путь функционален: приложение может сохранить и передать nonce стороне расшифрования.

*Принятый риск:* безопасный предел — не более ≈2¹⁶ сообщений на одном ключе (вероятность коллизии p ≤ 2⁻³²). При превышении вероятность коллизии 64-битного nonce растёт по «парадоксу дней рождения» (≈50% к ≈2³² сообщений). Совпадение nonce в CTR даёт один и тот же keystream (счётчик у обоих стартует с 0), и XOR двух шифртекстов раскрывает открытый текст — потеря конфиденциальности. Severity при мисюзе: HIGH; риск структурно обусловлен ГОСТ CTR и снимается корректным использованием.

*Митигирование:* для больших объёмов или большого числа сообщений на ключ передавать явный уникальный nonce через `IvParameterSpec` (например, монотонный счётчик, гарантирующий неповторяемость), либо использовать `Kuznyechik/CTR-ACPKM` (детерминированный UKM + секционная смена ключа по RFC 8645), где данная проблема отсутствует.

*Граница применимости:* распространяется только на сырой CTR-путь `GostCipherSpi` (`MODE_CTR`). Режимы CBC/CFB/OFB используют 128-битный IV (birthday-граница 2⁶⁴), и их повтор IV не катастрофичен в CTR-смысле. `GostCtrAcpkmCipherSpi` не затронут: там UKM детерминирован и выполняется key meshing.

*Пересмотреть если:* появится stateless-механизм гарантированно уникального nonce в рамках JCA SPI, либо сырой CTR-путь будет выведен из состава поддерживаемых трансформаций в пользу CTR-ACPKM.
