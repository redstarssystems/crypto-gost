Модуль `crypto-gost-jsse` реализует JSSE-провайдера для ГОСТ-криптографии на основе модуля `crypto-gost-tls13`.

*Классы JSSE:*

* *`GostSsl` / `GostSslBuilder`* — упрощённый фасад: контекст сервера или клиента одной цепочкой вызовов.
* *`RssysGostJsseProvider`* — регистрация провайдера через `Security.addProvider()`.
* *`GostSSLContextSpi`* — `SSLContext` для `TLSv1.3` / `GOST-TLSv1.3`.
* *`GostSSLEngine`* — полный `SSLEngine`: рукопожатие, `wrap`/`unwrap`, ALPN (RFC 7301), SNI (RFC 6066), mTLS, OCSP stapling, PSK, обновление ключа, экспорт ключевого материала.
* *`GostX509KeyManager`* — `X509ExtendedKeyManager` для ГОСТ-ключей: SNI и выбор клиентского сертификата по `CertificateRequest`.
* *`GostX509TrustManager`* — `X509ExtendedTrustManager`: цепочка, OCSP, CRL, проверка имени узла.
* *`GostSSLSocketFactory` / `GostSSLServerSocketFactory`* — фабрики сокетов.
* *`GostSSLSocket` / `GostSSLServerSocket`* — сокеты.
* *`GostSSLSession` / `GostSSLSessionContext`* — сессии, PSK-возобновление, экспорт ключевого материала.

*Возможности:*

* Рукопожатие: полное, сокращённое (PSK), взаимное (mTLS).
* ALPN — согласование протокола прикладного уровня (HTTP/2, HTTP/1.1).
* SNI — выбор сертификата по имени сервера (multi-tenant).
* OCSP: stapling серверного и клиентского сертификата, client-side fetch, кэш.
* CRL: client-side fetch, политики `DISABLED` / `IF_CDP_PRESENT` / `REQUIRE`, кэш проверенных CRL.
* `max_fragment_length`: клиент может запросить фрагменты 512, 1024, 2048 или 4096 байт.
* Экспорт ключевого материала (RFC 8446 §7.5) для привязки к каналу.
* Наборы шифров `TLS_GOSTR341112_256_WITH_KUZNYECHIK_MGM_L/S` (RFC 9367 §3.1.2); защита записей MGM-AEAD с nonce по RFC 8446 §5.3 и per-record TLSTREE re-keying.
* Логирование через `java.util.logging`; записи соединения помечаются префиксом `[conn#N]`.

*Безопасность реализации:*

* Constant-time сравнения для `verify_data` и PSK binders.
* Затирание ключевого материала при закрытии, fatal alert и исключении.
* Защита от DoS: лимиты на размер записей, цепочку сертификатов, post-handshake сообщения.
* Один `ReentrantLock` на движок, как в JDK; у сокета три замка (handshake, read, write), замки сокета берутся раньше замка движка.

*Ограничения:*

* Только TLS 1.3.
* Только ГОСТ-наборы шифров.
* `HelloRetryRequest` (RFC 8446 §4.1.3) поддерживается: смена ECDHE-группы при несовпадении с сервером. Группа по умолчанию GC256B, задаётся `GostSSLEngine.setClientNamedGroup()`.

+
Все криптографические операции выполняются средствами библиотеки, без внешних зависимостей.

=== Быстрый старт

Примеры ниже используют только публичное API модулей `crypto-gost-core` и `crypto-gost-pkix`.

==== Генерация тестовых сертификатов

Для примеров нужны сертификаты: CA и серверный сертификат для `localhost`.
В production сертификаты получают через УЦ и загружают как PKCS12 (см. ниже).

[source,java]
----
import org.rssys.gost.api.KeyGenerator;
import org.rssys.gost.signature.ECParameters;
import org.rssys.gost.pkix.cert.*;
import org.rssys.gost.pkix.GostOids;
import org.rssys.gost.jca.spec.GostDerCodec;

ECParameters params = ECParameters.tc26a256();

// CA (самоподписанный, BasicConstraints:CA)
var caKp = KeyGenerator.generateKeyPair(params);
byte[] caDn = GostDnParser.encodeDn("CN=Test CA");
GostCertificate ca = GostCertificateBuilder.create(params, caDn)
    .publicKey(caKp.getPublic())
    .notBeforeNow().validForYears(100)   // <1>
    .basicConstraints(true, null)        // <2>
    .randomSerial()
    .sign(caKp.getPrivate());

// Серверный сертификат (подписан CA, SAN=localhost)
var srvKp = KeyGenerator.generateKeyPair(params);
byte[] srvDn = GostDnParser.encodeDn("CN=localhost");
GostCertificate server = GostCertificateBuilder.create(params, srvDn)
    .publicKey(srvKp.getPublic())
    .issuerDn(caDn)                      // <3>
    .notBeforeNow().validForYears(100)
    .extendedKeyUsage(GostOids.EXT_SERVER_AUTH)  // <4>
    .sanDns("localhost")                 // <5>
    .randomSerial()
    .sign(caKp.getPrivate());
----
<1> `notBeforeNow()` задаёт начало срока, `validForYears` считает конец от него.
<2> `isCA=true, pathLen=null` — CA без ограничения длины цепочки.
<3> Издатель — наш CA, а не сам субъект.
<4> EKU `serverAuth`: явно разрешает серверную аутентификацию.
<5> Subject Alternative Name `dNSName=localhost`: по нему клиент проверяет имя узла.

Экспорт в PEM-файлы для использования в `GostSsl.builder()`:

[source,java]
----
import org.rssys.gost.pkix.cert.GostPemUtils;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Paths;

Files.writeString(Paths.get("ca.pem"), ca.toPem());
Files.writeString(Paths.get("server.pem"), server.toPem());
byte[] keyDer = GostDerCodec.encodePrivateKey(srvKp.getPrivate());
Files.write(Paths.get("server-key.pem"),
    GostPemUtils.toPem(keyDer, "PRIVATE KEY").getBytes(StandardCharsets.US_ASCII));
----

==== Эхо-сервер

Сервер принимает соединение, читает строку, возвращает `ECHO: <строка>`.

[source,java]
----
import org.rssys.gost.jsse.GostSsl;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import java.nio.charset.StandardCharsets;

SSLContext ctx = GostSsl.builder()
    .certificate(                             // <1>
        Files.readAllBytes(Paths.get("server.pem")),
        Files.readAllBytes(Paths.get("server-key.pem")))
    .buildServerContext();

try (SSLServerSocket ss = GostSsl.serverSocket(8443, ctx)) {
    while (true) {
        try (SSLSocket s = (SSLSocket) ss.accept()) {
            s.startHandshake();               // <2>
            byte[] buf = new byte[1024];
            int n = s.getInputStream().read(buf);
            String msg = new String(buf, 0, n, StandardCharsets.UTF_8);
            s.getOutputStream().write(
                ("ECHO: " + msg).getBytes(StandardCharsets.UTF_8));
        }
    }
}
----
<1> `.certificate(byte[], byte[])` — авто-определение PEM/DER для сертификата и ключа.
<2> Для `SSLSocket` рукопожатие запускается автоматически при первом read/write.
Явный `startHandshake()` — идиоматичный контроль.

Серверу без mTLS доверенные якоря не нужны: клиентские сертификаты он не проверяет. Добавьте
`trustCa` с CA клиентов, когда включите `needClientAuth` (см. «Взаимная аутентификация»).

==== Клиент

[source,java]
----
SSLContext ctx = GostSsl.builder()
    .trustCa(Files.readAllBytes(Paths.get("ca.pem")))
    .buildClientContext();

try (SSLSocket s = GostSsl.socket("localhost", 8443, ctx)) {  // <1>
    s.getOutputStream().write("PING".getBytes(StandardCharsets.UTF_8));
    byte[] buf = new byte[1024];
    int n = s.getInputStream().read(buf);
    System.out.println(new String(buf, 0, n, StandardCharsets.UTF_8)); // ECHO: PING
}
----
<1> `GostSsl.socket()` создаёт `SSLSocket`, выполняет рукопожатие и проверяет имя узла (HTTPS).
Имя должно быть в SAN сертификата; для подключения по IP задайте `sanIp` и используйте IP.

==== Взаимная аутентификация (mTLS)

Клиент предоставляет свой сертификат — сервер проверяет его по тому же CA.
Переменные `params`, `caDn`, `caKp` — из раздела «Генерация тестовых сертификатов» выше.
Переменные `serverPem`, `serverKeyPem`, `caPem` (`byte[]`) —
из примера «Эхо-сервер» (результат `Files.readAllBytes`).

[source,java]
----
// Сервер: требует клиентский сертификат
SSLContext srv = GostSsl.builder()
    .certificate(serverPem, serverKeyPem)
    .trustCa(caPem)               // CA, которым проверяются клиентские сертификаты
    .needClientAuth(true)         // <1>
    .buildServerContext();
SSLServerSocket ss = GostSsl.serverSocket(8443, srv);

// Клиент: предоставляет свой сертификат
var clientKp = KeyGenerator.generateKeyPair(params);
GostCertificate clientCert = GostCertificateBuilder.create(params,
        GostDnParser.encodeDn("CN=Test Client"))
    .publicKey(clientKp.getPublic())
    .issuerDn(caDn)
    .notBeforeNow().validForYears(100)
    .extendedKeyUsage(GostOids.EXT_CLIENT_AUTH)  // <2>
    .randomSerial()
    .sign(caKp.getPrivate());

SSLContext cli = GostSsl.builder()
    .certificate(clientCert.getEncoded(),       // DER-байты сертификата
        GostDerCodec.encodePrivateKey(clientKp.getPrivate()))
    .trustCa(caPem)
    .buildClientContext();
SSLSocket s = GostSsl.socket("localhost", 8443, cli);
----
<1> `needClientAuth(true)` — клиентский сертификат обязателен. `wantClientAuth(true)` запрашивает
сертификат, но клиент вправе его не предъявлять; тогда приложение само проверяет
`SSLSession.getPeerCertificates()`.
<2> EKU `clientAuth`: сервер принимает сертификат только с этим назначением (или без EKU).

==== PKCS12 (production)

В production сертификаты и ключи хранятся в PKCS12-контейнере. Доверенные якоря нужны только
для mTLS: без них сервер клиентов не проверяет.

[source,java]
----
byte[] p12 = Files.readAllBytes(Paths.get("server.p12"));
SSLContext ctx = GostSsl.builder()
    .certificate(p12, "password".toCharArray())
    .buildServerContext();
----

Если сервер проверяет клиентов, CA берут из PFX одним из двух явных методов; оба требуют
проверенного MAC: `trustCaChain(pfx, pwd)` -- CA из цепочки ключа контейнера (isCA=true);
независимые сертификаты контейнера якорями не становятся. `trustCaBundle(pfx, pwd)` -- все
сертификаты контейнера, который обязан состоять только из CA (ключ УЦ и несколько независимых
корней); защиту обеспечивает только MAC. Если в контейнере есть не-CA сертификат, метод бросает
`IllegalArgumentException`.

==== Режим разработки

Для отладки — клиент без проверки сертификата сервера.
Не для production.

[source,java]
----
import org.rssys.gost.jsse.GostSslDev;

SSLContext dev = GostSslDev.trustAllClientContextInsecure();
----

Если нужно также отключить проверку hostname (подключение по
IP-адресу к серверу с самоподписанным сертификатом):

[source,java]
----
SSLContext dev = GostSslDev.trustAllNoHostnameCheckInsecure();
----

Или через builder:

[source,java]
----
SSLContext dev = GostSsl.builder()
    .trustAll()                                 // <1>
    .withoutHostnameVerification()              // <2>
    .buildClientContext();
----
<1> `trustAll()` — только для разработки и изолированных сетей.
<2> `withoutHostnameVerification()` — отключает проверку hostname: сертификат любого доверенного узла будет принят для любого имени. Применимо только к `buildClientContext()`.

==== Loopback-проверка

Проверка работоспособности TLS без написания серверного и клиентского кода.

[source,java]
----
// mTLS: обе стороны с сертификатами; сервер требует и проверяет сертификат клиента
GostSsl.verify(serverCertPem, serverKeyPem, clientCertPem, clientKeyPem, caPem);
// Односторонний TLS: сервер с сертификатом, клиент только проверяет сервер
GostSsl.verifyServer(serverCertPem, serverKeyPem, caPem);
----


=== GostSsl — упрощённый API

Статический фасад `GostSsl` — один вызов, готовый `SSLContext`.
Никаких KeyManagerFactory, TrustManagerFactory, JKS.

==== Статические методы

Все методы возвращают `SSLContext` или создают сокет.

.Серверные контексты:
[source,java]
----
// PKCS12
SSLContext srv = GostSsl.serverContext(p12Bytes, "password".toCharArray(), caDer);
// PEM-строки
SSLContext srv = GostSsl.serverContext(certPem, keyPem, caPem);
// DER-байты
SSLContext srv = GostSsl.serverContext(certDer, keyDer, caDer);
----

.Клиентские контексты:
[source,java]
----
// Без клиентского сертификата — только проверка сервера
SSLContext cli = GostSsl.clientContext(caDer);
// mTLS: PKCS12
SSLContext cli = GostSsl.clientContext(p12Bytes, "password".toCharArray(), caDer);
// mTLS: PEM-строки
SSLContext cli = GostSsl.clientContext(certPem, keyPem, caPem);
// mTLS: DER-байты
SSLContext cli = GostSsl.clientContext(certDer, keyDer, caDer);
----

.Создание сокетов:
[source,java]
----
// Клиентский SSLSocket с автоматическим handshake
SSLSocket s = GostSsl.socket("localhost", 8443, ctx);
// SSLServerSocket
SSLServerSocket ss = GostSsl.serverSocket(8443, ctx);
// С backlog
SSLServerSocket ss = GostSsl.serverSocket(8443, 100, ctx);
// С backlog и адресом
SSLServerSocket ss = GostSsl.serverSocket(8443, 100,
    InetAddress.getByName("0.0.0.0"), ctx);
----

==== GostSslBuilder

Строитель контекста. Все методы возвращают `this`; терминальные — `buildServerContext()` и
`buildClientContext()`.

.Типовые наборы:
[source,java]
----
// Минимальный сервер без mTLS
SSLContext srv = GostSsl.builder()
    .certificate(serverPem, serverKeyPem)
    .buildServerContext();

// Клиент без своего сертификата
SSLContext cli = GostSsl.builder()
    .trustCa(caPem)
    .buildClientContext();

// Сервер из PKCS12 с большим кэшем сессий
SSLContext srvP12 = GostSsl.builder()
    .certificate(serverP12, "pwd".toCharArray())
    .sessionCacheSize(5000)
    .buildServerContext();

// Клиент с CRL-проверкой и настроенными лимитами
SSLContext cliCrl = GostSsl.builder()
    .trustCa(caPem)
    .crlPolicy(CrlPolicy.IF_CDP_PRESENT)
    .crlFetcher(new JdkHttpCrlFetcher())
    .maxRevokedEntries(1_000_000)
    .maxOcspAgeMs(12 * 3600_000L)
    .buildClientContext();
----

.Полный перечень:
|===
| Метод | Назначение | По умолчанию

| `certificate(cert, key)` | сертификат и ключ, PEM или DER | —
| `certificate(p12, password)` | сертификат и ключ из PKCS12 | —
| `trustCa(ca)` | якоря: PEM, PEM-цепочка или DER; можно многократно | для mTLS
| `trustCaChain(pfx, pwd)` | CA из цепочки ключа PFX (нужен MAC) | —
| `trustCaBundle(pfx, pwd)` | все CA PFX-бандла, только CA (нужен MAC) | —
| `ocsp(true)` | клиент: требовать OCSP-статус серверного сертификата | выключено
| `ocspFetcher(fetcher)` | клиент: сетевой запрос, если staple не пришёл | —
| `maxOcspAgeMs(ms)` | предел возраста ответа без `nextUpdate` | 24 ч
| `maxThisUpdateAge(d)` | предел возраста `thisUpdate` для всех ответов | не задан
| `crlPolicy(policy)` | `DISABLED`, `IF_CDP_PRESENT`, `REQUIRE` | `DISABLED`
| `crlFetcher(fetcher)` | загрузчик CRL по CDP | —
| `maxCrlSize(bytes)` | предел размера CRL | 64 МиБ
| `maxRevokedEntries(n)` | предел числа отозванных записей | 1 000 000
| `crlCacheMaxBytes(bytes)` | бюджет кэша проверенных CRL | 512 МиБ
| `crlMaxAge(d)` | возраст записи до перепроверки | 6 ч
| `sessionCacheSize(n)` | размер кэша сессий, 0 — без предела | 20 480
| `needClientAuth(true)` | клиентский сертификат обязателен | выключено
| `wantClientAuth(true)` | сертификат запрашивается, не обязателен | выключено
| `clientOcspPolicy(p)` | staple клиента: `OFF`, `REQUEST`, `REQUIRE` | `OFF`
| `withoutHostnameVerification()` | клиент: не проверять имя узла, опасно | выключено
| `interopAcceptGostBaseSigScheme(true)` | обход openssl-gost-provider v3.6.0 | выключено
| `trustAll()` | не проверять сертификат, только dev | выключено
| `buildServerContext()` / `buildClientContext()` | терминальные методы | —
|===

NOTE: `ocsp*` — клиентские настройки проверки серверного сертификата; на серверном контексте они
не используются. Свой staple сервер задаёт `GostSSLEngine.setOcspResponse()` до `beginHandshake()`;
сокеты этот способ не поддерживают.

NOTE: `ocspFetcher` работает только вместе с `ocsp(true)`, а вместе с `trustAll()` обе настройки
отклоняются при сборке (`IllegalStateException`). С `ocsp(true)` и загрузчиком статус
запрашивается по сети, если staple не пришёл; недоступность ответчика для серверного сертификата —
отказ, а не пропуск проверки. Сетевые ответы OCSP и CRL кэшируются только после проверки.

NOTE: Для клиентских сертификатов сетевой OCSP дополнительно требует `clientOcspPolicy`, отличную
от `OFF`: по умолчанию сервер не обращается по AIA из сертификатов клиентов. Политики и staple —
в разделе «OCSP API».

WARNING: С включённым сетевым OCSP сервер ходит по AIA из сертификата клиента: число URI не
ограничено, DNS-rebinding штатным `HttpClient` не закрыт. Риск — отказ в обслуживании и сканирование
сети.

WARNING: При умолчаниях `clientOcspPolicy(OFF)` и `crlPolicy(DISABLED)` отзыв клиентского
сертификата не проверяется: отозванный клиент с валидной цепочкой будет принят. CRL проверяется по
`crlPolicy` независимо от политики OCSP.

NOTE: `CrlPolicy.REQUIRE` требует CRL только при отсутствии OCSP-ответа. Если OCSP получен и
валиден, CRL не проверяется; ошибка OCSP — отказ без повторной проверки по CRL.

NOTE: `maxThisUpdateAge` по умолчанию выключен: возраст `thisUpdate` задаёт регламент стороны.
Предел должен быть больше интервала публикации ответов, иначе служба с заранее выпущенными
ответами получит отказы. Для ответа без `nextUpdate` действует меньший из двух пределов; кэш не
хранит ответ дольше предела. Устаревший stapled-ответ — отказ сразу, без запроса по сети; с
`trustAll()` несовместим.

NOTE: `maxCrlSize`, `maxRevokedEntries` и `maxOcspAgeMs` имеют безопасные значения по умолчанию;
`crlPolicy(null)` равносилен `DISABLED`, значения ≤ 0 отвергаются при создании
(`IllegalStateException` в builder, `IllegalArgumentException` в `fromTrustAnchors(...)` и
`GostTrustManagerParameters.Builder`). Предел
`maxResponseSize` загрузчика должен быть не меньше `maxCrlSize` и проверяется при построении;
своя реализация `CrlFetcher` может переопределить `maxResponseSize()`, иначе её предел не проверяется.

NOTE: `interopAcceptGostBaseSigScheme` (по умолчанию выключен) — обход openssl-gost-provider
v3.6.0: он шлёт базовые схемы подписи (0x0709 для 256 бит, 0x070D для 512 бит) независимо от
кривой сертификата, а RFC 9367 §5 требует точного соответствия. При срабатывании пишется WARNING.
Включайте только осознанно, в большинстве соединений флаг не нужен.

==== Ограничения GostSsl

* Сервер без mTLS собирается без доверенных якорей. Включение `needClientAuth`, `wantClientAuth`,
  `clientOcspPolicy` или `crlPolicy` без якорей отвергается при сборке контекста.
* Только один сертификат на контекст — для SNI (multi-tenant) используйте `GostX509KeyManager` напрямую (см. ниже).
* `GostX509TrustManager` принимает только якоря-сертификаты (`TrustAnchors`). Они аутентифицируют `pathLen` и `NameConstraints` корня.
* PKCS12 с GOST PBE поддерживается нативно (PBKDF2-HMAC-Streebog + Кузнечик CTR-ACPKM).


=== API — уровни интеграции

Модуль предоставляет три уровня. Для блокирующего I/O берите сокеты, для NIO и Netty — движок,
для серверов приложений — SPI.

*Socket API* — `GostSSLSocket / GostSSLServerSocket` — стандартный Java I/O.
Handshake запускается автоматически при первом read/write или явно через `startHandshake()`.

*Engine API* — `GostSSLEngine` — низкоуровневый API для неблокирующего I/O
(NIO, Netty). Ручное управление handshake через `wrap()`/`unwrap()`.

*Context API* — `GostSSLContextSpi` — фабрика engine и сокетов,
точка входа для интеграции с серверами приложений (см. раздел «Интеграция»).


=== Конфигурация сервера — ручная настройка

Если вам нужен SNI (несколько сертификатов), тонкая настройка OCSP/CRL
или интеграция с фреймворком — используйте ручную сборку `SSLContext`.
Для большинства случаев достаточно `GostSsl.builder()` (см. выше).

==== Загрузка сертификата и ключа

Три способа загрузки. Рекомендуется PKCS12 для production.

.PKCS12 (ключ и цепочка в одном файле):
[source,java]
----
import org.rssys.gost.pkix.cert.GostPkcs12Loader;
import org.rssys.gost.jsse.bridge.CertificateBridge;

GostPkcs12Loader.Result p12 = GostPkcs12Loader.load(
    Files.readAllBytes(Paths.get("server.p12")), "password".toCharArray(), false); // <1>
PrivateKeyParameters privateKey = p12.getPrivateKey();
X509Certificate[] chain = CertificateBridge.toJca(p12.getCertificateChain());
----
<1> `allowJdkFallback=false` — читаются только ГОСТ-контейнеры. Откат на JDK `KeyStore` включайте
явно (`true`), только если в вашей PKI есть не-ГОСТ контейнеры.

.DER-файлы:
[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.jca.spec.GostDerCodec;
import org.rssys.gost.jsse.bridge.CertificateBridge;

byte[] certDer = Files.readAllBytes(Paths.get("server.der"));
byte[] keyDer  = Files.readAllBytes(Paths.get("server.key"));
PrivateKeyParameters priv = GostDerCodec.decodePrivateKey(keyDer);
X509Certificate[] chain = {
    CertificateBridge.toJca(new GostCertificate(certDer))
};
----

.PEM-файлы (авто-определение формата):
[source,java]
----
import org.rssys.gost.jsse.GostSsl;
import org.rssys.gost.pkix.cert.GostCertificate;

byte[] certDer = GostCertificate.pemToDer(
    Files.readAllBytes(Paths.get("server.pem")));
PrivateKeyParameters privateKey = GostSsl.loadPrivateKey(
    Files.readAllBytes(Paths.get("server-key.pem")));
// Зашифрованный ключ (GOST PBES2):
PrivateKeyParameters encryptedKey = GostSsl.loadPrivateKey(
    Files.readAllBytes(Paths.get("encrypted-key.pem")), "password".toCharArray());
----

==== GostX509KeyManager

[source,java]
----
import org.rssys.gost.jsse.manager.GostX509KeyManager;

GostX509KeyManager km = new GostX509KeyManager();
km.addKeyEntry("default", chain, privateKey);
// SNI (multi-tenant): несколько записей
km.addKeyEntry("api", apiChain, apiKey);
----

Сервер сам вызывает `asSniSelector()`: берётся первая запись, чей лист подходит по имени
(`SubjectAltName/dNSName`, wildcard по RFC 6125; для IP — `iPAddress`). Без SNI берётся первая
запись. Тот же выбор вручную — `chooseAliasForHostname(hostname)`.

==== GostX509TrustManager

Фабрики `GostX509TrustManager.fromTrustAnchors(...)` покрывают все комбинации проверок.

.Проверка цепочки + срок действия (без OCSP/CRL):
[source,java]
----
import org.rssys.gost.jsse.manager.GostX509TrustManager;
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.TrustAnchors;

byte[] caDer = Files.readAllBytes(Paths.get("ca.der"));
GostCertificate caCert = new GostCertificate(caDer);
GostX509TrustManager tm =
        GostX509TrustManager.fromTrustAnchors(TrustAnchors.ofCertificate(caCert));
----

.С одним CA + OCSP (stapling или client-side fetch):
[source,java]
----
import org.rssys.gost.jsse.ocsp.OcspPolicy;
import org.rssys.gost.jsse.ocsp.JdkHttpOcspFetcher;

GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificate(caCert),
    OcspPolicy.STAPLING_OR_FETCH,   // <1>
    new JdkHttpOcspFetcher());
----
<1> Политика: `STAPLING_OR_FETCH` — если нет staple-ответа, клиент сам сходит на OCSP-responder.
Также доступны: `IF_PRESENT`, `STAPLING_REQUIRED`.
Для Android используйте `UrlConnectionOcspFetcher` вместо `JdkHttpOcspFetcher`.

.С несколькими CA + OCSP:
[source,java]
----
GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificates(List.of(caCert1, caCert2)),
    OcspPolicy.STAPLING_OR_FETCH,
    new JdkHttpOcspFetcher());
----
Все переданные сертификаты CA участвуют в проверке цепочки. Порядок не важен.

.Полная перегрузка: CA + OCSP + CRL (JVM — `JdkHttp*`; для Android подставьте `UrlConnection*`):
[source,java]
----
import org.rssys.gost.jsse.crl.CrlPolicy;
import org.rssys.gost.jsse.crl.JdkHttpCrlFetcher;

GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificates(List.of(caCert1, caCert2)),
    OcspPolicy.STAPLING_OR_FETCH,
    new JdkHttpOcspFetcher(),
    CrlPolicy.IF_CDP_PRESENT,         // <1>
    new JdkHttpCrlFetcher());
----
<1> `CrlPolicy`: `DISABLED` (не проверять), `IF_CDP_PRESENT` (проверять если CRL DP в сертификате),
`REQUIRE` (требовать CRL всегда).

.Перегрузка с настраиваемыми лимитами CRL/OCSP:
[source,java]
----
GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificates(List.of(caCert1, caCert2)),
    OcspPolicy.STAPLING_OR_FETCH,
    new JdkHttpOcspFetcher(),
    CrlPolicy.IF_CDP_PRESENT,
    new JdkHttpCrlFetcher(),
    16 * 1024 * 1024,                 // <1> maxCrlSize (байты)
    500_000,                          // <2> maxRevokedEntries
    512L * 1024 * 1024,               // <3> crlCacheMaxBytes
    Duration.ofHours(6),              // <4> crlMaxAge (ZERO - перепроверка выключена)
    12 * 3600_000L,                   // <5> maxOcspAgeMs (RFC 6960 §2.4)
    Duration.ofHours(12));            // <6> maxThisUpdateAge (null - не задан)
----
<1> Максимальный размер CRL. Лимит `maxResponseSize` у *CrlFetcher должен быть &ge; этого значения
(проверяется при построении, см. выше); превышение размера -- отказ проверки.
<2> Максимальное число отозванных записей в CRL (защита от DoS-раздувания).
<3> Бюджет кэша проверенных CRL в байтах оценки удержания (около шести байт кучи на байт DER);
`0` -- не хранить CRL между соединениями, отрицательное значение -- `IllegalArgumentException`.
Сокращённые перегрузки используют `CrlCache.DEFAULT_MAX_BYTES` (512 МиБ).
<4> Предельный возраст записи кэша CRL с последней успешной загрузки: запись старше, но ещё не
истёкшая (`nextUpdate`), перепроверяется. `Duration.ZERO` выключает перепроверку, иначе от 1
минуты до 30 суток, `null` -- `IllegalArgumentException`. Сокращённые перегрузки используют
`CrlCache.DEFAULT_MAX_AGE` (6 ч).
<5> Максимальный возраст OCSP-ответа без `nextUpdate` — локальная политика свежести relying party.
Перегрузка без `maxOcspAgeMs` использует дефолт `GostOids.MAX_OCSP_AGE_MS` (24 ч).
<6> Необязательный предел возраста `thisUpdate` для всех OCSP-ответов, в том числе с `nextUpdate`
(Р 1323565.1.059-2024, п. 5.3). Тип `Duration`, `null` - не задан; ноль и отрицательное
значение отвергаются. Сокращённые перегрузки предел не задают.

.С якорями-сертификатами (pathLen и NameConstraints корня):
[source,java]
----
import org.rssys.gost.pkix.cert.TrustAnchors;

TrustAnchors anchors = TrustAnchors.ofCertificates(List.of(rootCaCert));
GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    anchors,
    OcspPolicy.IF_PRESENT,
    null);
----

`fromTrustAnchors(...)` принимает полный сертификат якоря. При опущенном корне
эффективная цепочка строится снизу вверх: перевыпущенный корень с тем же ключом
и закреплённый промежуточный CA поддерживаются, лишние сертификаты выше якоря
игнорируются. Срок якоря при `n > 1` не проверяется (WARNING), закреплённый leaf
(`n == 1`) проверяется как обычный leaf.

.Через фабрику JSSE (`TrustManagerFactory`) с параметрами:
[source,java]
----
import org.rssys.gost.jsse.manager.GostTrustManagerParameters;
import org.rssys.gost.pkix.cert.TrustAnchors;

GostTrustManagerParameters params = GostTrustManagerParameters.builder()
    .trustAnchors(TrustAnchors.ofCertificate(rootCaCert))
    .ocspPolicy(OcspPolicy.IF_PRESENT)
    .crlPolicy(CrlPolicy.IF_CDP_PRESENT)
    .maxCrlSize(16 * 1024 * 1024)
    .maxRevokedEntries(500_000)
    .maxOcspAgeMs(12 * 3600_000L)
    .maxThisUpdateAge(Duration.ofHours(12))   // необязательный предел возраста thisUpdate
    .build();

TrustManagerFactory tmf =
    TrustManagerFactory.getInstance("GostX509", GostJsseConstants.PROVIDER_NAME);
tmf.init(params);   // <1>
----
<1> Штатный JSSE-путь `TrustManagerFactory.init(ManagerFactoryParameters)` — прокидывает
лимиты в `GostX509TrustManager` без прямого вызова фабрики. `.build()`
требует непустой набор `trustAnchors`.

.Trust-all (только для разработки):
[source,java]
----
GostX509TrustManager tm = GostX509TrustManager.insecureTrustAll();
----

WARNING: `insecureTrustAll()` отключает проверку цепочки. Срок, KU, EKU, имя узла и присланный
staple проверяются, но сетевых OCSP/CRL-запросов и проверки CRL нет, а подмена узла не
обнаруживается. Только для разработки; строгий путь — `fromTrustAnchors(...)`: якоря-сертификаты
аутентифицируют `pathLen` и `NameConstraints` корня.

NOTE: `TrustManagerFactory.init((KeyStore) null)` и KeyStore без ГОСТ-якорей дают
`KeyStoreException`: неявного системного trust store для ГОСТ нет. Передайте KeyStore с
доверенными сертификатами; они сохраняются как якоря, поэтому ограничения корня применяются.

import org.rssys.gost.jsse.RssysGostJsseProvider;

Security.addProvider(new RssysGostJsseProvider());          // <1>
SSLContext ctx = SSLContext.getInstance("TLSv1.3", "RssysGostJsse");

=== Конфигурация клиента

Клиент проверяет сервер по доверенным якорям; свой сертификат нужен только для mTLS.
Для типового случая достаточно `GostSsl.builder()` (см. выше), ниже — ручная сборка.

[source,java]
----
import org.rssys.gost.jsse.RssysGostJsseProvider;
import org.rssys.gost.jsse.manager.GostX509KeyManager;
import org.rssys.gost.jsse.manager.GostX509TrustManager;
import org.rssys.gost.pkix.cert.TrustAnchors;

Security.addProvider(new RssysGostJsseProvider());

// caCert — сертификат CA из раздела «Конфигурация сервера»
GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificate(caCert));
// Пустой KeyManager — без клиентского сертификата
GostX509KeyManager km = new GostX509KeyManager();

SSLContext ctx = SSLContext.getInstance("TLSv1.3", "RssysGostJsse");
ctx.init(new KeyManager[]{km}, new TrustManager[]{tm}, null);

// Клиентский SSLEngine — при непустом host проверка hostname (HTTPS) включена по умолчанию
SSLEngine engine = ctx.createSSLEngine("host", 8443);
engine.setUseClientMode(true);
// Или socket factory
SSLSocketFactory sf = ctx.getSocketFactory();
----

mTLS — клиент предоставляет свой сертификат:

[source,java]
----
GostX509KeyManager km = new GostX509KeyManager();
km.addKeyEntry("client", clientChain, clientPrivateKey);  // цепочка лист-первым

SSLContext ctx = SSLContext.getInstance("TLSv1.3", "RssysGostJsse");
ctx.init(new KeyManager[]{km}, new TrustManager[]{tm}, null);
----

WARNING: Без проверки имени клиент не отличит нужный узел от любого другого с доверенным
сертификатом. По умолчанию проверка включена: сокеты из `ctx.getSocketFactory()` и
`ctx.createSSLEngine(host, port)` с непустым host получают `endpointIdentificationAlgorithm =
"HTTPS"` (RFC 6125).

NOTE: Кириллический `peerHost` (`пример.рф`) преобразуется в A-label; в SNI
уходит punycode, и проверка hostname использует то же значение. IP-литералы
проверяются по iPAddress SAN и в SNI не отправляются.

*Имя SNI отдельно от проверяемого имени.* `SSLParameters.setServerNames(List.of(new SNIHostName(...)))`
на движке и сокете меняет только имя в SNI:

* сертификат сервера по-прежнему сверяется с `peerHost`, и PSK-тикет привязан к `peerHost`;
* пустой список отключает SNI; `SSLParameters` без заданных имён (`getServerNames() == null`)
  переопределение не меняет, как в JDK; имена не типа `host_name` игнорируются;
* неотправляемое имя (например, длиннее 253 символов) отвергается сразу в `setSSLParameters`
  (`IllegalArgumentException`); `getSSLParameters()` возвращает заданные имена, поэтому круговой
  `setSSLParameters(getSSLParameters())` их не сбрасывает.


Явный отказ (тесты, изолированные сети; в production не используйте):

* По контракту `SSLParameters`: `params.setEndpointIdentificationAlgorithm(null)`
  и `engine.setSSLParameters(params)` — отключает проверку, но каждое рукопожатие
  без проверки hostname логгирует WARNING.
* `GostSSLEngine.createForClientNoHostnameCheck()` — однократный WARNING при создании,
  рукопожатия без логов.
* `GostSslDev.trustAllNoHostnameCheckInsecure()` — dev-контекст без проверки цепочки
  сертификатов и без проверки hostname (через session context флаг).
* `GostSslBuilder.withoutHostnameVerification()` — флаг в builder, компонуется
  с `trustAll()` или `trustCa()`.

==== Выбор клиентского сертификата по CertificateRequest

`GostSSLEngine` не выбирает клиентский сертификат заранее: выбор делается, когда сервер прислал
`CertificateRequest`, селектором `GostX509KeyManager.asClientCertificateSelector()`. Запись
подходит, если одновременно:

* лист удовлетворяет `oid_filters` (RFC 8446 §4.2.5);
* при непустом `certificate_authorities` издатель какого-либо сертификата цепочки входит в список
  (§4.2.4); пустой список означает «CA не указаны» и не фильтрует;
* схема подписи ключа листа входит в `signature_algorithms` сервера (§4.4.3).

Среди подошедших предпочитается запись, подписи цепочки которой входят в
`signature_algorithms_cert` (§4.2.3), иначе берётся первая. Если не подошла ни одна, клиент
отправляет пустой Certificate (§4.4.2.3).

[source,java]
----
import org.rssys.gost.jsse.manager.GostX509KeyManager;

GostX509KeyManager km = new GostX509KeyManager();
km.addKeyEntry("kc256", kc256Chain, kc256Key);   // ключ 256 бит
km.addKeyEntry("kc512", kc512Chain, kc512Key);   // ключ 512 бит

GostSSLEngine engine = GostSSLEngine.createForClient(km, tm, "host", 8443, sessionCtx);
// Сервер предложил только 512-битные схемы - уйдёт kc512, а не первая запись
----

NOTE: `SSLSession.getLocalCertificates()` и `getLocalPrincipal()` отражают то, что реально
отправлено в этом рукопожатии: до `CertificateRequest`, при пустом Certificate и при возобновлении
по PSK они равны `null` (как в JDK для рукопожатия без клиентской аутентификации).

NOTE: Записи перебираются в порядке добавления.

=== OCSP API

API для проверки статуса сертификатов через OCSP (RFC 6960).

==== OcspRequestBuilder

Fluent-построитель DER-закодированного OCSP-запроса с поддержкой nonce (RFC 8954).

[source,java]
----
import org.rssys.gost.jsse.ocsp.OcspRequestBuilder;
import org.rssys.gost.jsse.ocsp.OcspRequest;
import org.rssys.gost.api.GostSigner;

// Базовый запрос (без подписи)
OcspRequest req = OcspRequestBuilder.create()
    .targetCert(certDer)            // проверяемый сертификат (DER) — обязателен
    .issuerCert(issuerDer)          // сертификат издателя (DER) — обязателен
    .hashLen(32)                    // 32=Streebog-256 (по умол.), 64=Streebog-512
    .build();

byte[] ocspRequestDer = req.der();   // DER-байты OCSPRequest для отправки на респондер
byte[] nonce = req.nonce();          // nonce для сверки с ответом

// Запрос с подписью (PrivateKeyParameters)
OcspRequest signedReq = OcspRequestBuilder.create()
    .targetCert(certDer)
    .issuerCert(issuerDer)
    .signKey(privateKey)            // ключ для подписи (опционально)
    .params(ECParameters.tc26a256())// параметры кривой; обязательны с signKey
    .build();

// Запрос с подписью через GostSigner (HSM-адаптер)
OcspRequest hsmReq = OcspRequestBuilder.create()
    .targetCert(certDer)
    .issuerCert(issuerDer)
    .signKey(gostSigner)            // GostSigner (параметры кривой берутся из signer)
    .build();
----

==== OcspPolicy

Перечисление политик проверки OCSP, передаётся в `GostX509TrustManager`.

|===
| Константа | Поведение
| `IF_PRESENT` | Проверить OCSP-ответ, если сервер его предоставил (не фатально при отсутствии)
| `STAPLING_REQUIRED` | Требовать OCSP stapling серверного сертификата — fail-closed при отсутствии
| `STAPLING_OR_FETCH` | Для серверного сертификата: stapling или client-side fetch; иначе fail-closed
|===

NOTE: Обязательность OCSP относится к серверному сертификату. Для клиентских сертификатов
ответ проверяется, но не обязателен: при `STAPLING_OR_FETCH` — best-effort fetch, при
`STAPLING_REQUIRED` загрузки нет. Строгий отзыв клиента — `CrlPolicy.REQUIRE`, и только при
отсутствии OCSP-ответа.

==== OCSP-staple клиентского сертификата

Сервер может запросить у клиента OCSP-ответ для его сертификата (RFC 8446 §4.4.2.1)
политикой `ClientOcspPolicy` из `crypto-gost-tls13`:

* `OFF` (по умолчанию) — staple не запрашивается, присланный без запроса отвергается
  (`unsupported_extension`);
* `REQUEST` — запрашивается; присланный ответ проверяется, отсутствие допустимо;
* `REQUIRE` — запрашивается и обязателен для предъявленного сертификата; без него
  `bad_certificate`. Ответ, полученный сервером по сети (`STAPLING_OR_FETCH`), требование
  не выполняет: нужен именно staple клиента.

[source,java]
----
import org.rssys.gost.tls13.config.ClientOcspPolicy;

SSLContext srv = GostSsl.builder()
    .certificate(serverPem, serverKeyPem)
    .trustCa(caPem)
    .needClientAuth(true)
    .clientOcspPolicy(ClientOcspPolicy.REQUIRE)
    .buildServerContext();

// Клиент: staple собственного сертификата, до beginHandshake()
GostSSLEngine engine = (GostSSLEngine) clientContext.createSSLEngine("host", 8443);
engine.setOcspResponse(ocspDer);   // сырой OCSPResponse DER для клиентского сертификата
----

Правила режима:

* `needClientAuth(true)` — сертификат обязателен; `wantClientAuth(true)` — запрашивается, но клиент
  вправе его не предъявлять. Приложение тогда само проверяет `SSLSession.getPeerCertificates()`
  (без сертификата — `SSLPeerUnverifiedException`). При обоих флагах действует `needClientAuth`.
* Политика требует аутентификации клиента, иначе `beginHandshake()` бросает `SSLException`;
  с `trustAll()` builder бросает `IllegalStateException`.
* При `wantClientAuth` и `REQUIRE` анонимный клиент допустим, а клиент с сертификатом обязан
  приложить staple. Staple отправляется только по запросу сервера и должен относиться к
  сертификату, который выберет `KeyManager`.
* Staple задаётся только через `GostSSLEngine` (`setOcspResponse`), сокеты его не поддерживают.

==== OCSP-staple сервера в клиентской сессии

После handshake `((ExtendedSSLSession) session).getStatusResponses()` клиентской сессии
возвращает OCSP-ответы, которые прислал сервер, в порядке его цепочки: запись нулевой длины
означает «ответа нет», хвостовые пустые записи отбрасываются, без staple список пуст. В список
попадает только присланное сервером: ответ, который клиент получил сам по сети
(`STAPLING_OR_FETCH`), и собственный staple клиента (`setOcspResponse`) в него не входят.
Серверная сессия возвращает собственный staple сервера.

==== HTTP-фетчеры OCSP и CRL

Реализации `OcspFetcher` и `CrlFetcher` для HTTP-загрузки OCSP-ответов
и CRL-списков. На выбор две реализации:

* `JdkHttpOcspFetcher` / `JdkHttpCrlFetcher` — на JDK HttpClient (JVM, JDK 11+);
* `UrlConnectionOcspFetcher` / `UrlConnectionCrlFetcher` — на HttpURLConnection
  (Android, API level 1+, не требует java.net.http).

Адрес загрузки задаёт тот, кто выпустил сертификат, поэтому загрузчики ограничены одинаково:

* *Один общий срок на весь запрос*: соединение, заголовки, тело и перенаправления. Сервер, который
  быстро отдал заголовки и затем присылает тело по байту, срок не продлевает. Срок задаётся от 1 мс
  до 10 минут (`Deadline.MAX_FETCH_TIMEOUT`), иначе конструктор бросает `IllegalArgumentException`;
  предел размера ответа должен быть больше нуля. У `HttpURLConnection` (Android) блокирующее
  чтение прервать нельзя, поэтому гарантия честная: тело не позже «срок + одно чтение»
  (`readTimeout` равен четверти срока), и сервер, молчащий дольше `readTimeout`, считается
  недоступным раньше общего срока. Разрешение имени в срок не входит.
* *Перенаправления*: GET (CRL) следует 301, 302, 303, 307, 308, POST (OCSP) только 307 и 308, не более
  5 запросов; SSRF-защита и проверка схемы выполняются на каждом переходе, понижение `https` до `http`
  запрещено. OCSP принимает только `http://`, CRL — `http://` и `https://`.
* *Размер*: заявленный `Content-Length` сверяется до чтения тела, фактический — при приёме. Для CRL
  превышение даёт `CrlSizeLimitException`, для OCSP — `null`. Тело ответа не-200 не читается.
* *Исключения*: `OcspFetcher.fetch` никогда не бросает исключений (любая ошибка — `null`);
  `CrlFetcher.fetch` бросает только `IOException` (срок — `DeadlineExceededException`) и
  `CrlSizeLimitException`.

Менеджер доверия, кроме того, пробует не более 3 адресов каждого вида на сертификат и расходует на
сетевые загрузки отзыва общий бюджет 30 с на проверку цепочки (см. Javadoc `GostX509TrustManager`).

=== CRL API

Проверка отзыва по CRL (RFC 5280 §5). По умолчанию выключена: включите `crlPolicy` и загрузчик.

==== CrlPolicy

Перечисление политик проверки CRL, передаётся в `GostX509TrustManager`.

|===
| Константа | Поведение
| `DISABLED` | CRL не проверяется (по умолчанию)
| `IF_CDP_PRESENT` | Проверить CRL, если в сертификате есть CRL Distribution Points
| `REQUIRE` | Требовать CRL всегда — fail-closed при отсутствии CDP
|===

WARNING: Загрузчик CRL (`crlFetcher`) без политики, отличной от `DISABLED`, — ошибка
конфигурации: `GostSslBuilder` бросает `IllegalStateException`, `GostTrustManagerParameters.Builder`
и фабрика `fromTrustAnchors(...)` — `IllegalArgumentException`. Раньше такой загрузчик молча не
использовался, и отзыв по CRL фактически не проверялся. Задайте `crlPolicy(CrlPolicy.IF_CDP_PRESENT)`
или `REQUIRE`.

[[crl-fetchers]]
==== UrlConnectionCrlFetcher (Android) и JdkHttpCrlFetcher (JVM)

Реализация `CrlFetcher` на JDK HttpClient или HttpURLConnection. Имеет защиту от SSRF.

[source,java]
----
import org.rssys.gost.jsse.crl.CrlPolicy;
import org.rssys.gost.jsse.crl.JdkHttpCrlFetcher;
import org.rssys.gost.jsse.crl.UrlConnectionCrlFetcher;

// JVM
GostX509TrustManager tm = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificate(caCert),
    OcspPolicy.IF_PRESENT,
    null,
    CrlPolicy.IF_CDP_PRESENT,
    new JdkHttpCrlFetcher());

// Android
GostX509TrustManager tmAndroid = GostX509TrustManager.fromTrustAnchors(
    TrustAnchors.ofCertificate(caCert),
    OcspPolicy.IF_PRESENT,
    null,
    CrlPolicy.IF_CDP_PRESENT,
    new UrlConnectionCrlFetcher());
----

NOTE: Проверенные CRL кэшируются до `nextUpdate` с допуском часов 5 минут; CRL без
`nextUpdate` проверка не принимает. Подробности — «Кэш проверенных CRL».

==== Лимиты CRL

CRL больше предела загрузчика или `maxCrlSize` -- это ошибка проверки
(`CrlSizeLimitException` из загрузчика, отказ рукопожатия), а не «адрес недоступен»: CRL не
пропускается молча даже при `CrlPolicy.IF_CDP_PRESENT`. Отказ наступает сразу, без перехода к
следующему адресу CDP: одного зеркала со слишком большим ответом достаточно, чтобы соединение
не состоялось, даже если другое зеркало исправно. Поэтому, когда CRL крупного УЦ
подходит к пределу, лимиты нужно поднять заранее, все три согласованно:

[source,java]
----
GostSsl.builder()
    .crlPolicy(CrlPolicy.IF_CDP_PRESENT)
    .crlFetcher(new JdkHttpCrlFetcher(Duration.ofSeconds(60), crlSizeLimit)) // maxResponseSize
    .maxCrlSize(crlSizeLimit)           // размер CRL в байтах
    .maxRevokedEntries(entriesLimit)    // число записей
    .buildServerContext();
----

Здесь `crlSizeLimit` и `entriesLimit` -- значения, подобранные под конкретный УЦ с запасом
относительно его текущего CRL; готовых рекомендуемых чисел библиотека не даёт.

Рост лимитов увеличивает память, которую удерживает проверенный CRL (см. «Кэш проверенных CRL»
ниже); значения ≤ 0 отвергаются при создании.

Превышение предела записей -- отказ проверки с причиной `CRL_LIMIT_EXCEEDED` при `IF_CDP_PRESENT` и
`REQUIRE`: такой CRL не равносилен недоступному адресу и не пропускается. CRL ФНС содержит 829 548
записей (83% предела записей) и занимает 38,9 МиБ (61% предела размера), поэтому первым упрётся
число записей; пределы поднимают вместе.

==== Кэш проверенных CRL

Хэш, подпись ГОСТ и строгий разбор записей не зависят от проверяемого сертификата, поэтому
менеджер доверия выполняет их один раз и хранит результат до `nextUpdate` (плюс допуск часов).
На каждом соединении остаётся проверка самого сертификата по готовому объекту:
`thisUpdate` и срок, издатель, `cRLNumber`, запись об отзыве, область CRL. Измерение на синтетическом CRL
с 800 000 записей (по размеру близок к CRL ФНС): проверка одного CRL занимала около 0,84 с и
около 400 МиБ мусора на каждое соединение, теперь это один раз на `nextUpdate`.

* *Одна загрузка на адрес.* Если CRL нет в кэше, его загружает и проверяет один поток, остальные
соединения ждут и проверяют по тому же объекту свои сертификаты. Ожидание ограничено остатком
бюджета проверки (30 с на проверку цепочки): ожидающий, не дождавшийся CRL, считает адрес
недоступным. Поэтому при `IF_CDP_PRESENT` он пропускает проверку отзыва, как при недоступном CDP
(в том числе когда подлинный CRL просто ещё не загрузился), а при `REQUIRE` получает отказ.
Об этом пишется одна запись в журнале на серию сдач по адресу (после успешной загрузки следующая сдача снова пишется). Загрузка инициатора от сдачи ожидающего не
страдает. Собственный `CrlFetcher` по-прежнему обязан ограничивать время загрузки; проверка
подписи загруженного CRL срока не имеет. Ошибка загрузки не кэшируется.
* *Перепроверка раньше `nextUpdate`* (`crlMaxAge`, по умолчанию 6 часов). Если УЦ выпустил новый
CRL раньше, чем истекает загруженный, кэш его не видит. Запись, загруженная давнее `crlMaxAge`,
но ещё не истёкшая, перепроверяется: одно соединение (первое, поставившее отметку на адрес) грузит
CRL заново, остальные не ждут и берут действующую запись. Больший `cRLNumber` заменяет запись;
тот же номер только сбрасывает возраст; меньший номер или отсутствие номера при известном --
признак отката, запись остаётся, в журнал пишется ERROR. Если перепроверка не удалась, запись
остаётся до `nextUpdate`, возраст не сбрасывается, следующая попытка по адресу не раньше чем
через 5 минут (или `crlMaxAge`, если он меньше), а в журнал пишется одно предупреждение на серию
неудач. Это сознательное ослабление свежести ради доступности: при `REQUIRE` отзыв,
опубликованный после загрузки, не виден до `nextUpdate`, пока сервер недоступен.
+
*Задержка видимости нового CRL равна `crlMaxAge` плюс интервал, с которым УЦ выпускает CRL*, а не
самому `crlMaxAge`: при ежесуточной публикации и 6 часах худший случай около 30 часов. Если
между перепроверками УЦ не выпустил новый CRL, перепроверка принесёт тот же CRL. Для повышенных
требований безопасности разумны 1--6 часов, но пока идёт перепроверка, в куче лежат старая и
новая записи: бюджет `crlCacheMaxBytes` должен вмещать две самые большие разобранные записи. Одно соединение раз в
`crlMaxAge` на каждый адрес может занять до потолка проверки (около 60 с) плюс срок загрузчика
CRL. Перепроверка защищает от устаревшего кэша в обычных условиях, а не от подмены ответа на канале.
+
*Условный запрос.* Перепроверка идёт с `If-Modified-Since`: загрузчик посылает серверу значение
`Last-Modified` прошлого ответа строкой как есть (`If-None-Match` не посылается), и ответ 304
означает «CRL не изменился», тело не загружается, разбор и проверка подписи не повторяются.
Валидатор хранится вместе с записью; его принимают и обязательные, и перепроверочные полные
загрузки, поэтому условной бывает уже первая перепроверка. Валидатор принимается, только если он
короткий, из печатных ASCII и разбирается как HTTP-дата; ответ без `Last-Modified` его очищает.
Условный запрос посылается только на исходный адрес: адреса, которые отвечают перенаправлением,
перепроверяются полной загрузкой. Сервер вправе ответить 200 вместо 304: это обычная полная
загрузка. Проверка на большом CRL ФНС (около 40 МБ, IIS 10, 8 ноября 2026): ответ 304 приходит
без тела, но за адресом несколько узлов с разной датой файла. С валидатором от более старого узла
5 из 12 запросов дали 304, остальные 200 с полным телом; с валидатором от более нового узла 16 из
16 запросов дали 304. Клиент после ответа 200 запоминает его `Last-Modified`, поэтому валидатор
сходится к дате более нового узла: на публикацию CRL приходится не больше двух полных загрузок, а
между публикациями перепроверка стоит несколько сотен байт. При нескольких узлах за одним адресом
ответ 304 означает «на этом узле не новее», а не «нового CRL нет»: от устаревшей копии защищают
проверка отката `cRLNumber`, пауза и граница `nextUpdate`. Дата `Last-Modified` из ответа 304
не читается совсем: по смыслу 304 дата файла не позже отправленной, более ранняя откатила бы
валидатор (следующий запрос к более новому узлу стал бы полной загрузкой), а более поздняя
противоречит RFC 9110 и увела бы валидатор вперёд без тела, и новый CRL перестал бы приходить до
`nextUpdate`. Валидатор двигает только ответ 200, где тело и дата согласованы. Дата из будущего в
ответе 200 (сбой часов сервера) даёт 304 до `nextUpdate`: граница свежести остаётся `nextUpdate`,
как у любого неподписанного 304. Если CDP не
отдаёт `Last-Modified` или CRL большой и адрес отвечает перенаправлением, каждая перепроверка --
полная загрузка, и `crlMaxAge` стоит увеличить. Собственный `CrlFetcher` без метода
`fetchConditional` работает как раньше, но перепроверяется полной загрузкой. *Ответ 304 не
подписан:* любой, кто управляет каналом до http-CDP, может отвечать «не изменился», пряча обновление до
`nextUpdate`; хуже, чем без перепроверки, это не делает.
* *Ключ кэша* -- адрес CRL и сертификат издателя: один адрес у двух издателей не смешивается.
* *Бюджет* `crlCacheMaxBytes` (по умолчанию 512 МиБ). Разобранный CRL удерживает около шести
байт кучи на байт DER (CRL ФНС: около 233 МиБ при 40 МБ DER). Бюджет -- верхняя граница, а не
занятая память; он общий для разобранных и сырых записей. Если разобранный CRL не помещается, но
помещается его DER, хранится сырой DER: сеть используется один раз, а проверка подписи и разбор
повторяются на каждом соединении. Если не помещается и DER, CRL загружается заново на каждом
соединении (в журнал пишется предупреждение). Значение 0 запрещает хранить CRL между
соединениями. Бюджет должен быть не меньше оценки самого большого ожидаемого CRL; для устройств
с малой памятью его уменьшают.
* *Защита от отката.* Последний известный `cRLNumber` хранится отдельно от записей и не
теряется ни при истечении, ни при вытеснении, ни при нулевом бюджете.
* *Кэш принадлежит менеджеру доверия*: у каждого `SSLContext` своя копия CRL и своя загрузка.
Просроченный объект освобождается при следующем обращении к кэшу.
* Подлинный CRL, не покрывающий данный сертификат (другой сегмент, `onlyContainsCACerts`),
тоже кэшируется: он годится другим сертификатам. Для своего сертификата соединение получает
отказ области на каждом соединении без повторной загрузки.
* Прерывание потока при загрузке CRL даёт отказ проверки, а не переход к следующему адресу.
=== GostSSLEngine (низкоуровневый API)

`GostSSLEngine` предназначен для неблокирующих интеграций (NIO, Netty,
кастомные selector-циклы). Управление handshake — через wrap/unwrap
с `ByteBuffer`.

[source,java]
----
import org.rssys.gost.jsse.engine.GostSSLEngine;
import org.rssys.gost.jsse.manager.GostX509KeyManager;
import org.rssys.gost.jsse.manager.GostX509TrustManager;
import org.rssys.gost.tls13.TlsConstants;

import javax.net.ssl.SSLEngineResult;
import java.nio.ByteBuffer;

GostSSLEngine clientEngine = GostSSLEngine.createForClient(
        km, tm, "host", 8443, null /* без PSK-контекста */);

clientEngine.beginHandshake();
ByteBuffer netOut = ByteBuffer.allocate(TlsConstants.MAX_CIPHERTEXT_LENGTH + 64);
ByteBuffer netIn = ByteBuffer.allocate(TlsConstants.MAX_CIPHERTEXT_LENGTH + 64);
ByteBuffer appBuf = ByteBuffer.allocate(TlsConstants.MAX_PLAINTEXT_LENGTH);

clientEngine.wrap(ByteBuffer.allocate(0), netOut);   // ClientHello
netOut.flip();
// отправить netOut пиру
// прочитать ответ пира в netIn, затем:
netIn.flip();
SSLEngineResult result = clientEngine.unwrap(netIn, appBuf);
----

Дальше цикл повторяется по `getHandshakeStatus()`: `NEED_WRAP` — `wrap()`, `NEED_UNWRAP` —
`unwrap()`, `NEED_TASK` — выполнить `getDelegatedTask()`. Полный цикл — в
`GostSSLEngineLoopbackTest.java` (`doClientHandshake()` / `doServerHandshake()`).

==== max_fragment_length

Клиент может попросить уменьшить максимальный размер фрагмента (RFC 6066 §4): коды `1`..`4` —
512, 1024, 2048 и 4096 байт. Запрос задаётся до `beginHandshake()`.

[source,java]
----
clientEngine.setClientMaxFragLenRequest(3);   // 2048 байт
clientEngine.beginHandshake();
// после рукопожатия:
int code = clientEngine.getMaxFragmentLength();   // 3; 0 — размер по умолчанию
----

Для сокета — `((GostSSLSocket) s).setMaxFragmentLengthRequest(3)` до `startHandshake()`.
Сервер принимает запрос автоматически: код возвращается в `EncryptedExtensions`. Ограничение
действует на сообщения рукопожатия и на `application_data`. Неверный код —
`IllegalArgumentException`, вызов после начала рукопожатия — `IllegalStateException`.

==== Наборы шифров, параметры и закрытие

*Включённые наборы шифров и протоколы действуют.* Движок предлагает (клиент) и принимает
(сервер) только наборы из `setEnabledCipherSuites`, а TLS 1.3 должен быть в `setEnabledProtocols`.
Как и в JDK, пустой массив принимается сеттером, но рукопожатие тогда завершается
`SSLHandshakeException`; неизвестное имя отвергается сразу (`IllegalArgumentException`).
Серверу контейнера (например, Tomcat через `SSLUtil.getEnabledCiphers()`) нужно отдавать
`GostJsseConstants.supportedCipherSuites()`: пустой список теперь означает «наборов нет».

*Параметры снимаются при `beginHandshake()`.* Сеттеры и геттеры параметров берут замок движка, как
в JDK: рукопожатие видит либо все значения одного вызова `setSSLParameters`, либо ни одного.
Наборы, протоколы, режим аутентификации клиента,
алгоритм проверки имени и протоколы ALPN, заданные позже (`setEnabledCipherSuites`,
`setSSLParameters`), видны через геттеры, но на уже идущее рукопожатие не влияют. В частности,
поздний `setSSLParameters` с отключённой проверкой имени не отключает сверку имени у текущего
рукопожатия. `setSSLParameters` задаёт режим аутентификации клиента полностью, как в JDK:
`needClientAuth` включает обязательный режим, иначе `wantClientAuth` включает запрашиваемый,
иначе сертификат клиента не запрашивается; пустой массив ALPN снимает ранее заданные протоколы.

*Закрытие.* Контракт близок к JDK, с одним отличием (последний пункт):

* после `closeOutbound()` `wrap()` отдаёт `close_notify` со статусом `CLOSED`, повторный `wrap()`
  возвращает `CLOSED` без байтов; `isOutboundDone()` истинно, когда закрывающая запись отдана
  (до этого приложение обязано вызвать `wrap()`);
* после `close_notify` пира `unwrap()` сначала выдаёт данные, расшифрованные до закрытия, затем
  `CLOSED`; пока остаток не выдан, статус `OK` (или `BUFFER_OVERFLOW`, если выдавать некуда);
  `isInboundDone()` истинно после выдачи этих данных;
* `closeInbound()` означает отказ приложения читать дальше: невыданные данные затираются, и это
  верно также после `close_notify` пира;
* после отказа (fatal alert) исключение с кодом alert остаётся при каждом `unwrap()`, а
  невыданные данные затираются; `wrap()` отдаёт alert пиру один раз, затем `CLOSED`;
* *отличие от JDK:* `closeInbound()` без `close_notify` пира закрывает и выходную сторону: `isOutboundDone()` истинно,
  `wrap()` возвращает `CLOSED` без записи, потому что ключи записи уничтожены и отвечать нечем.
  В JDK `closeInbound()` выходную сторону не трогает; здесь иначе, чтобы цикл контейнера по
  `isOutboundDone()` завершался.

`SSLSession.getPacketBufferSize()` вмещает запись наибольшей длины вместе с заголовком.

==== Экспорт ключевого материала (привязка к каналу)

После рукопожатия сессия соединения выводит одинаковые секретные байты на обеих сторонах
(RFC 8446 §7.5): для `tls-exporter` (RFC 9266, SCRAM-PLUS), EAP-TLS 1.3, NTS.

[source,java]
----
import org.rssys.gost.jsse.engine.GostSSLSession;

GostSSLSession session = (GostSSLSession) engine.getSession();
byte[] channelBinding = session.exportKeyingMaterialData("EXPORTER-Channel-Binding", null, 32);
try {
    // передать в протокол аутентификации
} finally {
    java.util.Arrays.fill(channelBinding, (byte) 0); // значение секретное
}
----

Сигнатуры `exportKeyingMaterialData` и `exportKeyingMaterialKey` совпадают с `ExtendedSSLSession` из JDK 25.
Проект собирается под JDK 21 и Android 14, поэтому методы объявлены без `@Override`: на JDK 25 и новее они
переопределяют стандартные, и приложение может вызывать их через `ExtendedSSLSession` (так делают драйверы БД),
на более ранних версиях это обычные методы класса `GostSSLSession`.

Контракт исключений повторяет JDK: `NullPointerException` для `label` и `keyAlg`, `IllegalArgumentException`
для длины, метки (1-249 байт в UTF-8), контекста (до 255 байт) и пустого `keyAlg`, `IllegalStateException`
до завершения рукопожатия. Отличие от JDK: после закрытия соединения экспорт недоступен (секрет живёт в движке и
затирается при закрытии), а `invalidate()` его на живом соединении не отключает.

NOTE: RFC 9367 экспорт для ГОСТ-наборов не определяет. Значения сверены с OpenSSL (gost-provider), совместимость
с другими ГОСТ-реализациями не проверялась.

import org.rssys.gost.signature.PrivateKeyParameters;
import org.rssys.gost.pkix.cert.GostPkcs12Loader;
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.TrustAnchors;

import javax.net.ssl.SSLContext;
import javax.net.ssl.TrustManager;

import java.nio.file.Paths;
import java.security.Security;
import java.util.List;

        CertificateBridge.toJca(tlsChain);

// Шаг 3: KeyManager
GostX509KeyManager km = new GostX509KeyManager();

// Шаг 4: TrustManager — загрузка CA
byte[] caDer = Files.readAllBytes(Paths.get("ca.der"));

GostX509TrustManager tm =
        GostX509TrustManager.fromTrustAnchors(TrustAnchors.ofCertificate(caCert));

// Шаг 5: SSLContext
SSLContext sslContext = SSLContext.getInstance("TLSv1.3", "RssysGostJsse");
sslContext.init(new KeyManager[]{km}, new TrustManager[]{tm}, null);
----

.Клиент (mTLS):
[source,java]
----
import org.rssys.gost.netty.GostSslContext;
import org.rssys.gost.netty.GostSslContextBuilder;
import org.rssys.gost.jsse.manager.GostX509KeyManager;

import io.netty.bootstrap.Bootstrap;
import io.netty.channel.ChannelInitializer;
import io.netty.channel.EventLoopGroup;
import io.netty.channel.MultiThreadIoEventLoopGroup;
import io.netty.channel.nio.NioIoHandler;
import io.netty.channel.socket.SocketChannel;
import io.netty.channel.socket.nio.NioSocketChannel;

// Клиентский KeyManager для mTLS (опционально — только если нужен mTLS)
GostX509KeyManager clientKm = new GostX509KeyManager();
clientKm.addKeyEntry("client", clientChain, clientPrivateKey);

GostSslContext clientCtx = GostSslContextBuilder.forClient()
        .trustManager(tm)
        .keyManager(clientKm)                          // для mTLS
        .applicationProtocols("h2", "http/1.1")
        .build();

EventLoopGroup group = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());
try {
    Bootstrap b = new Bootstrap();
    b.group(group)
     .channel(NioSocketChannel.class)
     .handler(new ChannelInitializer<SocketChannel>() {
         @Override
         protected void initChannel(SocketChannel ch) {
             ch.pipeline().addLast(
                     clientCtx.newHandler(ch.alloc(), "host", 8443));
             ch.pipeline().addLast(new MyClientHandler());
         }
     });
    ChannelFuture f = b.connect("host", 8443).sync();
    f.channel().closeFuture().sync();
} finally {
    group.shutdownGracefully();
}
----

Клиентский контекст проверяет имя узла в сертификате сервера (RFC 6125), поэтому
обработчик нужно создавать с узлом: `newHandler(alloc, host, port)`. Без узла
рукопожатие отказывает до отправки ClientHello, пока проверка не отключена
осознанно через `withoutHostnameVerification()` (небезопасно, только для закрытых сетей и тестов).

.Режимы mTLS и политика OCSP клиента (серверный builder):
* `.clientAuth(ClientAuth.REQUIRE)` — клиентский сертификат обязателен, `.clientAuth(ClientAuth.OPTIONAL)` — опционален;
* `.clientOcspPolicy(ClientOcspPolicy.REQUIRE)` — требовать OCSP-staple клиентского сертификата (только при `OPTIONAL` или `REQUIRE`).

.ALPN:
* Приоритет у списка сервера: выбирается первый протокол сервера, который есть у клиента.
* Списки есть у обеих сторон, общего протокола нет: сервер завершает рукопожатие алертом `no_application_protocol` (120).
* ALPN настроен только у одной стороны: рукопожатие проходит, `applicationProtocol()` равен `null`; запасной протокол выбирает приложение (например, `ApplicationProtocolNegotiationHandler`).

.Доступ к движку:
* `newHandler(...)` возвращает обработчик над «сырым» `GostSSLEngine`: приведение
  `(GostSSLEngine) handler.engine()` работает всегда, в том числе при ALPN. Это нужно для
  `setOcspResponse` (клиентский staple при mTLS), `initiateKeyUpdate` и других методов движка.
  Вызывайте их до добавления обработчика в канал: Netty начинает рукопожатие при добавлении.
* `newEngine(...)` объявлен `final` в Netty. При ALPN движок возвращается в закрытой обёртке,
  и приведение к `GostSSLEngine` невозможно. Путь годится, только если `SslHandler` создаёт
  сам фреймворк.

.Сессии:
* `sessionCacheSize(n)` — размер кэша JSSE-сессий: 0 снимает предел, по умолчанию 20 480.
  Тикеты возобновления (PSK) хранятся отдельно, предел хранилища фиксирован (1000).
* `sessionTimeout(s)` — тайм-аут сессии в секундах.
* Внешний контекст (`sessionContext(...)`) разделяет только PSK-тикеты и привязки host:port;
  тайм-аут, размер кэша, режим проверки имени и политика OCSP остаются у создаваемого контекста.


==== HTTP/2 и gRPC на Netty

HTTP/2 поверх ГОСТ TLS проверяется настоящими кадрами, а не только согласованием ALPN:
`GostSslContextHttp2Test` поднимает сервер и клиент на `Http2FrameCodec` и
`Http2MultiplexHandler`, а тесты `examples/jsse` проверяют сервер Netty клиентом OkHttp —
независимой реализацией протокола. Рабочие примеры: `make -C examples/jsse http2`
(`Http2EchoServer`) и `make -C examples/jsse grpc` (`GrpcEchoServer`). В fat-jar `gost-curl`
зависимости HTTP/2 и gRPC не входят.

Зависимость:

[source,xml]
----
<dependency>
    <groupId>io.netty</groupId>
    <artifactId>netty-codec-http2</artifactId>
    <version>4.2.20.Final</version>
</dependency>
----

[source,java]
----
GostSslContext serverCtx = GostSslContextBuilder.forServer(km)
        .applicationProtocols("h2", "http/1.1")     // без ALPN клиент HTTP/2 не согласует протокол
        .build();

// В ChannelInitializer сервера
ch.pipeline().addLast(serverCtx.newHandler(ch.alloc()));
ch.pipeline().addLast(new ApplicationProtocolNegotiationHandler("http/1.1") {
    @Override
    protected void configurePipeline(ChannelHandlerContext ctx, String protocol) {
        if ("h2".equals(protocol)) {
            ctx.pipeline().addLast(Http2FrameCodecBuilder.forServer().build(),
                    new Http2MultiplexHandler(new MyStreamInitializer()));
        } else {
            ctx.close();
        }
    }
});
----

* Обработчик создавайте через `newHandler(...)`: при этом `handler.engine()` остаётся
  `GostSSLEngine`, и до добавления обработчика в канал можно вызвать, например,
  `setOcspResponse` (клиентский OCSP-staple при mTLS). Сочетание HTTP/2, mTLS и обязательного
  staple проверено тестом.
* Клиент обязан создавать обработчик с узлом: `newHandler(alloc, host, port)`, иначе
  рукопожатие отказывает до отправки ClientHello (проверка имени узла включена по умолчанию).
* Клиент OkHttp в примерах (`Http2Clients`) отключает собственный `hostnameVerifier`, потому что имя узла
  сверяет `GostX509TrustManager` внутри рукопожатия, а OkHttp не знает ГОСТ-сертификаты. Это не
  то же, что `withoutHostnameVerification()`: проверка имени остаётся включённой. В своём коде не
  копируйте такую настройку без проверки имени на стороне движка.

.gRPC
Нешейденный `grpc-netty` (проверен 1.85.1 на Netty 4.2.20) работает с `GostSslContext`: унарные
вызовы, серверные потоки и mTLS проверены тестом `GrpcTest`, пример `GrpcEchoServer`.

[source,xml]
----
<dependency>

    <artifactId>grpc-netty</artifactId>   <!-- не grpc-netty-shaded -->
    <version>1.85.1</version>
</dependency>
<dependency>
    <groupId>io.grpc</groupId>
    <artifactId>grpc-stub</artifactId>
    <version>1.85.1</version>
</dependency>
<dependency>
    <groupId>io.grpc</groupId>
    <artifactId>grpc-api</artifactId>

[source,java]
----
Server server = NettyServerBuilder.forPort(8443).sslContext(serverCtx).addService(svc).build();
ManagedChannel channel = NettyChannelBuilder.forAddress("host", 8443).sslContext(clientCtx).build();
----

* `sslContext(...)` принимает Netty `SslContext`, то есть `GostSslContext`, а не
  `javax.net.ssl.SSLContext`.
* ALPN `h2` обязателен на обоих контекстах: `applicationProtocols("h2")`. Без него gRPC отвергает
  контекст ещё при настройке (`ensureAlpnAndH2Enabled`).
* gRPC сам создаёт движок через `newEngine(...)` и свой `SslHandler`. Движок при этом скрыт в
  обёртке Netty: `GostSSLEngine`, клиентский и серверный OCSP-staple через gRPC недоступны.
* Адрес канала должен совпадать с SAN сертификата сервера (клиентский контекст проверяет имя узла).
* `grpc-netty-shaded` не подходит: у него свой перемещённый `SslContext`, и `GostSslContext` к
  нему не применим.
* Netty и gRPC в проекте задаются одной версией через `netty-bom` и `grpc-bom`; смешивать
  `netty-codec-http2` другой версии с `netty-handler` нельзя.

[source,java]
----
import org.eclipse.jetty.server.HttpConfiguration;
import org.eclipse.jetty.server.HttpConnectionFactory;
import org.eclipse.jetty.server.Request;
import org.eclipse.jetty.server.Response;
import org.eclipse.jetty.server.Server;
import org.eclipse.jetty.server.ServerConnector;
import org.eclipse.jetty.server.SslConnectionFactory;
import org.eclipse.jetty.server.Handler;
import org.eclipse.jetty.util.Callback;
import org.eclipse.jetty.util.ssl.SslContextFactory;

import java.nio.charset.StandardCharsets;

// SslContextFactory принимает готовый SSLContext
SslContextFactory.Server scf = new SslContextFactory.Server();
scf.setSslContext(sslContext);
scf.setIncludeProtocols("TLSv1.3");

Server server = new Server();
ServerConnector connector = new ServerConnector(server,
        new SslConnectionFactory(scf, "http/1.1"),
        new HttpConnectionFactory(new HttpConfiguration()));
connector.setPort(8443);
server.addConnector(connector);

// Handler.Abstract — Jetty 12 core handler API (блокирующий обработчик)
server.setHandler(new Handler.Abstract() {
    @Override
    public boolean handle(Request request, Response response, Callback callback) {
        try {
            String body = org.eclipse.jetty.io.Content.Source.asString(
                    request, StandardCharsets.UTF_8).trim();
            if ("PING".equals(body)) {
                response.setStatus(200);
                org.eclipse.jetty.io.Content.Sink.write(
                        response, true, "PONG\n", callback);
            } else {
                callback.succeeded();
            }
            return true;
        } catch (Exception e) {
            callback.failed(e);
            return true;
        }
    }
});
server.start();
----

Взаимная аутентификация (mTLS) включается на стороне сервера флагом

=== Возобновление сессии по PSK

После полного рукопожатия сервер выдаёт `NewSessionTicket`, клиент сохраняет тикет в
`GostSSLSessionContext`, и следующее соединение с тем же сервером возобновляется без обмена
сертификатов. Результат показывает `wasResumed()` у `GostSSLEngine` и `GostSSLSocket`: до завершения рукопожатия метод
бросает `IllegalStateException`, после завершения возвращает его итог, в том числе после закрытия.

Возобновление не показывает сертификат и наследует проверку исходного рукопожатия, поэтому
клиентский тикет привязан к серверу и модели доверия:

* к имени узла (без учёта регистра) и порту;
* к режиму проверки имени: тикет, полученный на engine без проверки имени, не используется engine
  с HTTPS, и наоборот;
* к экземпляру `GostX509TrustManager` (`bindingId()`): якоря, политики, загрузчики отзыва и
  будущие настройки охватываются одним идентификатором. Создавайте один менеджер доверия на
  `SSLContext` и переиспользуйте его: engine с разными экземплярами менеджера возобновление не
  делят, а тикет не переживает пересоздание менеджера.

Сервер привязывает тикет к SNI клиента и при другом SNI не принимает его (RFC 6066 §3).

Тикет не переживает сертификат сервера. Клиент запоминает границу доверия: наименьший `notAfter` среди
сертификатов, по которым сервер принят (`GostX509TrustManager.validateChainWithOcsp` возвращает проверенную
цепочку без якоря, срок которого проверка не учитывает; в режиме `insecureTrustAll` берётся срок leaf).
Срок тикета ограничивается остатком до границы, запись просрочена строго после неё, а новые тикеты
возобновлённой сессии наследуют границу прежней. Сервер ограничивает `ticket_lifetime` сроком собственной
цепочки и не выдаёт тикет, если остаток меньше секунды.

WARNING: Не используйте один `GostSSLSessionContext` для клиента и сервера (в том числе через
`redirectToSharedState` и `GostSslContextBuilder.sessionContext`): клиентская и серверная записи с
одним тикетом имеют разные привязки, а ключ хранилища — байты тикета, поэтому они затирают друг
друга и возобновление молча отключается. Общий контекст между клиентскими контекстами с разными
менеджерами доверия возобновления не даёт, это намеренно.

NOTE: Возобновление подтверждено кросс-валидацией для MGM L и S: клиент `GostSSLEngine`
возобновляется с сервером OpenSSL (GC256B и GC256A; для GC256A задайте группу через
`setClientNamedGroup`), клиенты OpenSSL и КриптоПро (`csptest`) — с сервером `GostSSLEngine`.
Работает и через HelloRetryRequest: binder второго ClientHello по RFC 8446 §4.2.11.2. Группа по
умолчанию — GC256B в обеих ролях; задавайте её заранее, чтобы не тратить обмен на HRR.


=== Исключения при ошибках рукопожатия

Алерт TLS отображается в исключение по таблице JDK (`sun.security.ssl.Alert`), а не по фазе соединения. Алерты
рукопожатия, в том числе сертификатные (`bad_certificate`, `unknown_ca`, `certificate_expired`) и `decrypt_error`
(неверные `Finished`, подпись `CertificateVerify`, PSK binder), дают `SSLHandshakeException`; `unexpected_message`
и неизвестный код - `SSLProtocolException`; `bad_record_mac`, `record_overflow`, `internal_error` - `SSLException`.
`SSLPeerUnverifiedException` бросают только методы сессии (`getPeerCertificates()`), когда сертификата пира нет.

=== Логирование

Модуль пишет в `java.util.logging` через обёртку модуля core. Имя логгера — полное имя класса
(`org.rssys.gost.jsse.engine.GostSSLEngine`, `org.rssys.gost.jsse.manager.GostX509TrustManager`,
`org.rssys.gost.jsse.crl.CrlCache`), поэтому уровень настраивается и для класса, и для пакета.
Записи экземпляра движка помечаются префиксом `[conn#N]` (`GostSSLEngine.getConnectionLabel()`):
номер выдаётся при создании движка и не является идентификатором сессии. Фабричные предупреждения
(`applyEndpointIdentification`, `createForClientNoHostnameCheck`) идут без префикса; записи общего
`GostX509TrustManager` номера соединения не имеют — он обслуживает параллельные рукопожатия,
корреляция по серийному номеру и времени. Уровни, включение и правила о том, что не попадает в
журнал, — в разделе «Логирование» файла `crypto-gost-core/README.adoc`.

* `DEBUG`: успешные операции (загрузка OCSP, принятие клиентского сертификата, сохранение CRL в
  кэше), ход сетевой загрузки (код ответа, перенаправление, тип содержимого, блокировка адреса),
  отказ сертификата собеседника (одна запись: стадия, имя alert, очищенный текст; причина остаётся
  в исключении) и отказ рукопожатия (стадия, alert, тип исключения без текста). Итог рукопожатия
  пишет набор шифров IANA-именем и кодом (`TLS_GOSTR341112_256_WITH_KUZNYECHIK_MGM_L (0xc103)`).
  Для разбора mTLS включите `DEBUG` для `org.rssys.gost.jsse`: отказ клиентского сертификата по
  умолчанию не пишется, чтобы внешний узел не мог заполнить журнал.
* `WARNING`: отказ, который библиотека обработала сама, и ослабленные режимы. Отказ загрузки CRL
  или OCSP пишется один раз менеджером доверия: серийный номер, адрес без учётных данных и
  параметров запроса, причина (`TIMEOUT`, `NETWORK`, `HTTP_STATUS`, `ADDRESS_BLOCKED` и другие
  значения `FetchFailure`). Загрузчики в журнал сами не пишут: причина приходит в результате
  (`OcspFetchResult.failure()`, `CrlFetchResult.failure()`). Отзыв — одна WARNING с серийным
  номером (для CRL — с адресом списка).
* DN собеседника в записи `Handshake completed` усечён, SNI и ALPN очищены. Управляющие символы в
  SAN и других IA5String отвергаются при разборе сертификата и не попадают ни в журнал, ни в
  сообщение исключения.
* Текст исключения HTTP-клиента или стороннего загрузчика в журнал не попадает: он недоверен и
  может нести адрес с учётными данными.
* `ERROR` не используется там, где отказ обработан: превышение размера CRL, отзыв по CRL и откат
  `cRLNumber` пишутся на `WARNING`, а решение остаётся за исключением.

Приложение с SLF4J перенаправляет `java.util.logging` мостом `jul-to-slf4j`.

=== Потокобезопасность (Thread safety)

`GostSSLEngine` разрешает параллельные `wrap()` и `unwrap()` из разных
потоков: вызовы сериализуются одним `ReentrantLock`, как в JDK. Проверка цепочки
сертификатов (`NEED_TASK`) идёт вне замка.

`GostSSLSocket` потокобезопасен после завершения рукопожатия: чтение и запись могут идти из
разных потоков, для них три независимых замка — handshake, read и write. Замки сокета всегда
берутся раньше замка движка, никогда наоборот.

`GostSSLSocket.getSession()` по контракту `SSLSocket` запускает рукопожатие и ждёт его.
Из обратного вызова рукопожатия (например, селектора ALPN) он возвращает текущую сессию без
повторного запуска. При отказе рукопожатия возвращается пустая сессия
(`SSL_NULL_WITH_NULL_NULL`) без исключения, а сокет закрывается: после отказа рукопожатия
(ошибка протокола, обрыв соединения, непредвиденный сбой) `SSLSocket` закрыт и дальнейший обмен
невозможен. Тайм-аут чтения (`setSoTimeout`) не роковой, как в JDK: сокет остаётся открытым,
повторный `startHandshake()` или `read()` продолжает рукопожатие, а посреди TLS-записи уже
прочитанные байты не теряются.

`GostSSLEngine.initiateKeyUpdate()` ставит обновление ключа, которое уходит при следующем
`wrap()`. Повторный вызов до отправки объединяется с ним: секрет записи сдвигается один раз, а
запрос `update_requested` повышает стоящее обновление и не теряется. Так же ведёт себя
`TlsSession.initiateKeyUpdate()` (tls13).

`GostX509TrustManager` thread-safe — OCSP-кэш использует `ConcurrentHashMap`.

`GostX509KeyManager` thread-safe — хранилище entry'ей использует
`CopyOnWriteArrayList` (read-heavy, lock-free reads, редкие writes).

`GostSSLSessionContext` thread-safe — PSK-хранилище использует
`InMemoryPskStore` (thread-safe), карта сессий — `LinkedHashMap` с
LRU-вытеснением под `ReentrantLock`.


=== Мост сертификатов

JSSE работает с `java.security.cert.X509Certificate`, а модуль pkix — с `GostCertificate`.
`CertificateBridge` переводит типы в обе стороны:

[source,java]
----
import org.rssys.gost.jsse.bridge.CertificateBridge;
import org.rssys.gost.pkix.cert.GostCertificate;

import java.security.cert.X509Certificate;
import java.util.List;

GostCertificate gost = new GostCertificate(der);
X509Certificate jca = CertificateBridge.toJca(gost);
List<GostCertificate> chain = CertificateBridge.toGost(jcaChain);
----

`toJca()` принимает `GostCertificate` или `List<GostCertificate>`, `toGost()` — `X509Certificate`
или `X509Certificate[]`. Мост нужен при ручной сборке `GostX509KeyManager`: `addKeyEntry` ждёт
JCA-цепочку. Для production сертификаты и ключи берите из PKCS12 (см. «Конфигурация сервера»).


=== Безопасность реализации

* `GostX509TrustManager` — fail-closed для серверного сертификата: при
отсутствии OCSP-ответа (политика `STAPLING_REQUIRED` или `STAPLING_OR_FETCH`
без успешного fetch) сертификат считается невалидным. Для клиентских
сертификатов OCSP не обязателен: при `STAPLING_OR_FETCH` выполняется
best-effort fetch, при `STAPLING_REQUIRED` загрузка не выполняется. Клиентский
staple запрашивается только политикой `ClientOcspPolicy` (по умолчанию `OFF`).
`CrlPolicy.REQUIRE` обеспечивает строгий отзыв только при отсутствии OCSP-ответа:
если OCSP получен и валиден, CRL не проверяется.
* Constant-time сравнения для verify_data и PSK binders.
* Пустой `getAcceptedIssuers()` — не раскрываем список доверенных CA клиенту
(защита от fingerprinting).
* Затирание ключевого материала при close, fatal alert, exception.
* OCSP-кэш с TTL (1 час по умолчанию).
* Защита от downgrade: только TLSv1.3, только ГОСТ-наборы.


=== Ограничения

* Только TLS 1.3 (TLS 1.2 и ниже не поддерживаются).
* Только ГОСТ-наборы (`TLS_GOSTR341112_256_WITH_KUZNYECHIK_MGM_L/S`).
* Сервер не принимает PSK-тикет повторно (RFC 8446 §8.1); клиент хранит полученные тикеты до
  вытеснения.
* PSK-тикет клиента привязан к серверу, режиму проверки имени и экземпляру `GostX509TrustManager`
  (см. «Возобновление сессии по PSK»).
* При `needClientAuth` и `wantClientAuth` сервер не выдаёт `NewSessionTicket`:
  PSK-resumption обошёл бы повторную аутентификацию клиента.
* KeyManagerFactory — только алгоритм `GostX509` (не `PKIX`, не `NewSunX509`).
* Проверка nonce в OCSP-ответах — ответственность приложения (RFC 8954).


=== Примеры интеграции с серверами приложений

Все примеры интеграции с популярными серверами находятся в модуле `examples/jsse` и запускаются через
Makefile из его корня:

[source,sh]
----
# Все серверные примеры последовательно
make -C examples/jsse all

# По одному
make -C examples/jsse netty
make -C examples/jsse http2
make -C examples/jsse grpc
make -C examples/jsse jetty
make -C examples/jsse undertow
make -C examples/jsse tomcat

# Spring Boot — интерактивно
make -C examples/jsse springboot

# Spring Boot — CI-тест (@SpringBootTest + GostSSLSocket)
make -C examples/jsse test
----

Каждый сервер поднимается на случайном порту, выполняет TLS 1.3
handshake с ГОСТ-наборами, выводит `SUCCESS` и останавливается.
Исключение — `make springboot` (бесконечный цикл, останов через Ctrl+C).

NOTE: Примеры Jetty, Undertow и Tomcat проверяют TLS-рукопожатие; полный HTTP-обмен проверяют
тесты HTTP/2 (`JettyHttp2Test`, `NettyHttp2OkHttpTest`) и `gost-curl`. HTTP/2 в Undertow и Tomcat
поверх ГОСТ TLS не поддерживается (см. разделы выше).


=== Запуск интеграционных тестов

Интеграционные тесты проверяют конкурентность shared state
(`GostSSLSessionContext`, `GostX509KeyManager`), mTLS через Jetty,
PSK resumption, reconnect под нагрузкой и таймауты в сетевых условиях.

Интеграционные тесты помечены `@Tag("integration")` — запуск одной командой:

[source,sh]
----
# Все интеграционные тесты JSSE (20 тестов, 7 файлов)
make -C examples/jsse test-int-all

# Или напрямую через Maven:
mvn test -pl crypto-gost-jsse,examples/jsse -am -Dgroups="integration" -Dsurefire.excludedGroups=

# Отдельные группы:
make -C examples/jsse test-integration   # 16 тестов examples/jsse
make -C examples/jsse test-keymanager    # 3 теста GostX509KeyManager
make -C examples/jsse test-concurrent    # 100 параллельных handshake'ов
----

=== Запуск стресс-теста

Стресс-тест предназначен для выявления: утечек памяти, зависаний, корректности имплементации TLS 1.3 протокола, устойчивость к аварийным обрывам, выявлени максимума одновременных сессий.

Описание методики стресс-теста приведено link:doc/stress-test-05.md[в документе].

[source,sh]
----
# Полный прогон (5 минут)
make -C examples/jsse test-stress

# Быстрый прогон (1 минута)
make -C examples/jsse test-stress ARGS=-Dstress.duration=1

# Через Maven напрямую
mvn test -pl examples/jsse \
  -Dtest="JsseStressTest#stressTest" \
  -Dsurefire.excludedGroups="" \
  -Dstress.duration=5 \
  -Dstress.cacheSize=5000
----

Дополнительный стресс-тест через реальный HTTP-сервер Undertow:

[source,sh]
----
# Undertow: HTTP-профили, Connection: keep-alive (5 минут)
make -C examples/jsse test-undertow-stress

# Быстрый прогон (1 минута)
mvn test -pl examples/jsse -am -Dtest="UndertowStressTest#stressTest" \
  -Dstress.duration=1 -Dsurefire.failIfNoSpecifiedTests=false

# Через Maven напрямую
mvn test -pl examples/jsse -am \
  -Dtest="UndertowStressTest#stressTest" \
  -Dstress.duration=5 -Dsurefire.failIfNoSpecifiedTests=false
----

WARNING: Jetty 12 с `GostSSLSocket` при keep-alive соединениях под нагрузкой
не сбрасывает TLS-буфер после `response.write()` — зашифрованные данные
не доставляются клиенту. Одиночные запросы (`Connection: close`) работают
корректно. Для production-использования  рекомендуется Undertow
или Netty. Баг воспроизводится в Jetty 12.0.19, корень проблемы —
в `SslConnection.flush()`.
