.Модуль `crypto-gost-pkix` содержит ГОСТ-реестр OID, CMS, CAdES, TSP, X.509-сертификаты и PKCS#12:
* *GostOids* — единый реестр объектных идентификаторов (ГОСТ-алгоритмы, PKCS#7/9/12, CAdES, TSP, OCSP, сертификатные расширения).
* *CMS SignedData (RFC 5652 §5 + RFC 4490)* — построение и верификация подписи с signed- и unsigned-атрибутами.
* *CAdES-BES/T (ETSI EN 319 122)* — долговременная электронная подпись: `signingCertificateV2`, метки времени от TSA.
* *CAdES-C (RFC 5126 §6.2)* — полные ссылки на сертификаты и данные отзыва: `complete-certificate-references`, `complete-revocation-references`.
* *CMS Countersignature (RFC 5652 §11.4)* — контрподпись: отдельная подпись поверх подписи автора (нотариус, УЦ).
* *TSP (RFC 3161)* — клиент и сервер службы штампов времени: `TimeStampReq`, `TimeStampResp`, транспорт HTTP,
  разбор запросов (`TspRequest`), построение ответов (`TspResponseBuilder`).
* *CMS EnvelopedData (RFC 5652 §6)* — ГОСТ-шифрование через связку VKO + KExp15 + Кузнечик CTR-ACPKM.
* *CMS SignedAndEnvelopedData* — совмещённая подпись и шифрование: sign-then-encrypt / encrypt-then-sign.
* *GostCertificate* — парсинг и верификация X.509-сертификатов (ГОСТ Р 34.10-2012): подпись, срок, расширения (KeyUsage, EKU, BasicConstraints, SAN, CDP, FreshestCRL, AIA), hostname verification.
* *ChainValidator* — валидация цепочки сертификатов: подписи, DN-связность, KU/EKU, BasicConstraints, pathLen, опционально — CertificatePolicies leaf-сертификата.
* *OCSP/CRL* — верификация OCSP-ответов (RFC 6960) и CRL (RFC 5280 §6.3), разбор OCSP (`GostOcspResponse`, `SingleOcspResponse`), встроенный DER-парсер (`GostDerParser`), хеширование идентификатора сертификата (`CertIdHasher`).
* *X.509-строители:* `GostCertificateBuilder` — сборка сертификатов (TBS + подпись, расширения SAN/KeyUsage/EKU/CDP/AIA/NameConstraints); `GostCrlBuilder` — построение CRL (RFC 5280); `GostCsrBuilder` — построение CSR (RFC 2986 §4.1); `GostCsrParser` — разбор и верификация CSR (proof-of-possession, DN, SPKI, extensionRequest); `GostOcspResponseBuilder` — OCSP-ответы с делегированными сертификатами; `TspResponseBuilder` — TSP-ответы (TimeStampResp), включая rejection и grantedWithMods; `ExtensionsAccumulator` — накопитель общих расширений и канонические статические строители (SAN, KeyUsage, EKU, BasicConstraints, SKI, CertificatePolicies).
* *`GostDnParser.encodeDn()`* — сборка DER Distinguished Name по атрибутам (CN, O, OU, L, ST, C).
* *PKCS#12 (RFC 7292)* — загрузка (`GostPkcs12Loader`/`Pkcs12Loader`), построение (`GostPkcs12Builder`), парсинг (`GostPkcs12Parser`) PFX-контейнеров с нативной поддержкой ГОСТ PBE (PBKDF2-HMAC-Streebog + Кузнечик CTR-ACPKM).
* *DER-кодеки* — базовые CMS-структуры (ContentInfo, AlgorithmIdentifier, IssuerAndSerialNumber, Attribute). Вспомогательные классы расширяют `DerCodec` (core) поддержкой BER indefinite-length.

+
Все криптографические операции выполняются модулем `crypto-gost-core`. Модуль `crypto-gost-pkix`
не имеет внешних зависимостей, кроме core.

=== Быстрый старт

Создаём ключевую пару ГОСТ Р 34.10-2012 (кривая tc26a256) и самоподписанный сертификат.

[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.GostCertificateBuilder;
import org.rssys.gost.pkix.cert.GostDnParser;
import org.rssys.gost.signature.ECParameters;
import org.rssys.gost.api.KeyGenerator;

ECParameters params = ECParameters.tc26a256();
var kp = KeyGenerator.generateKeyPair(params);
byte[] subjectDn = GostDnParser.encodeDn("CN=Demo Cert,O=MyOrg,C=RU");
GostCertificate cert = GostCertificateBuilder.create(params, subjectDn)
        .publicKey(kp.getPublic())
        // Удобный способ: срок 365 дней от текущего момента
        .notBeforeNow()
        .validForDays(365)
        // Альтернатива для воспроизводимости (явные даты):
        // .notBefore("20260101120000Z").notAfter("21060101120000Z")
        .sanDns("gost.example.com")
        .issuerDn(subjectDn)
        .randomSerial()
        // CertificatePolicies (RFC 5280 §4.2.1.4) — опционально:
        .certificatePolicies(GostOids.POLICY_KC1, GostOids.POLICY_KC2)
        // С CPS-квалификатором (ссылка на регламент УЦ):
        // .certificatePolicyInfos(
        //     new CertificatePolicy(GostOids.POLICY_KC1, "https://ca.example.com/cps/russian-ca.html"),
        //     new CertificatePolicy(GostOids.POLICY_KC2))
        .sign(kp.getPrivate());

// Для самоподписанных сертификатов .issuerDn() опционален —
// библиотека автоматически подставит subjectDn.
// Сертификат — публичный документ, не содержит секретов.
// PEM-представление можно свободно передавать по сети.
String certPem = cert.toPem();

// Двухшаговый вариант (TBS-сборка отдельно, для кросс-валидации):
// byte[] tbs = GostCertificateBuilder.create(params, subjectDn)
//         .publicKey(kp.getPublic())
//         .notBeforeNow().validForDays(365)
//         // или явно: .notBefore("20260101120000Z").notAfter("21060101120000Z")
//         .randomSerial()
//         .buildTbs();
// GostCertificate cert = GostCertificateBuilder.sign(tbs, GostSigner.of(kp.getPrivate()));

// Чтение политик из сертификата:
CertificatePolicy[] infos = cert.getCertificatePolicyInfos();
// infos[0].policyOid() == "1.2.643.100.113.1"
// infos[0].cpsUri()  == "https://ca.example.com/cps/russian-ca.html" (или null)
----

В production загружайте сертификат и ключ из PKCS#12 через `GostPkcs12Loader`
(см. раздел PKCS#12).

=== GostCertificate — загрузка и верификация X.509

Загружаем и проверяем сертификат, созданный в <<Быстрый старт,Быстром старте>>.
`GostCertificate` — минимальный парсер X.509 для ГОСТ Р 34.10-2012:
извлекает открытый ключ, подпись, срок действия, расширения, DN, SAN, AIA, CDP, FreshestCRL.

==== Загрузка из PEM / DER

[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;

// Из PEM (автоопределение формата)
GostCertificate cert = GostCertificate.fromPemOrDer(certPemBytes);

// Из DER
GostCertificate cert = GostCertificate.fromDer(derBytes);

// Чтение цепочки из PEM (несколько блоков подряд)
List<GostCertificate> chain = GostCertificate.listFromPem(chainPemBytes);
----

==== Проверка подписи и срока

[source,java]
----
import org.rssys.gost.signature.PublicKeyParameters;

PublicKeyParameters caPubKey = cert.getPublicKey();
// Для самоподписанного — верифицируем собственным публичным ключом
boolean signatureOk = cert.verifySignature(caPubKey);

boolean expired = cert.isExpired();
boolean validNow = cert.isValidAt(Instant.now());

// Отдельно: notBefore / notAfter
Instant notBefore = cert.getNotBefore();
Instant notAfter  = cert.getNotAfter();
----

==== Проверка атрибутов

[source,java]
----
// Subject / Issuer Distinguished Name
String subject = cert.getSubjectDn();   // "CN=Demo Cert, O=MyOrg, C=RU"
String issuer  = cert.getIssuerDn();

// Самоподписанный?
boolean selfSigned = cert.isSelfSigned();

// CA-атрибуты
boolean isCA = cert.isCA();
int pathLen = cert.getPathLen();

// SERIAL NUMBER
BigInteger serial = cert.getSerialNumberBigInt();

// Algorithm identifier подписи
String sigAlg = cert.getSignatureAlgorithmOid();
----

==== Hostname verification — сверка SAN (Subject Alternative Name)

Поддерживаются все типы GeneralName (RFC 5280 §4.2.1.6): dNSName, iPAddress,
rfc822Name, URI, directoryName, otherName (включая UPN). Hostname-верификация
по RFC 6125 использует только dNSName и iPAddress — остальные типы информационные.

[source,java]
----
// Сверка с DNS-именем из SAN
boolean hostMatch = cert.verifyHostname("gost.example.com");

// Сверка с IP-адресом из SAN
boolean ipMatch = cert.verifyAddress("192.168.1.1");

// Чтение всех типов имён
String[] emails = cert.getSanRfc822Names();     // rfc822Name (email)
String[] uris = cert.getSanUris();               // URI
byte[][] dirNames = cert.getSanDirectoryNames(); // directoryName (raw DER DN)
OtherNameEntry[] otherNames = cert.getSanOtherNames();  // otherName (OID + DER-значение)
----

==== Экспорт

[source,java]
----
String pem = cert.toPem();
byte[] der = cert.getEncoded();

// Экспорт цепочки в PEM
String chainPem = GostCertificate.chainToPem(chain);
----

==== Расширения — bulk-доступ

`getExtensions()` возвращает структурированный результат парсинга всех расширений
X.509v3 одним объектом `GostExtensionParser.ExtensionsResult` — зеркало
`GostCsrParser.getExtensions()`. Позволяет оператору УЦ прочитать расширения
существующего сертификата одним вызовом и осознанно решить, какие переносить
при перевыпуске.

[source,java]
----
if (cert.hasExtensions()) {
    GostExtensionParser.ExtensionsResult ext = cert.getExtensions();

    String[] san = ext.sanDnsNames;          // SubjectAltName dNSName
    String[] ian = ext.ianDnsNames;          // IssuerAltName dNSName
    String[] ocspUris = ext.ocspUris;        // AIA OCSP URI
    int kuBits = ext.keyUsageBits;           // KeyUsage битовая маска
    boolean isCa  = ext.isCA;                // BasicConstraints CA
    int pathLen   = ext.pathLen;             // BasicConstraints pathLen

    // Множество OID всех присутствующих расширений
    Set<String> presentOids = ext.presentExtensionOids;
}
----

=== Подпись через внешний модуль — `GostSigner` (HSM/PKCS#11)

Все X.509-строители (`GostCertificateBuilder`, `GostCrlBuilder`, `GostCsrBuilder`)
принимают абстракцию подписанта `GostSigner` (модуль `crypto-gost-core`, пакет
`org.rssys.gost.api`). Это позволяет подписывать корневым или промежуточным ключом УЦ
внутри аппаратного модуля (HSM, PKCS#11, внешний CSP), не извлекая закрытый ключ в
память JVM — обязательное требование для аккредитованных УЦ.

Строитель вычисляет хэш TBS-структуры и передаёт его в `signHash(hash)`; наружу
возвращается только готовая подпись. Полное описание интерфейса — в README модуля
`crypto-gost-core` (раздел «Абстракция подписанта»).

.Сборка сертификата подписантом (HSM или ключ в памяти)
[source,java]
----
import org.rssys.gost.api.GostSigner;

// Ключ в памяти — тонкий мост GostSigner.of(priv):
GostSigner signer = GostSigner.of(caKey);

// Либо собственная реализация поверх HSM/PKCS#11 (см. crypto-gost-core).
byte[] tbs = GostCertificateBuilder.create(params, subjectDn)
        .publicKey(subjectPub)
        // Удобный способ: .notBeforeNow().validForDays(365)
        .notBefore("20260101120000Z").notAfter("21060101120000Z")
        .issuerDn(issuerDn)
        .randomSerial()
        .buildTbs();
GostCertificate cert = GostCertificateBuilder.sign(tbs, signer);

// CRL и CSR — тот же паттерн:
byte[] crl = GostCrlBuilder.create(issuerDn).nextUpdate("20990101000000Z").sign(signer);
byte[] csr = GostCsrBuilder.create("CN=demo.example.com", subjectPub).sign(signer);
----

Этот же подход работает для CMS SignedData и OCSP — все строители,
работающие с подписью, принимают `GostSigner`. Паттерн один и тот же:
билдер вычисляет хэш, отдаёт в `signHash(hash)`, получает готовую подпись —
закрытый ключ остаётся в аппаратном модуле (HSM/PKCS#11/внешний CSP) и
никогда не попадает в кучу JVM.

.CMS SignedData и OCSP-ответ через GostSigner (HSM-совместимый путь)
[source,java]
----
// CMS SignedData: addSigner(GostSigner, cert) — закрытый ключ не попадает в JVM
byte[] signedData = CmsSignedDataBuilder.create()
        .data(payload)
        .addSigner(signer, cert)    // GostSigner вместо PrivateKeyParameters
        .build();
VerifiedSignedData verified = CmsSignedDataVerifier.verifyAny(signedData, cert);

// OCSP-ответ: sign(GostSigner) — ключ остаётся в HSM, params берутся из signer
byte[] ocsp = GostOcspResponseBuilder.create(serial)
        .issuerDn(issuerDn)
        .good()
        .sign(signer);
OcspVerifier.verify(ocsp, serial, issuerCert);

// Транзитивные строители пробрасывают GostSigner прозрачно:
TspResponseBuilder.create(request).signer(signer, tsaCert).buildGranted();
CountersignatureBuilder.buildCountersignature(parentSig, signer, cert, digestOid);
CAdESExtender.embedCountersignature(cadesDer, signer, cert);
----

Существующие перегрузки, принимающие `PrivateKeyParameters` напрямую, сохранены и
делегируют через `GostSigner.of(priv)` — обратная совместимость полная.

NOTE: После подписи строитель выполняет *fail-closed*-проверку результата (длина +
self-verify открытым ключом подписанта). Неисправный HSM-адаптер, вернувший подпись
неверной длины или не тем ключом, приводит к немедленному исключению, а не к молчаливому
выпуску сертификата или CRL с невалидной подписью.

=== PKCS#12 — хранение ключей и сертификатов

PKCS#12 (PFX) — контейнер, объединяющий закрытый ключ, сертификат и цепочку CA
в одном защищённом паролем файле. Библиотека поддерживает нативную схему
ГОСТ PBE: PBKDF2-HMAC-Streebog + Кузнечик CTR-ACPKM.


NOTE: Закрытый ключ внутри PFX зашифрован на пароле (PBES2).
Пароль — единственный секрет; знающий пароль владеет ключом.
PFX-файл можно передавать по сети — без пароля он бесполезен.

==== Построение PFX — `GostPkcs12Builder`

[source,java]
----
import org.rssys.gost.pkix.cert.GostPkcs12Builder;
import org.rssys.gost.pkix.GostOids;

// PFX можно сохранить в файл и передать по сети.
// Закрытый ключ внутри зашифрован — без пароля расшифровать невозможно.
byte[] pfx = GostPkcs12Builder.create()
        .key(kp.getPrivate())
        .certificate(cert)
        .password("changeit".toCharArray())
        .friendlyName("my-server-cert")
        .build();

// Опционально: настроить число итераций PBKDF2 (по умолчанию 2000)
byte[] pfxCustom = GostPkcs12Builder.create()
        .key(kp.getPrivate())
        .certificate(cert)
        .password("changeit".toCharArray())
        .iterations(50_000)
        .friendlyName("my-server-cert")
        .build();
----

=== CSR (PKCS#10) — запрос сертификата

`GostCsrBuilder` строит PKCS#10 CertificationRequest (RFC 2986 §4.1).
`GostCsrParser` разбирает и верифицирует CSR: извлечение DN, SPKI,
проверка proof-of-possession, расширения extensionRequest.

==== Построение CSR

CSR содержит открытый ключ заявителя, DN и подпись (proof-of-possession).
Атрибутный блок по умолчанию пустой — без расширений.

CSR не содержит закрытого ключа — его можно свободно передавать по сети.
Подпись (proof-of-possession) доказывает владение закрытым ключом,
не раскрывая его.

*Базовый CSR (без расширений)* — fluent API:

[source,java]
----
import org.rssys.gost.pkix.cert.GostCsrBuilder;

ECParameters params = ECParameters.tc26a256();
var kp = KeyGenerator.generateKeyPair(params);

byte[] csrDer = GostCsrBuilder.create(
        "CN=myserver.example.com,O=MyOrg,C=RU", kp.getPublic())
        .sign(kp.getPrivate());
----

*CSR с запрошенными расширениями* — fluent API и атрибут extensionRequest (PKCS#9 §5.4.1):

[source,java]
----
byte[] csrDer = GostCsrBuilder.create("CN=myserver.example.com,O=MyOrg,C=RU", pubKey)
        .sanDns("myserver.example.com", "www.myserver.example.com")   // SubjectAltName
        .sanIp("192.168.1.1")                                         // SAN IP
        .keyUsage(GostCertificateBuilder.KeyUsage.DIGITAL_SIGNATURE)  // KeyUsage
        .extendedKeyUsage(GostOids.EXT_SERVER_AUTH)                   // EKU
        .basicConstraints(false, null)                                 // не CA
        .certificatePolicies(GostOids.POLICY_KC1)                       // CertificatePolicies
        .ski()                                                         // SubjectKeyIdentifier
        .sign(privKey);
----

[CAUTION]
====
`extensionRequest` — *просьба* подписчика, не полномочие.
Оператор УЦ обязан валидировать запрошенные расширения перед копированием
в сертификат: проверка владения доменом для SAN, никогда не выдавать CA=TRUE
по запросу подписчика без процесса выпуска подчинённого УЦ.
====

==== Разбор и верификация CSR

[source,java]
----
import org.rssys.gost.pkix.cert.GostCsrParser;

// Из DER или PEM
GostCsrParser csr = GostCsrParser.fromPemOrDer(csrBytes);

// DN
String dn = csr.getSubjectDn();               // "CN=myserver.example.com, O=MyOrg, C=RU"
String[] cn = csr.getSubjectDnField("2.5.4.3"); // ["myserver.example.com"]

// Публичный ключ и алгоритм
PublicKeyParameters pubKey = csr.getPublicKey();
String sigAlg = csr.getSignatureAlgorithmOid();

// Proof-of-possession
if (csr.verifySelf()) {
    // CSR подписан ключом из SPKI — запрос валиден
}

// Расширения из extensionRequest (если есть)
if (csr.hasExtensions()) {
    var ext = csr.getExtensions();
    String[] san = ext.sanDnsNames;  // запрошенные SAN
}

// Байтово-точный DER subject DN
byte[] subjectDnDer = csr.getSubjectDnDer();  // не теряет тип строки при перекодировке

// PEM-сериализация
String pem = csr.toPem();  // ----BEGIN CERTIFICATE REQUEST-----
----

==== Выпуск сертификата из CSR

`GostCertificateBuilder.fromCsrIdentity` — статическая фабрика, принимает
распарсенный CSR и возвращает предзаполненный билдер: subject DN (байтово-точно
через `getSubjectDnDer()`) и открытый ключ заявителя. Proof-of-possession
проверяется внутри метода — при провале выбрасывается `PkixException`.

Расширения из CSR не копируются автоматически — УЦ обязан явно проверить
и перенести нужные расширения через `csr.getExtensions()`:

[source,java]
----
GostCsrParser csr = GostCsrParser.fromPemOrDer(csrBytes);
ECParameters caParams = ECParameters.tc26a256();  // кривая УЦ

// fromCsrIdentity проверяет proof-of-possession и копирует DN + ключ
GostCertificateBuilder certBuilder = GostCertificateBuilder.fromCsrIdentity(csr, caParams);

// Оператор УЦ явно валидирует расширения из CSR
GostExtensionParser.ExtensionsResult ext = csr.getExtensions();
if (ext.sanDnsNames != null) {
    // УЦ проверил владение доменом — переносим SAN
    certBuilder.sanDns(ext.sanDnsNames);
}
if (ext.ekuOids != null) {
    // УЦ проверил полномочия на EKU — переносим
    // byte[][] -> String[] ручная конвертация или через GostDerParser
}

// УЦ задаёт issuer-поля, срок действия и подписывает
GostCertificate cert = certBuilder
        .issuerDn(caSubjectDnDer)
        // Удобный способ: .notBeforeNow().validForDays(365)
        .notBefore("20250101000000Z")
        .notAfter("20260101000000Z")
        .randomSerial()
        .sign(caSigner);
----

[NOTE]
====
`fromCsrIdentity` — единственный метод в `GostCertificateBuilder`, бросающий
checked-исключение `PkixException` (с `Reason.SIGNATURE_INVALID`),
поскольку выполняет криптографическую верификацию proof-of-possession,
а не строительный шаг билдера. Остальные проверки в классе
(`IllegalStateException`, `IllegalArgumentException`) — unchecked.
====

==== Перевыпуск из существующего сертификата — `fromCertificate`

`GostCertificateBuilder.fromCertificate` — зеркало `fromCsrIdentity` для сценария
перевыпуска (renewal). Копирует subject DN (байтово-точно) и публичный ключ
из существующего сертификата в новый билдер. Расширения не копируются
автоматически — оператор обязан явно прочитать их через `cert.getExtensions()`
и валидировать перед переносом.

[CAUTION]
====
Короткий срок действия сертификатов (≈1 год по CA/Browser Forum) введён для
принудительной периодической переаттестации: проверка владения доменом (SAN),
полномочий на EKU, статуса CA для BasicConstraints. Автоматическое копирование
всех расширений при перевыпуске подрывает эту политику — используйте
`getExtensions()` для осознанного выборочного переноса.
====

[source,java]
----
GostCertificate original = GostCertificate.fromDer(derBytes);
ECParameters caParams = ECParameters.tc26a256();

// Identity-мост: DN и ключ из старого сертификата
GostCertificateBuilder renewedBuilder =
        GostCertificateBuilder.fromCertificate(original, caParams);

// Оператор явно читает и валидирует расширения
GostExtensionParser.ExtensionsResult ext = original.getExtensions();
if (ext.sanDnsNames != null) {
    renewedBuilder.sanDns(ext.sanDnsNames);  // владение доменом перепроверено
}
if (ext.keyUsageBits != 0) {
    if (GostCertificateBuilder.KeyUsage.DIGITAL_SIGNATURE.isSetIn(ext.keyUsageBits)) {
        renewedBuilder.keyUsage(GostCertificateBuilder.KeyUsage.DIGITAL_SIGNATURE);
    }
}
if (ext.isCA) {
    renewedBuilder.basicConstraints(true, ext.pathLen);
}

// Новые сроки, новый serial
GostCertificate renewed = renewedBuilder
        .issuerDn(caSubjectDnDer)
        .notBeforeNow()
        .validForDays(365)
        .randomSerial()
        .sign(caSigner);
----

=== Цепочки сертификатов — ChainValidator

Валидация цепочки доверия по RFC 5280: подписи, DN-связность, CA-флаги,
pathLen, сроки действия. Не содержит TLS-специфики — все ошибки через
`PkixException`.

[source,java]
----
import org.rssys.gost.pkix.cert.ChainValidator;
import org.rssys.gost.signature.PublicKeyParameters;
import java.util.List;

// Цепочка leaf-first: конечный сертификат -> промежуточный CA
// В production цепочка загружается из PKCS#12 или собирается из PEM
List<GostCertificate> chain = List.of(leafCert, intermediateCaCert);

// Доверенный публичный ключ корневого CA
PublicKeyParameters rootKey = rootCaCert.getPublicKey();
List<PublicKeyParameters> trustedKeys = List.of(rootKey);

// Валидация: PkixException если цепочка невалидна
ChainValidator.validateChain(chain, trustedKeys);

// С проверкой CertificatePolicies leaf-сертификата:
// leaf должен содержать POLICY_KC1 или anyPolicy (2.5.29.32.0)
ChainValidator.validateChain(chain, trustedKeys, GostOids.POLICY_KC1);
----

Возможные причины ошибки: `EXPIRED`, `SIGNATURE_INVALID`,
`DN_MISMATCH`, `NOT_CA`, `PATH_LEN_EXCEEDED`, `POLICY_VIOLATION`.

[CAUTION]
.CertificatePolicies — только leaf, не RFC 5280 §6.1
====
Метод `validateChain(…, requiredPolicyOids)` проверяет только leaf-сертификат —
промежуточные CA, `PolicyMappings`, `PolicyConstraints` и `InhibitAnyPolicy`
не обрабатываются. Это намеренно упрощённая проверка, покрывающая
80% практических сценариев («принимать только сертификаты класса КС2»).
Для полной проверки по RFC 5280 §6.1 используйте внешний валидатор с поддержкой
valid_policy_tree, PolicyMappings, PolicyConstraints и InhibitAnyPolicy —
`ChainValidator` эти расширения не обрабатывает.
====

==== Комбинированная проверка: цепочка + отзыв

Метод `validateChainWithRevocation` объединяет PKIX-валидацию цепочки
и проверку статуса отзыва (OCSP/CRL) в одном вызове.
Для каждого сертификата, кроме trust anchor, передаются данные отзыва
через запись `CertRevocationData`. Если для сертификата предоставлен
OCSP-ответ — проверяется OCSP (приоритет по RFC 5280), иначе — CRL.
`null` в `revocationData` означает пропуск проверки для этого сертификата.

[source,java]
----
import org.rssys.gost.pkix.cert.CertRevocationData;
import org.rssys.gost.pkix.cert.ChainValidator;
import java.util.Arrays;

// CRL: leaf не отозван
byte[] crlDer = GostCrlBuilder.create(issuerDn)
        .nextUpdate("270801120000Z")
        .sign(caKey);

ChainValidator.validateChainWithRevocation(
        chain, trustedKeys,
        Arrays.asList(new CertRevocationData(null, crlDer), null));

// OCSP: leaf имеет статус good
byte[] ocspResp = GostOcspResponseBuilder.create(serial)
        .issuerDn(issuerDn)
        .good()
        .sign(caKey);

ChainValidator.validateChainWithRevocation(
        chain, trustedKeys,
        Arrays.asList(new CertRevocationData(ocspResp, null), null));
----

[NOTE]
.Не проверяет delegated signer / delta CRL / nonce
====
Для delegated CRL signer, delegated OCSP responder, delta CRL и nonce-проверки
используйте `CrlVerifier` и `OcspVerifier` напрямую — их полные сигнатуры
принимают дополнительные параметры.
====

=== CRL — списки отзыва сертификатов

Построение и проверка CRL (Certificate Revocation List, RFC 5280 §5).

CRL — публичный документ, распространяемый через CDP (CRL Distribution Point).
Для проверки нужен только открытый ключ CA.

==== Построение CRL — `GostCrlBuilder`

[source,java]
----
import org.rssys.gost.pkix.cert.GostCrlBuilder;
import org.rssys.gost.pkix.cert.RevokedEntry;
import org.rssys.gost.pkix.cert.ReasonCode;
import org.rssys.gost.pkix.cert.GostDnParser;
import org.rssys.gost.signature.PrivateKeyParameters;
import org.rssys.gost.signature.PublicKeyParameters;

byte[] issuerDn = GostDnParser.encodeDn("CN=My CA,O=MyOrg,C=RU");
RevokedEntry entry = new RevokedEntry(
        cert.getSerialNumberBigInt().toByteArray(),
        "260701120000Z",
        ReasonCode.KEY_COMPROMISE,
        null,  // invalidityDate
        null   // certificateIssuer (для indirect CRL)
);

// Строим CRL с одним отозванным сертификатом
byte[] crlDer = GostCrlBuilder.create(issuerDn)
        .withCrlNumber(1)          // монотонный номер CRL (RFC 5280 §5.2.3)
        // Удобный способ: .thisUpdateNow().nextUpdateDays(30) вместо явных дат
        .nextUpdate("270601120000Z")
        .addRevoked(entry)
        .sign(caPrivateKey);

// CRL с IssuingDistributionPoint (флаги onlyContainsUserCerts/onlyContainsCACerts)
byte[] crlWithIdp = GostCrlBuilder.create(issuerDn)
        .withCrlNumber(2)
        .withIdpExtension(true, false)  // onlyContainsUserCerts=true
        .sign(caPrivateKey);

// CRL с AuthorityKeyIdentifier (RFC 5280 §5.2.1) — keyIdentifier подписанта
byte[] caPubPoint = GostDerCodec.subjectPublicKeyPointBytes(caPublicKey);
byte[] caSki = Digest.digest256(caPubPoint);

byte[] crlWithAki = GostCrlBuilder.create(issuerDn)
        .withAki(caSki)               // байты SKI сертификата подписанта
        .sign(caPrivateKey);

// Удобная перегрузка: вычисляет SKI из открытого ключа подписанта
byte[] crlWithAki2 = GostCrlBuilder.create(issuerDn)
        .withAki(signerPublicKey)     // Delegated CRL signer: ключ делегирован, issuer — CA
        .sign(signerPrivateKey);
----

==== Проверка CRL — `CrlVerifier`

[source,java]
----
import org.rssys.gost.pkix.cert.CrlVerifier;
import java.time.Instant;

// PkixException если сертификат отозван или CRL невалиден
CrlVerifier.verify(crlDer,
        cert.getSerialNumberBigInt().toByteArray(),
        caPublicKey,
        cert.getIssuerDnBytes());

// Проверить дату следующего обновления CRL
Instant nextUpdate = CrlVerifier.extractNextUpdate(crlDer);
----

==== Делегированный CRL-подписант — `CrlVerifier.verifyDelegated()`

RFC 5280 §6.3.3 разрешает CA делегировать подпись CRL отдельному ключу.
Для этого CA выпускает сертификат CRL-подписанту с битом `cRLSign` в KeyUsage.
CRL подписывается ключом подписанта (не ключом CA).

Верификатор: проверяет подпись ключом CA, при неудаче — перебирает сертификаты
подписантов. Каждый сертификат подписанта валидируется: срок, `GostCertificate.isCrlSigner()`,
цепочка подписи к CA.

[source,java]
----
import org.rssys.gost.pkix.cert.GostCrlBuilder;
import org.rssys.gost.pkix.cert.CrlVerifier;
import org.rssys.gost.pkix.cert.GostCertificate;

// CA выпускает сертификат CRL-подписанту с cRLSign в KeyUsage
GostCertificate crlSignerCert = new GostCertificate(crlSignerCertDerDer);

// CRL подписывается ключом подписанта (не ключом CA)
byte[] crlDer = GostCrlBuilder.create(caIssuerDn)
        .withCrlNumber(7)
        .nextUpdate("270701120000Z")
        .sign(crlSignerPrivateKey);

// Проверка: передаём список сертификатов подписантов
CrlVerifier.verifyDelegated(
        crlDer,
        cert.getSerialNumberBigInt().toByteArray(),
        caPublicKey,                     // открытый ключ CA (fast path)
        cert.getIssuerDnBytes(),
        caCert,                          // сертификат CA (defence-in-depth: LOG warning без cRLSign)
        List.of(crlSignerCertDerDer));   // сертификаты CRL-подписантов

// Проверка с защитой от CRL rollback (cRLNumber монотонность)
CrlVerifier.verifyDelegated(
        crlDer,
        cert.getSerialNumberBigInt().toByteArray(),
        caPublicKey,
        cert.getIssuerDnBytes(),
        caCert,
        List.of(crlSignerCertDerDer),
        BigInteger.valueOf(6));          // minCrlNumber
----

Сертификат подписанта должен иметь бит `cRLSign` в KeyUsage (`GostCertificate.isCrlSigner()`).
Если KeyUsage отсутствует — ограничений нет. Проверка `cRLSign` у CA в прямом пути —
defence-in-depth (LOG warning, не reject).

==== Delta CRL — частичные списки отзыва (RFC 5280 §5.2.4)

Delta CRL содержит только изменения относительно базового CRL. При проверке
верификатор склеивает оба списка: запись в delta перекрывает запись в base.
Если delta удаляет сертификат (reasonCode = `REMOVE_FROM_CRL`) — он больше не считается отозванным.

[source,java]
----
import org.rssys.gost.pkix.cert.CrlVerifier;

// 1. Базовый CRL (полный список отозванных)
byte[] baseCrl = GostCrlBuilder.create(issuerDn)
        .withCrlNumber(1)
        .nextUpdate("270601120000Z")
        .addRevoked(entry)
        .sign(caPrivateKey);

// 2. Delta CRL — только изменения. Ссылается на cRLNumber базового.
//    deltaCRLIndicator — CRITICAL-расширение, требуемое по RFC 5280.
byte[] deltaCrl = GostCrlBuilder.create(issuerDn)
        .withCrlNumber(2)
        .withDeltaCrlIndicator(1)   // ссылается на base cRLNumber = 1
        .addRevoked(removedSerial, "260801120000Z",
                ReasonCode.REMOVE_FROM_CRL)  // удалить из base
        .sign(caPrivateKey);

// 3. Проверка через base + delta
//    crlNumber base и deltaCRLIndicator delta должны совпадать.
//    thisUpdate delta должен быть >= thisUpdate base.
CrlVerifier.verify(baseCrl, deltaCrl,
        cert.getSerialNumberBigInt().toByteArray(), caPublicKey);

// 4. Base CRL может указывать URI для получения delta CRL
//    через расширение freshestCRL (структура = CDP, RFC 5280 §5.2.6)
byte[] baseWithFreshest = GostCrlBuilder.create(issuerDn)
        .withCrlNumber(3)
        .withFreshestCrl("http://ca.example/delta.crl")
        .nextUpdate("270601120000Z")
        .sign(caPrivateKey);
----

Delta CRL нельзя верифицировать изолированно. При попытке `crl.verify(caKey)` на delta CRL
верификатор бросает `PkixException` с сообщением «delta CRL not supported»,
требуя использования `CrlVerifier.verify(base, delta, ...)`.

==== Разбор CRL — `GostCrl`

`GostCrl` — парсинг CRL отдельно от верификации. Позволяет прочитать структуру
(issuer, даты, отозванные сертификаты) без проверки подписи.
Полная верификация — через `CrlVerifier.verify()` или `crl.verify(caKey)`.

[source,java]
----
import org.rssys.gost.pkix.cert.GostCrl;
import org.rssys.gost.pkix.cert.RevokedEntry;
import java.time.Instant;

GostCrl crl = GostCrl.fromDer(crlDer);

// Метаданные CRL
String issuer = crl.getIssuerDn();           // "CN=My CA, O=MyOrg, C=RU"
Instant thisUpdate = crl.getThisUpdate();
Instant nextUpdate = crl.getNextUpdate();    // может быть null

// Верификация подписи + парсинг revoked-списка (порядок обязателен)
crl.verify(caPublicKey);                     // бросит PkixException при невалидной подписи

// Проверка отзыва конкретного сертификата
if (crl.isRevoked(cert.getSerialNumber())) {
    System.err.println("Сертификат отозван");
}

// Список всех отозванных — с причиной (если есть)
for (RevokedEntry e : crl.getRevokedCertificates()) {
    System.out.println("Отозван: " + e.revocationDate() + " причина: " + e.reason());
}

// CRL-расширения (доступны после verify)
BigInteger crlNum = crl.getCrlNumber();        // cRLNumber из расширения
ReasonCode code = crl.getReason(cert.getSerialNumber());        // причина отзыва конкретного сертификата
boolean isDelta = crl.isDelta();                // true если CRL — delta

// FreshestCRL (2.5.29.46) — URI для получения delta CRL
boolean hasFreshest = crl.isFreshestCrl();      // true если расширение присутствует
String[] deltaUris = crl.getFreshestCrlUris();  // URI точек распространения delta CRL

// AuthorityKeyIdentifier (2.5.29.35) — идентификатор ключа подписанта CRL
byte[] akiBytes = crl.getAuthorityKeyIdentifier(); // null если расширения нет

// IssuingDistributionPoint (2.5.29.28) — парсится при verify
boolean hasIdp = crl.isIdp();                   // true если IDP присутствует
boolean onlyUser = crl.isOnlyContainsUserCerts(); // флаг IDP
boolean onlyCa = crl.isOnlyContainsCACerts();     // флаг IDP
boolean indirect = crl.isIndirectCrl();           // true -> reject (вне scope)

// Экспорт в PEM
String crlPem = crl.toPem();
----

`GostCrl` поддерживает автоопределение формата через `fromPemOrDer()` — метод
принимает PEM или DER и возвращает распарсенный CRL, аналогично `GostCertificate.fromPemOrDer()`.

По умолчанию CRL ограничен `DEFAULT_MAX_CRL_SIZE` = 64 МБ и
`DEFAULT_MAX_REVOKED_ENTRIES` = 1 000 000 отозванных записей.
Для крупных CRL национальных УЦ доступны перегрузки `GostCrl(byte[], int, int)`,
`fromDer(byte[], int, int)` и `fromPemOrDer(byte[], int, int)` с настраиваемыми
лимитами. Аналогичные лимиты есть у `CrlVerifier.verify()`.

=== OCSP — онлайн-проверка статуса сертификата

Online Certificate Status Protocol (RFC 6960) — альтернатива CRL для проверки
отзыва в реальном времени.


OCSP-ответ — публичный документ, подписанный CA. Для проверки нужен
сертификат CA (OcspVerifier автоматически вычисляет CertID по issuer и проверяет
EKU OCSP-подписанта). Допустима передача по незащищённому каналу.

==== Выпуск сертификата делегированного OCSP-респондера — `.ocspNoCheck()`

Если OCSP-ответы подписывает не сам CA, а отдельный делегированный респондер,
его сертификат должен нести EKU `id-kp-OCSPSigning` и расширение
`id-pkix-ocsp-nocheck` (RFC 6960 §4.2.2.2.1). Последнее сообщает проверяющей
стороне не проверять рекурсивно отзыв самого сертификата респондера — иначе
возникла бы циклическая зависимость (для проверки OCSP-ответа понадобился бы
ещё один OCSP-запрос про подписанта).

[source,java]
----
GostCertificate responder = GostCertificateBuilder.create(params, "CN=OCSP Responder,O=MyOrg,C=RU")
        .publicKey(responderPublicKey)
        .issuerDn(caSubjectDer)
        .notBefore("20250101000000Z")
        .notAfter("20250103000000Z")                       // короткий срок жизни
        .extendedKeyUsage(GostOids.EXT_OCSP_SIGNING)        // обязательно
        .ocspNoCheck()                                      // id-pkix-ocsp-nocheck
        .randomSerial()
        .sign(caPrivateKey);

boolean marked = responder.hasOcspNoCheck();               // true
----

WARNING: Сертификат с `id-pkix-ocsp-nocheck` фактически невозможно эффективно
отозвать (клиенты по определению не проверяют его отзыв), поэтому его выдают
только короткоживущим (сутки-двое). Расширение допустимо лишь вместе с EKU
`id-kp-OCSPSigning` — иначе `buildTbs()`/`sign()` бросает
`IllegalStateException` (защита от постановки на обычный сертификат).

==== Построение OCSP-ответа — `GostOcspResponseBuilder`

[source,java]
----
import org.rssys.gost.pkix.cert.GostOcspResponseBuilder;
import org.rssys.gost.pkix.cert.GostDnParser;

byte[] caSubjectDer = GostDnParser.encodeDn("CN=My CA,O=MyOrg,C=RU");
byte[] ocspResp = GostOcspResponseBuilder.create(cert.getSerialNumberBigInt().toByteArray())
        .issuerDn(caSubjectDer)
        .good()
        .sign(caPrivateKey);

// nextUpdate по умолчанию — now + 3 года.
// noNextUpdate() убирает поле (RFC 6960 §2.4 — опционально).
// В этом случае relying party применяет локальную политику свежести
// через maxOcspAgeMs в OcspVerifier.
byte[] noNuOcsp = GostOcspResponseBuilder.create(cert.getSerialNumberBigInt().toByteArray())
        .issuerDn(caSubjectDer)
        .good()
        .noNextUpdate()
        .sign(caPrivateKey);

// byKey responder ID — хэш Streebog-256 от публичного ключа подписанта.
// Рекомендовано RFC 5019bis для высоконагруженных сред; компактнее byName.
// Распознаётся только ГОСТ-клиентами; для универсальной совместимости — byName.
byte[] byKeyOcsp = GostOcspResponseBuilder.create(cert.getSerialNumberBigInt().toByteArray())
        .issuerDn(caSubjectDer)
        .withResponderByKey()
        .good()
        .sign(caPrivateKey);

// byKey со Streebog-512 — для 512-битных кривых
byte[] byKey512Ocsp = GostOcspResponseBuilder.create(cert.getSerialNumberBigInt().toByteArray())
        .issuerDn(ca512SubjectDer)
        .withResponderByKey(GostOids.STREEBOG_512_HASH_LEN)
        .good()
        .sign(ca512PrivateKey);
----

==== Проверка OCSP-ответа — `OcspVerifier`

[source,java]
----
import org.rssys.gost.pkix.cert.OcspVerifier;

// PkixException если сертификат отозван или ответ невалиден
// CertID (issuerNameHash/issuerKeyHash) вычисляется из caCert автоматически
OcspVerifier.verify(ocspResp,
        cert.getSerialNumberBigInt().toByteArray(),
        caCert);

// Для ответов без nextUpdate — настраиваемая политика свежести:
// OcspVerifier.verify(ocspResp, cert.getSerialNumberBigInt().toByteArray(),
//         caCert, expectedNonce, maxOcspAgeMs);
----

NOTE: Есть аддитивные перегрузки с раздельными ролями RFC 6960 —
`verify(..., certIdIssuer, responderAuthority, ...)`. В обычной конфигурации оба
параметра — один и тот же сертификат CA (как в перегрузках с одним `caCert`).
Разделение нужно лишь для редких легитимных сценариев (например, плановая смена
ключа CA с действующим кросс-сертификатом): `certIdIssuer` — источник CertID-хэшей
истинного издателя листа, `responderAuthority` — authority подписи ответа. Authority
обязан криптографически цепляться к истинному издателю; совпадение лишь Subject DN
доверия не создаёт (иначе — fail-closed отказ).

==== Разбор OCSP-ответа — `GostOcspResponse`

`GostOcspResponse` — доменный объект для разбора OCSP-ответа без ключа CA.
Позволяет извлечь статус, даты, серийные номера и делегированные сертификаты.

[source,java]
----
import org.rssys.gost.pkix.cert.GostOcspResponse;
import org.rssys.gost.pkix.cert.SingleOcspResponse;
import java.time.Instant;
import java.util.List;

GostOcspResponse ocsp = GostOcspResponse.fromDer(ocspResp);

// Статус ответа (0 = успех)
boolean ok = ocsp.isSuccessful();

// Все ответы по сертификатам
for (SingleOcspResponse sr : ocsp.getResponses()) {
    if (sr.isGood()) {
        Instant thisUpdate = sr.thisUpdate();
        Instant nextUpdate = sr.nextUpdate();  // может быть null
    }
}

// Делегированные сертификаты responder'а (RFC 6960 §4.2.2.2)
List<byte[]> delegated = ocsp.getDelegatedCertificates();

// Тип responder ID (byName или byKey)
GostOcspResponse.ResponderIdType ridType = ocsp.getResponderIdType();
if (ridType == GostOcspResponse.ResponderIdType.BY_KEY) {
    byte[] keyHash = ocsp.getResponderKeyHash();
    // keyHash — Streebog-хэш SPKI, сопоставляется с сертификатом подписанта
}

// Проверка подписи
ocsp.verify(caPublicKey);
boolean verified = ocsp.isSignatureVerified();
----

==== Построение OCSP-запроса — `GostOcspRequestBuilder`

`GostOcspRequestBuilder` строит OCSPRequest (RFC 6960 §4.1) с автоматическим nonce (RFC 8954)
и опциональной подписью запроса (RFC 9215).

[source,java]
----
import org.rssys.gost.pkix.cert.GostOcspRequestBuilder;
import org.rssys.gost.pkix.GostOids;

// Базовый запрос: один сертификат
GostOcspRequestBuilder builder = GostOcspRequestBuilder.create()
        .targetCert(cert.getEncoded())
        .issuerCert(caCert.getEncoded());

byte[] requestDer = builder.build();
byte[] nonce = builder.getNonce();       // автоматически сгенерирован

// Multi-cert: запрос статуса нескольких сертификатов
byte[] multiDer = GostOcspRequestBuilder.create()
        .targetCert(cert1.getEncoded()).issuerCert(caCert.getEncoded())
        .addRequest(cert2.getEncoded(), caCert.getEncoded())
        .hashLen(GostOids.STREEBOG_512_HASH_LEN)
        .build();

// С подписью запроса (RFC 9215 §4.2)
byte[] signedDer = GostOcspRequestBuilder.create()
        .targetCert(cert.getEncoded())
        .issuerCert(caCert.getEncoded())
        .signKey(requestorPriv)
        .params(ecParams)
        .build();
----

==== Разбор OCSP-запроса — `GostOcspRequest`

`GostOcspRequest` разбирает полученный OCSPRequest в структурированный объект.

[source,java]
----
import org.rssys.gost.pkix.cert.GostOcspRequest;
import org.rssys.gost.pkix.cert.CertId;

GostOcspRequest request = GostOcspRequest.fromDer(requestDer);

// Список сертификатов из запроса
for (CertId cid : request.getCertIds()) {
    byte[] sn = cid.serialNumber();           // серийный номер
    byte[] nameHash = cid.issuerNameHash();   // хэш имени издателя
    byte[] keyHash = cid.issuerKeyHash();     // хэш ключа издателя
}

// Nonce (RFC 8954)
byte[] nonce = request.getNonce();

// Проверка подписи запроса (RFC 9215)
if (request.isSigned()) {
    request.verifySignature(requestorPubKey);
    boolean ok = request.isSignatureVerified();
}
----

=== CMS SignedData — подпись и верификация

`CmsSignedDataBuilder` формирует SignedData DER-байты по RFC 5652 §5 с ГОСТ-подписью.
Без параметров подпись инкапсулированная — данные включаются внутрь CMS-сообщения.


Подпись не раскрывает закрытый ключ. Результат `build()` — DER-байты,
которые можно свободно передавать по сети или хранить в файле.
Верификатору нужен только открытый ключ (из сертификата подписанта).

==== Подпись с инкапсулированными данными

[source,java]
----
import org.rssys.gost.pkix.cms.CmsSignedDataBuilder;
import org.rssys.gost.pkix.cms.CmsSignedDataVerifier;

byte[] data = "Документ для подписи".getBytes(StandardCharsets.UTF_8);

// Подпись
byte[] signedData = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(privateKey, cert)
        .build();

// Верификация
VerifiedSignedData result =
        CmsSignedDataVerifier.verifyAny(signedData, cert);

byte[] extracted = result.data(); // == data
GostCertificate signer = result.signerCertificate();
----

NOTE: `verifyAny()` возвращает первого валидного подписанта (OR-семантика). Если нужна
гарантия, что *все* подписанты прошли проверку, используйте `verifyAll()` — он
вернёт `MultiSignerVerifiedData` со списком всех подписантов, либо бросит `PkixException`
с указанием, какой именно подписант не прошёл верификацию.

==== Detached подпись

Данные не включаются в CMS — подпись и документ хранятся отдельно.
Верификатор не извлекает данные — приложение проверяет их самостоятельно.
Подпись можно передавать открыто, данные — по необходимости.

[source,java]
----
byte[] data = "Внешний документ".getBytes(StandardCharsets.UTF_8);

// detached: данные не упаковываются в CMS
byte[] signedData = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(privateKey, cert)
        .detached(true)
        .build();

// Верификация
VerifiedSignedData result =
        CmsSignedDataVerifier.verifyAny(signedData, cert);

assert result.data() == null; // detached — данных в CMS нет
----

==== Дополнительные сертификаты в цепочке

Промежуточные CA-сертификаты добавляются через `addCertificate()`.
Верификатор найдёт сертификат подписанта среди встроенных.

[source,java]
----
byte[] signedData = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(leafKey, leafCert)
        .addCertificate(intermediateCaCert)   // промежуточный CA
        .addCertificate(rootCaCert)           // корневой CA (опционально)
        .build();

VerifiedSignedData result =
        CmsSignedDataVerifier.verifyAny(signedData, rootCaCert);
----

==== Встраивание CRL в подпись

CRL (списки отзыва сертификатов, RFC 5280 §5) можно встроить в SignedData
через `addCrl()` — получатель проверяет статус отзыва офлайн, без
обращения к CDP. CRL попадают в поле `crls [1]` (RFC 5652 §5.1)
и возвращаются в результате верификации.

[source,java]
----
import org.rssys.gost.pkix.cert.GostCrl;
import org.rssys.gost.pkix.cert.GostCrlBuilder;

GostCrl crl = GostCrl.fromDer(crlDer);

byte[] signedData = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(privateKey, cert)
        .addCertificate(intermediateCaCert)
        .addCrl(crl)                          // <1>
        .build();

// CRL возвращается в результате верификации
VerifiedSignedData result =
        CmsSignedDataVerifier.verifyAny(signedData, cert);
List<GostCrl> embeddedCrls = result.embeddedCrls(); // <2>
----
<1> CRL должны быть в DER-кодировке (`GostCrl.fromDer()` или результат `GostCrlBuilder.sign()`).
    Верификатор проверяет размер поля и число CRL (защита от DoS: лимиты
    `MAX_EMBEDDED_CRLS_TOTAL_SIZE` и `MAX_EMBEDDED_CRLS` в `CmsConstants`).
    Поддерживается только выбор `crl` из `RevocationInfoChoice` (RFC 5652 §10.2.1),
    OCSP-ответы (`other`) не поддерживаются.
<2> `embeddedCrls()` возвращает CRL только после структурного разбора DER.
    Для проверки отзыва конкретного сертификата нужен отдельный вызов
    `crl.verify(caPublicKey)` + `crl.isRevoked(certSerial)`
    (либо используйте `verifyAnyWithRevocationCheck` — автоматически).

Для certs-only контейнеров (`.p7b`) CRL добавляются через перегрузку
`GostPkcs7.buildCertsOnly`:

[source,java]
----
byte[] p7b = GostPkcs7.buildCertsOnly(
        List.of(crl), cert1, cert2, intermediateCaCert);

// extractCertificates() не ломается при наличии crls [1]
List<GostCertificate> certs = GostPkcs7.extractCertificates(p7b);
----

==== Автоматическая проверка отзыва — `verifyAnyWithRevocationCheck`

Методы `verifyAnyWithRevocationCheck` и `verifyAllWithRevocationCheck`
автоматически проверяют статус отзыва каждого сертификата цепочки по embedded CRL
из SignedData и опционально по внешним CRL. Используют `CrlVerifier`
(проверка подписи CRL, срока, issuer DN и статуса отзыва).

[source,java]
----
import org.rssys.gost.pkix.cert.GostCrl;
import org.rssys.gost.pkix.cms.CmsSignedDataVerifier;

// CRL встроен в CMS SignedData: проверка автоматическая
VerifiedSignedData result1 =
    CmsSignedDataVerifier.verifyAnyWithRevocationCheck(signedData, trustedCaCert);

// Внешний CRL (например, из кэша): передаётся параметром
List<GostCrl> externalCrls = List.of(crlFromCache);
VerifiedSignedData result2 =
    CmsSignedDataVerifier.verifyAnyWithRevocationCheck(
        signedData, externalCrls, trustedCaCert);

// AND-семантика: каждый подписант проверяется на отзыв
MultiSignerVerifiedData all =
    CmsSignedDataVerifier.verifyAllWithRevocationCheck(
        signedData, trustedCaCert, trustedCaCert2);
----

Стратегия проверки:

* Для каждого сертификата цепочки (кроме trust anchor) ищется CRL
  с совпадающим issuer DN — сначала в embedded, затем во внешних.
* CRL найден и валиден, сертификат не в revoked-списке — ок.
* CRL найден, но невалиден (просрочен, битая подпись) — `PkixException` fail-closed.
* Сертификат в revoked-списке — `PkixException` с `Reason.REVOKED`.
* CRL не найден — best-effort пропуск (warn в лог).
* Delta CRL (и partial/indirect) пропускаются, верификатор ищет следующий подходящий CRL.
* `trustedCerts` обязан быть непустым — иначе `IllegalArgumentException`.

Базовые методы `verifyAny` и `verifyAll` сохраняют обратную совместимость —
без проверки отзыва.

==== Извлечение сертификатов из .p7b — `GostPkcs7`

Формат `.p7b` (PKCS#7/CMS SignedData, у которого заполнено поле `certificates`,
а подписантов обычно нет) — распространённый способ обмена сертификатами и их
цепочками. `GostPkcs7.extractCertificates()` разбирает контейнер и
возвращает список `GostCertificate`. Это обратная операция к `addCertificate()`.

[source,java]
----
import org.rssys.gost.pkix.cms.GostPkcs7;
import org.rssys.gost.pkix.cert.GostCertificate;

// Автоопределение DER/PEM (-----BEGIN PKCS7-----) по первому байту
byte[] p7b = Files.readAllBytes(Path.of("chain.p7b"));
List<GostCertificate> certs = GostPkcs7.extractCertificates(p7b);

// Перегрузка с явным потолком числа сертификатов (по умолчанию MAX_P7B_CERTS = 256)
List<GostCertificate> limited = GostPkcs7.extractCertificates(p7b, 16);
----

CAUTION: `extractCertificates()` выполняет только разбор DER — без проверки подписи,
цепочки, срока действия и отзыва. Извлечённые сертификаты нужно проверять отдельно
(`ChainValidator`, `CrlVerifier`, `OcspVerifier`). Потолки `MAX_P7B_CERTS` и
`MAX_P7B_SIZE` (10 МиБ) защищают от DoS на подготовленном входе.

==== Формирование certs-only .p7b — `GostPkcs7.buildCertsOnly`

Обратная операция к `extractCertificates`: собирает `.p7b` (SignedData без
подписантов, только сертификаты) для обмена цепочками.

[source,java]
----
import org.rssys.gost.pkix.cms.GostPkcs7;

byte[] p7b = GostPkcs7.buildCertsOnly(leafCert, intermediateCaCert, rootCaCert);
Files.write(Path.of("chain.p7b"), p7b);

// round-trip: обратно извлекаются те же сертификаты
List<GostCertificate> back = GostPkcs7.extractCertificates(p7b);
----

Эквивалентно `CmsSignedDataBuilder.create().certsOnly().addCertificate(...).build()`.

NOTE: порядок сертификатов в контейнере не сохраняется — поле `certificates` есть
`SET OF` и кодируется в DER лексикографически отсортированным (X.690 §11.6).

==== Человекочитаемый вывод сертификата и .p7b

`CertificateTextFormatter.format(GostCertificate)` формирует подробный многострочный
отчёт по одному сертификату: полный DN, сроки, алгоритм ключа, расшифровка всех
расширений (KeyUsage, EKU, SAN, AIA, CDP, BasicConstraints, NameConstraints и др.)
на русском языке.

`GostPkcs7.formatText(byte[])` выводит отчёт по контейнеру `.p7b` целиком:
заголовок с числом сертификатов и CRL, детальный дамп каждого сертификата
(через `CertificateTextFormatter`) и метаданные встроенных CRL (issuer, thisUpdate,
nextUpdate). CRL-данные об отозванных сертификатах доступны только после
криптографической проверки — первая строка вывода явно предупреждает об этом.

В отличие от компактного, безопасного для журналов `toString()` (DN усечён до 256,
OCSP исключён), этот вывод предназначен для показа человеку на экране.

[source,java]
----
import org.rssys.gost.pkix.cert.CertificateTextFormatter;
import org.rssys.gost.pkix.cms.GostPkcs7;

// по одному сертификату
System.out.println(CertificateTextFormatter.format(cert));

// дамп .p7b-контейнера (автоопределение DER/PEM)
System.out.println(GostPkcs7.formatText(p7bDer));
----

==== Пользовательские signed-атрибуты

К стандартным атрибутам (contentType, messageDigest) можно добавить свои —

=== CAdES — долговременная электронная подпись

==== Что такое CAdES и TSP

*CAdES* (CMS Advanced Electronic Signatures, ETSI EN 319 122) — стандарт долговременной
электронной подписи. Расширяет CMS SignedData стандартными signed- и unsigned-атрибутами,
позволяющими проверять подпись спустя годы после истечения сертификата.

*Проблема.* ГОСТ-сертификат выпускается на 12–15 месяцев. Если подпись проверяют
после истечения срока сертификата, формально она «повисает» — невозможно установить
момент подписания. ФЗ-63 ст.11 требует достоверно установленного момента создания подписи.

*Решение.* CAdES-T (уровень T — Timestamp) добавляет метку времени от доверенного
центра TSA (Time-Stamp Authority по RFC 3161) в unsigned-атрибуты SignerInfo.
Метка криптографически доказывает, что подпись существовала на момент `genTime` —
сертификат подписанта проверяется относительно этого момента, а не текущего.

*Уровни CAdES:*

- *CAdES-BES* — базовая подпись: SignedData + `signingCertificateV2` (связка подписи с сертификатом).
- *CAdES-T* — BES + метка времени `signature-time-stamp` в unsigned-атрибутах.
- *CAdES-C* — BES/T + `complete-certificate-references` и `complete-revocation-references` — ссылки на все сертификаты и данные отзыва, необходимые для полной проверки (см. раздел CAdES-C ниже).

==== CAdES-BES — базовая электронная подпись

CAdES-BES добавляет signed-атрибут `signingCertificateV2` (ESS, RFC 5035 §3),
который содержит хэш DER-кодирования сертификата подписанта и его IssuerSerial.
Это надёжно связывает подпись с конкретным сертификатом.

Создать CAdES-BES — вызвать `.withCAdES()` на построителе SignedData.
Атрибут `signingCertificateV2` добавляется автоматически, для каждого подписанта.
Подпись остаётся инкапсулированной (данные внутри) или detached — как обычно.
Результат `.build()` — обычный CMS SignedData DER, без метки времени.
Его можно свободно передавать по сети.

.Создание CAdES-BES
[source,java]
----
import org.rssys.gost.pkix.cms.CmsSignedDataBuilder;
import org.rssys.gost.pkix.cms.CmsSignedDataVerifier;
import org.rssys.gost.pkix.cms.VerifiedSignedData;

byte[] data = "Документ для долговременной подписи".getBytes(StandardCharsets.UTF_8);

// Создание CAdES-BES — signingCertificateV2 добавляется автоматически
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(privateKey, cert)
        .withCAdES()                        // <1>
        .build();

// Верификация CAdES-BES — стандартная CMS-проверка
VerifiedSignedData result =
        CmsSignedDataVerifier.verifyAny(cadesBes, cert);

byte[] originalData = result.data();
GostCertificate signer = result.signerCertificate();
----
<1> Автоматически добавляет `signingCertificateV2` для каждого подписанта в signedAttrs.
Хэш вычисляется от DER сертификата: Стрибог-256 для 256-битных ключей,
Стрибог-512 для 512-битных.

NOTE: Для полной верификации CAdES-BES (включая `signingCertificateV2`)
используйте `CAdESExtender.verifyCAdESBES()`. Для CAdES-T с метками —
`CAdESExtender.verifyCAdEST()`. Эти методы проверяют все подписанты
(AND-семантика) и `signingCertificateV2` (fail-closed).

==== TSP-клиент — запрос меток времени

Протокол TSP (Time-Stamp Protocol, RFC 3161) — стандарт IETF для получения
криптографических меток времени от службы TSA.

*Принцип работы:*

. Приложение вычисляет хэш данных (signature подписанта) и отправляет `TimeStampReq`.
. TSA подписывает `TimeStampToken` (CMS SignedData с `TSTInfo` внутри) и возвращает `TimeStampResp`.
. Приложение проверяет подпись TSA и совпадение хэша — метка действительна.

NOTE: TSP-ответ — публичный документ. Его можно проверить с открытым ключом TSA.
Передача по незащищённому каналу допустима.

===== Построение TimeStampReq

[source,java]
----
import org.rssys.gost.pkix.tsp.TspRequestBuilder;
import org.rssys.gost.pkix.GostOids;
import org.rssys.gost.api.Digest;

byte[] data = "данные для метки".getBytes(StandardCharsets.UTF_8);
byte[] hash = Digest.digest256(data);       // Стрибог-256

// Строим запрос: обязательно messageImprint, + nonce (автоматически), + запрос сертификата TSA
byte[] tspReq = TspRequestBuilder.create()
        .messageImprint(hash, GostOids.DIGEST_256) // <1>
        .certReq(true)                             // <2>
        .build();                                  // <3>
----
<1> `messageImprint` — хэш данных, для которых запрашивается штамп. Для CAdES-T
это хэш подписи (см. раздел CAdES-T).
<2> `certReq(true)` — TSA пришлёт сертификат в ответе.
<3> `build()` автоматически генерирует `nonce` (8 байт, `CryptoRandom`) если не задан явно.

===== Отправка запроса и разбор ответа

[source,java]
----
import org.rssys.gost.pkix.tsp.JdkHttpTspTransport;
import org.rssys.gost.pkix.tsp.TspResponse;
import org.rssys.gost.pkix.tsp.TspTransport;

// Дефолтный HTTP-транспорт (JVM). Для Android — UrlConnectionTspTransport
TspTransport transport = new JdkHttpTspTransport();

// Отправляем запрос на TSA
byte[] tspRespDer = transport.send(tspReq, "http://tsa.example.com/tsa");

// Разбираем ответ
TspResponse tspResponse = TspResponse.fromDer(tspRespDer);

// Проверяем статус
if (tspResponse.status() != GostOids.PKI_STATUS_GRANTED) {
    throw new SecurityException("TSA rejected request: " + tspResponse.statusString());
}

// Верифицируем: хэш, алгоритм, время, nonce, подпись TSA, цепочку
tspResponse.verify(hash, GostOids.DIGEST_256, null, tsaTrustedCert);

// Извлекаем информацию о штампе
System.out.println("GenTime: " + tspResponse.tstInfo().genTime());        // YYYYMMDDHHMMSSZ
System.out.println("Serial: " + tspResponse.tstInfo().serialNumber());   // BigInteger
----

TIP: Для Android-приложений используйте `UrlConnectionTspTransport` из того же пакета
(`org.rssys.gost.pkix.tsp`). Он использует `HttpURLConnection` (доступен с API level 1)
вместо `java.net.http.HttpClient` и не требует десугаринга.

`TspResponse.verify()` проверяет:
. `messageImprint` — совпадает ли хэш в ответе с ожидаемым (constant-time через `MessageDigest.isEqual`).
. `genTime` — не в будущем (с допуском ±5 минут).
. nonce — если передан в запросе, должен совпадать.
. *Подпись TSA* на TimeStampToken (CMS SignedData).
. *Цепочку сертификатов TSA* через `ChainValidator`.

NOTE: Для кастомного HTTP-клиента (прокси, mTLS) реализуйте интерфейс `TspTransport`
самостоятельно и передайте в методы `CAdESExtender` или ваш код.

===== Кастомный HTTP-транспорт

По умолчанию используется `JdkHttpTspTransport` (JVM, `HttpClient`)
или `UrlConnectionTspTransport` (Android, `HttpURLConnection`).
Если требуется прокси, аутентификация mTLS или другой HTTP-клиент —
реализуйте интерфейс `TspTransport`:

[source,java]
----
import org.rssys.gost.pkix.tsp.TspTransport;

TspTransport myTransport = (requestDer, url) -> {
    // ваш HTTP POST на url, Content-Type: application/timestamp-query
    // вернуть тело ответа как byte[]
    return responseBody;
};
----

===== Построение TSP-ответа — `TspResponseBuilder`

Генерация штампов на стороне TSA: разбор входящего запроса, проверка
алгоритма, построение TimeStampResp, отклонение с сообщением.

[source,java]
----
import org.rssys.gost.pkix.tsp.TspRequest;
import org.rssys.gost.pkix.tsp.TspResponseBuilder;
import org.rssys.gost.pkix.GostOids;
import java.math.BigInteger;

byte[] requestDer = ...;  // тело HTTP POST от клиента

// 1. Разбираем запрос
TspRequest request = TspRequest.fromDer(requestDer);

// 2. Проверяем алгоритм хэширования
if (!GostOids.DIGEST_256.equals(request.messageImprintAlgOid())) {
    byte[] rejection = TspResponseBuilder.buildRejected(
            "Unsupported hash algorithm");
    // ... отправляем rejection обратно ...
    return;
}

// 3. Строим granted-ответ
byte[] responseDer = TspResponseBuilder.create(request)
        .signer(tsaPrivateKey, tsaCertificate)
        .policyOid("1.3.6.1.4.1.4146.1.2.1")           // <1>
        .serialNumber(BigInteger.valueOf(counter.getAndIncrement())) // <2>
        .accuracy(1, 500)                                // <3>
        .buildGranted();

// 4. Отправляем DER-байты клиенту
//    Content-Type: application/timestamp-reply
----
<1> `policyOid` — OID политики TSA, идентифицирует службу. Обязателен.
<2> `serialNumber` — серийный номер штампа, обязан быть глобально уникальным
    (RFC 3161 §2.4.2). Вызывающий обеспечивает уникальность сам (AtomicLong, БД).
    Обязателен.
<3> `accuracy` — точность часов TSA: 1 секунда ± 500 миллисекунд. Опционально.

Алгоритм хэширования определяется автоматически по размеру ключа TSA:
256-битный -> Streebog-256, 512-битный -> Streebog-512.

===== Отклонение, grantedWithMods и расширенные атрибуты

[source,java]
----
// Отклонение — без подписи, только PKIStatusInfo
byte[] rejectionDer = TspResponseBuilder.buildRejected("Unknown policy OID");

// Без сообщения, с кодом причины (RFC 4210 §D.2)
byte[] noMsgRej = TspResponseBuilder.buildRejected(GostOids.PKI_FAIL_BAD_ALG);

// С сообщением и кодом причины
byte[] rej = TspResponseBuilder.buildRejected("System error",
        GostOids.PKI_FAIL_SYSTEM_FAILURE);

// grantedWithMods (PKIStatus=1) — статус «с модификациями»
byte[] withModsDer = TspResponseBuilder.create(request)
        .signer(tsaPrivateKey, tsaCertificate)
        .policyOid("1.3.6.1.4.1.4146.1.2.1")
        .serialNumber(BigInteger.valueOf(counter.getAndIncrement()))
        .buildGrantedWithMods();

// CAdES-атрибуты и цепочка сертификатов
byte[] cadesDer = TspResponseBuilder.create(request)
        .signer(tsaPrivateKey, tsaCertificate)
        .policyOid("1.3.6.1.4.1.4146.1.2.1")
        .serialNumber(BigInteger.valueOf(counter.getAndIncrement()))
        .withCAdES()                                    // <1>
        .addChainCert(intermediateCaCert)                // <2>
        .ordering(true)                                  // <3>
        .buildGranted();
----
<1> `withCAdES()` — добавляет `signingCertificateV2` в TimeStampToken.
    По умолчанию атрибуты не добавляются.
<2> `addChainCert()` — включает промежуточные сертификаты TSA в ответ.
    Сертификат подписанта включается автоматически.
<3> `ordering(true)` — флаг упорядоченности штампов (RFC 3161 §2.4.2).
    По умолчанию `false`.

==== CAdES-T — подпись с меткой времени

CAdES-T — CAdES-BES с встроенной меткой времени `signature-time-stamp`
в unsigned-атрибутах. При верификации сертификат подписанта проверяется
на момент `genTime` метки, а не на текущую дату.

Метка добавляется *после* подписания документа — это отдельный шаг,
требующий доступ к TSA по сети.

===== Полный цикл: создание CAdES-T

`CAdESExtender.addTimestamp()` выполняет все шаги автоматически:
извлекает подпись из SignedData, отправляет TSP-запрос, встраивает метку.

Подпись не содержит закрытых ключей. Результат — DER-байты CAdES-T,
которые можно свободно хранить или передавать по сети.

[source,java]
----
import org.rssys.gost.pkix.cms.CAdESExtender;
import org.rssys.gost.pkix.cms.CmsSignedDataBuilder;
import org.rssys.gost.pkix.tsp.JdkHttpTspTransport;
import org.rssys.gost.pkix.tsp.TspTransport;

// Шаг 1. Создаём CAdES-BES
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(privateKey, cert)
        .withCAdES()
        .build();

// Шаг 2. Добавляем метку времени — один вызов
TspTransport transport = new JdkHttpTspTransport();
byte[] cadesT = CAdESExtender.addTimestamp(
        cadesBes,
        "http://tsa.example.com/tsa",
        transport,
        tsaTrustedCert);            // <1>
----
<1> `tsaTrustedCert` — доверенный корневой сертификат TSA (или промежуточный CA).
Для верификации подписи TSA.

===== Несколько подписантов — каждому своя метка

Если документ подписывают несколько человек, `CAdESExtender` запрашивает
отдельную метку времени для каждого. При верификации проверяются все.

[source,java]
----
// Два подписанта: директор и главбух
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(contract)
        .addSigner(dirKey, dirCert)          // <1>
        .addSigner(chiefKey, chiefCert)      // <2>
        .withCAdES()
        .build();

// Один вызов — метки для обоих
byte[] cadesT = CAdESExtender.addTimestamp(
        cadesBes, "http://tsa.example.com/tsa",
        transport, tsaTrustedCert);

// Оба подписанта проверены
VerifiedCAdESData result = CAdESExtender.verifyCAdEST(cadesT, tsaTrustedCert);
assert result.signers().size() == 2;         // директор + главбух

for (CAdESSignerResult sr : result.signers()) {
    System.out.println("Подписант: " + sr.signerCertificate().getSubjectDn());
    System.out.println("Меток: " + sr.timestamps().size());
}
----
<1> Директор — его ключ и сертификат.
<2> Главбух — его ключ и сертификат.

===== Верификация CAdES-T

`CAdESExtender.verifyCAdEST()` проверяет подпись целиком: подпись подписанта,
`signingCertificateV2`, метку времени, цепочки подписанта и TSA,
валидность сертификата подписанта на момент `genTime` метки.

[source,java]
----
import org.rssys.gost.pkix.cms.CAdESExtender;
import org.rssys.gost.pkix.cms.VerifiedCAdESData;

// trustedCerts — общий массив: корневые сертификаты подписанта и TSA
VerifiedCAdESData result =
        CAdESExtender.verifyCAdEST(cadesT, rootCaCert, tsaTrustedCert);

byte[] originalData = result.data();              // <1>
CAdESSignerResult firstSigner = result.signers().get(0);
GostCertificate signer = firstSigner.signerCertificate();
List<TstInfo> stamps = firstSigner.timestamps();  // <2>

for (TstInfo t : stamps) {
    System.out.println("Метка времени: " + t.genTime());
    System.out.println("TSA политика: " + t.policyOid());
}
----
<1> Для detached — `null`. Приложение проверяет данные самостоятельно.
<2> Список меток из unsigned-атрибутов. Каждая — проверена: `messageImprint`
совпадает с хэшем подписи подписанта, подпись TSA валидна.

Если любая из проверок не проходит — `PkixException` (fail-closed).

===== Ручное встраивание метки (DER-операция, без сети)

Если TimeStampToken уже получен (например, из файла или базы данных),
встроить его можно без сетевых вызовов:

[source,java]
----
byte[] cadesT = CAdESExtender.embedTimestamp(cadesBesDer, timeStampTokenDer);
----

Для нескольких подписантов с заранее полученными токенами —
`embedTimestamps()` (один токен на подписанта, в порядке чтения):

[source,java]
----
byte[] cadesT = CAdESExtender.embedTimestamps(cadesBesDer, List.of(token1, token2));
----

==== Countersignature (RFC 5652 §11.4) — контрподпись

Countersignature добавляет к подписи *контрподпись* — подпись третьего участника
(нотариуса, удостоверяющего центра), который подтверждает: «да, эта подпись
действительно была создана и существовала на такой-то момент».
Контрподпись хранится внутри основного CMS-документа, в unsigned-атрибутах.

Контрподпись не подписывает сам документ — она подписывает криптографическое
значение подписи автора. Поэтому изменение документа сломает подпись автора,
но не контрподпись — и наоборот.

===== Создание countersignature

Вызывается одним методом `embedCountersignature()`:

[source,java]
----
// 1. Создаём CAdES-BES подпись (автор документа)
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(documentBytes)
        .addSigner(authorPrivateKey, authorCert)    // автор
        .withCAdES()
        .build();

// 2. Добавляем контрподпись (нотариус)
byte[] countersigned = CAdESExtender.embedCountersignature(
        cadesBes,
        notaryPrivateKey,      // закрытый ключ нотариуса
        notaryCert);           // сертификат нотариуса (добавится в CMS-документ)
----

Можно передать как CAdES-BES (без меток времени), так и CAdES-T (с метками) —
контрподпись добавится в любом случае.

===== Проверка countersignature

При проверке `verifyCountersignature()` библиотека:
. Проверяет подпись автора и его сертификат.
. Проверяет контрподпись: что она подписала именно подпись автора, а не что-то другое.
. Проверяет цепочку сертификата нотариуса до доверенного корня.

Контрподпись обязательна — если её нет, проверка завершится ошибкой.

[source,java]
----
import org.rssys.gost.pkix.cms.CAdESExtender;
import org.rssys.gost.pkix.cms.VerifiedCAdESData;

// trustedCerts — корневой сертификат, которому доверяют и автор, и нотариус
VerifiedCAdESData result =
        CAdESExtender.verifyCountersignature(countersignedDer, rootCaCert);

// Результаты проверки
byte[] originalData = result.data();                    // исходный документ
CAdESSignerResult author = result.signers().get(0);     // результат автора
SignerResult notary = author.countersignatures().get(0); // результат нотариуса

// Сертификат и signed-атрибуты нотариуса
GostCertificate notaryCert = notary.signerCertificate();
List<CmsAttribute> notaryAttrs = notary.signedAttributes();
----

==== CAdES-C — полные ссылки на сертификаты и данные отзыва

CAdES-C (RFC 5126 §6.2) расширяет CAdES-BES/T двумя unsigned-атрибутами,
фиксирующими хэши и идентификаторы всех сертификатов и данных отзыва,
необходимых для полной проверки подписи.

*Проблема.* CAdES-BES/T содержит только сертификат подписанта и метку времени.
Верификатору нужно самостоятельно найти и проверить промежуточные CA-сертификаты
и CRL/OCSP-ответы `—` без них подпись невалидна. CAdES-C фиксирует *что именно*
нужно иметь для верификации (ссылки на сертификаты и отзыв).

*Атрибуты CAdES-C:*

- `complete-certificate-references` `—` SEQUENCE OF OtherCertID:
хэш DER-кодирования каждого CA-сертификата цепочки + IssuerSerial.
Сертификат подписанта не включается (он уже в `signingCertificateV2`).
Доверенный корень не включается (известен верификатору заранее).
- `complete-revocation-references` `—` SEQUENCE OF CrlOcspRef:
для каждого сертификата цепочки (включая подписанта) `—` хэш CRL или
OCSP-ответа + идентификатор (issuer, время, номер CRL / responderID).

*Что НЕ делает CAdES-C:*

- Не встраивает сами значения сертификатов/CRL в конверт (это CAdES-X Long).
- Не проверяет фактический статус отзыва сертификатов (только ссылки).
- crlHash не сверяется с актуальными CRL `—` CRL не эмбеддятся.

===== Создание CAdES-C

Метод `embedCompleteRefs()` встраивает C-атрибуты в CAdES-BES/T:
принимает CAdES-BES/T DER, цепочку сертификатов и данные отзыва (CRL и OCSP).
Сертификаты цепочки автоматически добавляются в поле `certificates` SignedData.

[source,java]
----
import org.rssys.gost.pkix.cms.CAdESExtender;
import org.rssys.gost.pkix.cms.CertChainBuilder;
import org.rssys.gost.pkix.cert.GostCrl;
import org.rssys.gost.pkix.cert.GostCrlBuilder;
import java.util.Arrays;
import java.util.List;

// 1. Строим CAdES-BES
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(signerKey, signerCert)
        .addCertificate(caCert)
        .withCAdES()
        .build();

// 2. Строим цепочку и данные отзыва
List<GostCertificate> chain = CertChainBuilder.buildChain(
        signerCert, Arrays.asList(caCert), rootCert);

byte[] crlDer = GostCrlBuilder.create(caCert.getSubjectDnBytes())
        .thisUpdateNow().nextUpdateDays(30).withCrlNumber(1)
        .sign(caKey);
GostCrl crl = new GostCrl(crlDer);

// 3. Встраиваем CAdES-C атрибуты
byte[] cadesC = CAdESExtender.embedCompleteRefs(
        cadesBes, chain,
        Arrays.asList(crl, null),    // CRL для signer и CA
        Arrays.asList(null, null));  // OCSP-ответы (нет)
----

===== Convenience-перегрузка через CertRevocationData

Удобная перегрузка принимает данные отзыва через `CertRevocationData` —
тот же формат, что и `ChainValidator.validateChainWithRevocation()`:

[source,java]
----
import org.rssys.gost.pkix.cert.CertRevocationData;

List<CertRevocationData> revData = Arrays.asList(
        new CertRevocationData(null, crlDer),   // CRL для подписанта
        null);                                   // для CA — пропускаем

byte[] cadesC = CAdESExtender.embedCompleteRefs(cadesBes, chain, revData);
----

===== Верификация CAdES-C

`verifyCAdESC()` проверяет: CMS-подпись (AND-семантика), `signingCertificateV2`,
метки времени, certHash каждого OtherCertID против embedded сертификатов
(dispatch строго по OID из OtherHash `—` whitelist Стрибог-256/512,
PkixException на незнакомом OID), структурную целостность CrlOcspRef.

[source,java]
----
VerifiedCAdESData result = CAdESExtender.verifyCAdESC(cadesC, rootCert);

for (CAdESSignerResult sr : result.signers()) {
    // C-атрибуты доступны через результат верификации
    List<CAdESCompleteData.OtherCertID> certRefs = sr.completeCertRefs();
    List<CAdESCompleteData.CrlOcspRef> revocRefs = sr.completeRevocRefs();

    System.out.println("Ссылок на сертификаты: " + certRefs.size());
    System.out.println("Ссылок на отзыв: " + revocRefs.size());
}
----

[CAUTION]
.C-уровень не проверяет отзыв
====
`verifyCAdESC` проверяет только структурную целостность атрибутов и
certHash против embedded сертификатов. Фактический статус отзыва
сертификатов (CRL revocation status, OCSP certStatus) не проверяется
`—` отложено до CAdES-X Long, где CRL/OCSP-ответы встраиваются
в конверт и доступны для проверки. Revoked-сертификат успешно
проходит `verifyCAdESC`.
====

===== CAdES-X Long Type 1 — долгосрочная подпись с проверкой отзыва

*Атрибуты CAdES-X Long Type 1 (добавляются поверх CAdES-C):*

- `certificate-values` (OID `1.2.840.113549.1.9.16.2.23`): SEQUENCE OF Certificate —
  встроенные значения всех сертификатов цепочки (signer + intermediate CA).
  Сертификат подписанта уже в `signingCertificateV2`, корень известен верификатору отдельно.
- `revocation-values` (OID `1.2.840.113549.1.9.16.2.24`): SEQUENCE { [0] CRL, [1] OCSP } —
  встроенные значения CRL и OCSP-ответов для каждого сертификата цепочки.
- `content-time-stamp` (OID `1.2.840.113549.1.9.16.2.20`): опциональная метка времени
  на содержимое документа (ES-C, RFC 5126 §5.11.1). Добавляется как signed-атрибут
  через `CmsSignedDataBuilder.contentTimestamp()`.

*Ключевое отличие от CAdES-C:*
CAdES-X Long Type 1 не только ссылается на сертификаты и данные отзыва (как C-уровень),
но и встраивает их значения в конверт. Это позволяет проверить статус отзыва
каждого сертификата цепочки непосредственно при верификации — без обращения
к внешним источникам. Отозванный сертификат → `PkixException` (fail-closed).

*Что НЕ делает CAdES-X Long Type 1:*
- Не добавляет архивные метки времени (это CAdES-A).
- Не добавляет вторую метку времени на сами certificate/revocation-values
  (это CAdES-X Long Type 2 по ETSI TS 101 733 — не реализован).

===== Создание CAdES-X Long Type 1

Метод `embedXLongType1()` выполняет авто-апгрейд: CAdES-BES → T → C → X-Long Type 1.
Если на входе уже CAdES-T или CAdES-C, соответствующие шаги пропускаются.

[source,java]
----
import org.rssys.gost.pkix.cms.CAdESExtender;
import org.rssys.gost.pkix.cms.CAdESCompleteData;
import org.rssys.gost.pkix.cms.CertChainBuilder;
import org.rssys.gost.pkix.tsp.InMemoryTspTransport;

// 1. Строим CAdES-BES (можно с content-time-stamp)
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(signerKey, signerCert)
        .addCertificate(caCert)
        .withCAdES()
        .contentTimestamp(tsaUrl, transport, tsaCert)  // опционально
        .build();

// 2. Строим цепочку и данные отзыва
List<GostCertificate> chain = CertChainBuilder.buildChain(
        signerCert, Arrays.asList(caCert), rootCert);

byte[] crlDer = GostCrlBuilder.create(caCert.getSubjectDnBytes())
        .thisUpdateNow().nextUpdateDays(30).withCrlNumber(1)
        .sign(caKey);
GostCrl crl = new GostCrl(crlDer);

// 3. Строим CAdES-X Long Type 1 (авто-апгрейд: T + C + X-Long)
//    crlsForChain — parallel list к chain: [signerCrl, caCrl]
//    без корневого CRL (revocRefs = chain-1 позиций)
byte[] cadesXLong = CAdESExtender.embedXLongType1(
        cadesBes, chain,
        Arrays.asList(crl, null),      // CRL для signer и CA (без корня)
        Arrays.asList(null, null),     // OCSP-ответы
        tspUrl, tsaTransport, tsaCert);
----

===== Верификация CAdES-X Long Type 1

`verifyCAdESXLong()` проверяет: CMS-подпись (AND-семантика), `signingCertificateV2`,
метки времени, complete-certificate-references, complete-revocation-references,
certificate-values (certHash + IssuerSerial ↔ embedded сертификат),
revocation-values (crlHash ↔ embedded CRL, ocspRepHash ↔ embedded OCSP),
валидность цепочки сертификатов и **фактический статус отзыва** каждого сертификата.

[source,java]
----
VerifiedCAdESData result = CAdESExtender.verifyCAdESXLong(cadesXLong, rootCert);

for (CAdESSignerResult sr : result.signers()) {
    // X-Long атрибуты доступны через результат верификации
    List<GostCertificate> certValues = sr.certificateValues();
    CAdESXLongData.RevocationValuesDecoded revocValues = sr.revocationValues();

    System.out.println("Встроенных сертификатов: " + certValues.size());
    System.out.println("CRL для цепочки: " + revocValues.crls().size());
    System.out.println("OCSP-ответов: " + revocValues.ocspResponses().size());
}
----

[IMPORTANT]
.X-Long проверяет статус отзыва
======
В отличие от `verifyCAdESC`, который не проверяет crlHash (CRL не встроены),
`verifyCAdESXLong` получает CRL и OCSP-ответы из `revocation-values` и
проверяет статус отзыва каждого сертификата цепочки через
`ChainValidator.validateChainWithRevocation()`. Отозванный сертификат
приводит к `PkixException`. Это основное семантическое отличие X-Long от C.
======

=== CMS EnvelopedData — шифрование

.CmsEnvelopedDataBuilder — шифрует данные по RFC 5652 §6:
- Генерирует случайный CEK (Content Encryption Key, 32 байта) и IV (8 байт).
- Шифрует данные на CEK через Кузнечик CTR-ACPKM.
- Для каждого получателя вычисляет KEK через VKO ГОСТ Р 34.10-2012,
  оборачивает CEK через KExp15 (RFC 9189 §8.2.1).
- CEK и IV затираются сразу после использования.
- По умолчанию используется KeyTransRecipientInfo (ktri, тег `0x30`) —
  обязательный формат по ТК26 §8.2.1, совместим с КриптоПРО 5.0.
  Для KeyAgreeRecipientInfo (kari, тег `0xA1`, ТК26 §8.2.2) —
  фабрика `.createKari()`.
- `.withOmac()` включает имитовставку (Encrypt-then-MAC, OID
  `id-gostr3412-2015-kuznyechik-ctracpkm-omac`) по ТК26 §8.3.1 —
  помимо конфиденциальности обеспечивает целостность данных.

+
Результат `build()` — DER-байты, содержащие зашифрованные данные и
обёрнутый CEK. Можно свободно передавать по сети: без закрытого ключа
получателя расшифровать невозможно. CEK не попадает в результат в открытом виде.

`CmsEnvelopedDataDecryptor` расшифровывает: определяет тип RecipientInfo
(ktri или kari) по тегу, находит свой идентификатор получателя,
вычисляет KEK через VKO, разворачивает CEK через KImp15, расшифровывает данные.
При наличии OMAC проверка MAC происходит автоматически.

`CmsKeyWrap` (пакет `org.rssys.gost.pkix.cms`) — stateless-абстракция алгоритма
обёртывания ключа: содержит только методы `wrap()` / `unwrap()` и `algorithmOid()`.
В DER-структуру EnvelopedData встраивается только OID алгоритма — сам объект
`CmsKeyWrap` не передаётся. Отправитель и получатель независимо создают
одинаковый `CmsKeyWrap` (по умолчанию `Kexp15CmsKeyWrap`).

==== Шифрование и расшифровка

[source,java]
----
import org.rssys.gost.pkix.cms.*;

byte[] data = "Конфиденциальный документ".getBytes(StandardCharsets.UTF_8);
// Stateless-объект алгоритма — не содержит секретов, не передаётся.
// В DER встраивается только OID ("1.2.643.7.1.1.7.2.1").
CmsKeyWrap keyWrap = new Kexp15CmsKeyWrap();

// Шифрование — передаём открытый ключ через сертификат получателя
byte[] envelopedData = CmsEnvelopedDataBuilder.create()
        .data(data)
        .addRecipient(recipientCert)   // сертификат получателя
        .keyWrap(keyWrap)
        .build();

// Расшифрование — получатель использует свой закрытый ключ.
// keyWrap создаётся независимо, не извлекается из EnvelopedData.
byte[] decrypted = CmsEnvelopedDataDecryptor.decrypt(
        envelopedData, recipientPrivateKey, recipientCert, keyWrap);

assert Arrays.equals(data, decrypted);
----

==== Шифрование с имитовставкой (OMAC)

При вызове `.withOmac()` контент шифруется в режиме Encrypt-then-MAC
(Кузнечик CTR-ACPKM-OMAC). Расшифрование автоматически проверяет MAC —
любая подделка данных приводит к `PkixException` (fail-closed).

[source,java]
----
byte[] data = "Конфиденциальный документ".getBytes(StandardCharsets.UTF_8);
CmsKeyWrap keyWrap = new Kexp15CmsKeyWrap();

// Шифрование с имитовставкой
byte[] envelopedData = CmsEnvelopedDataBuilder.create()
        .data(data)
        .addRecipient(recipientCert)
        .keyWrap(keyWrap)
        .withOmac()
        .build();

// Расшифрование — MAC проверяется автоматически
byte[] decrypted = CmsEnvelopedDataDecryptor.decrypt(
        envelopedData, recipientPrivateKey, recipientCert, keyWrap);
assert Arrays.equals(data, decrypted);

// Подделка зашифрованных данных → PkixException (fail-closed)
byte[] tampered = Arrays.copyOf(envelopedData, envelopedData.length);
tampered[envelopedData.length / 2] ^= 0xFF;
try {
    CmsEnvelopedDataDecryptor.decrypt(tampered,
            recipientPrivateKey, recipientCert, keyWrap);
    // Не должно дойти сюда
} catch (PkixException e) {
    // MAC проверка отклонила поддельные данные — корректно
}
----

==== KeyAgreeRecipientInfo (kari)

Для формата KeyAgreeRecipientInfo (RFC 5652 §6.2.2, ТК26 §8.2.2)
используйте фабрику `.createKari()`:
`CmsEnvelopedDataBuilder.createKari()`. Все флюент-методы идентичны.

==== Несколько получателей

Один CEK оборачивается для каждого получателя независимо.
Данные шифруются один раз — все получатели расшифровывают их своим ключом.

[source,java]
----
byte[] envelopedData = CmsEnvelopedDataBuilder.create()
        .data(data)
        .addRecipient(aliceCert)       // Алиса
        .addRecipient(bobCert)         // Боб
        .keyWrap(keyWrap)
        .build();

// Алиса расшифровывает своим ключом
byte[] aliceData = CmsEnvelopedDataDecryptor.decrypt(
        envelopedData, aliceKey, aliceCert, keyWrap);

// Боб — своим
byte[] bobData = CmsEnvelopedDataDecryptor.decrypt(
        envelopedData, bobKey, bobCert, keyWrap);
----

=== CMS Sign+Encrypt — совмещённая подпись и шифрование

.CmsSignedAndEnvelopedData — хелпер для вложения (nesting) одного CMS ContentInfo
в другой по RFC 5652.

Два порядка вложенности:

- *sign-then-encrypt* — SignedData внутри EnvelopedData.
  Подпись скрыта от внешнего наблюдателя: чтобы узнать подписанта, нужно расшифровать.
- *encrypt-then-sign* — EnvelopedData внутри SignedData.
  Подпись видна снаружи: можно проверить авторство без расшифрования (аудируемость).


Обе операции — stateless. Ключевой материал не сохраняется в объекте,
хелпер содержит только static-методы.

==== sign-then-encrypt: подпись, затем шифрование

[source,java]
----
import org.rssys.gost.pkix.cms.CmsSignedAndEnvelopedData;

byte[] data = "Конфиденциальный подписанный документ".getBytes();

// Подписать и зашифровать для получателя
byte[] combined = CmsSignedAndEnvelopedData.signThenEncrypt(
        data, signerKey, signerCert, recipientCert);

// Получатель расшифровывает и проверяет подпись
VerifiedSignedData result =
        CmsSignedAndEnvelopedData.decryptAndVerify(
                combined, recipientKey, recipientCert, signerCert);

byte[] original = result.data();
GostCertificate signer = result.signerCertificate();
----

==== encrypt-then-sign: шифрование, затем подпись

[source,java]
----
byte[] data = "Аудируемый зашифрованный документ".getBytes();

// Зашифровать для получателя и подписать
byte[] combined = CmsSignedAndEnvelopedData.encryptThenSign(
        data, signerKey, signerCert, recipientCert);

// Проверить подпись (без расшифрования) и расшифровать
VerifiedSignedData result =
        CmsSignedAndEnvelopedData.verifyAndDecrypt(
                combined, recipientKey, recipientCert, signerCert);

assert Arrays.equals(data, result.data());
----

==== Несколько получателей

Для sign-then-encrypt работает стандартный механизм EnvelopedData:
один CEK оборачивается для каждого получателя независимо.

[source,java]
----
byte[] combined = CmsSignedAndEnvelopedData.signThenEncrypt(
        data, signerKey, signerCert,
        aliceCert,    // Алиса
        bobCert);     // Боб

// Алиса расшифровывает
VerifiedSignedData aliceResult =
        CmsSignedAndEnvelopedData.decryptAndVerify(
                combined, aliceKey, aliceCert, signerCert);

// Боб расшифровывает
VerifiedSignedData bobResult =
        CmsSignedAndEnvelopedData.decryptAndVerify(
                combined, bobKey, bobCert, signerCert);

Классы, используемые совместно с основным API.

==== Построение цепочки из неупорядоченного пула — `CertChainBuilder`

`CertChainBuilder` собирает цепочку leaf->root по совпадению subject/issuer DN
и проверяет подписи на каждом шаге. Используется в `CmsSignedDataVerifier`
для построения цепочки из сертификатов внутри CMS.

[source,java]
----
import org.rssys.gost.pkix.cms.CertChainBuilder;

// pool — промежуточные сертификаты (из CMS или PEM)
// trustedRoots — доверенные корневые сертификаты
List<GostCertificate> chain = CertChainBuilder.buildChain(
        leafCert, intermediatePool, trustedRoots);

// Результат leaf-first: [leaf, inter, root]
GostCertificate root = chain.get(chain.size() - 1);
----

Возможные ошибки: `INCOMPLETE_CHAIN` (не найден issuer), `CHAIN_LOOP`
(зацикливание DN), `CHAIN_TOO_LONG` (превышена глубина), `ROOT_NOT_TRUSTED`.

==== Хеширование CertID для OCSP — `CertIdHasher`

Вычисляет `issuerNameHash` и `issuerKeyHash` для записей CertID
в OCSP-запросах и ответах (RFC 6960 §4.1.1).

[source,java]
----
import org.rssys.gost.pkix.cert.CertIdHasher;
import org.rssys.gost.pkix.GostOids;

// Из DER сертификата издателя
byte[] nameHash = CertIdHasher.hashIssuerName(issuerCertDer);
byte[] keyHash  = CertIdHasher.hashIssuerPublicKey(issuerCertDer);

// Из объекта GostCertificate — по размеру ключа (256/512)
int hlen = caCert.getKeySize() == 512

        : GostOids.STREEBOG_256_HASH_LEN;

byte[] keyHash2  = CertIdHasher.hashIssuerPublicKey(caCert, hlen);

==== Кодирование GeneralNames — `GeneralNameCodec`

Кодирует все типы GeneralName (RFC 5280 §4.2.1.6) в DER: dNSName, iPAddress,
rfc822Name, URI, directoryName, otherName (включая UPN).
Используется в `GostCertificateBuilder` (SAN) и `GostCrlBuilder` (certificateIssuer).

[source,java]
----
import org.rssys.gost.pkix.cert.GeneralNameCodec;

// DNS-имя
byte[] dnsName = GeneralNameCodec.encodeDnsName("example.com");

// IP-адрес
byte[] ipAddr = GeneralNameCodec.encodeIpAddress("192.168.1.1");

// Distinguished Name
byte[] issuerDn = GostDnParser.encodeDn("CN=My CA,O=MyOrg,C=RU");
byte[] dirName = GeneralNameCodec.encodeDirectoryName(issuerDn);

// rfc822Name (email), URI
byte[] rfc822 = GeneralNameCodec.encodeRfc822Name("admin@example.com");
byte[] uri = GeneralNameCodec.encodeUri("https://example.com");

// otherName с UPN (User Principal Name)
byte[] upn = GeneralNameCodec.encodeOtherNameUpn("user@domain.ru");

// Собрать SEQUENCE OF GeneralName (например, для certificateIssuer в CRL)
byte[] generalNames = GeneralNameCodec.encodeGeneralNames(
        dnsName, ipAddr, dirName, rfc822, uri, upn);

==== Типизированные причины ошибок — `PkixException.Reason`

`PkixException` — checked-исключение с перечислением `Reason` для межмодульного маппинга.
Все методы верификации бросают его при ошибке (fail-closed).
TLS-слой преобразует `Reason` в alert-код без разбора текста сообщения.

.Перечень причин:

|===
| `EXPIRED`                  | Сертификат просрочен
| `ROOT_NOT_SIGNED`          | Корневой сертификат не самоподписан
| `DN_MISMATCH`              | Несовпадение subject/issuer DN в цепочке
| `NOT_CA`                   | Сертификат не является CA
| `MISSING_KEY_CERT_SIGN`    | Отсутствует флаг keyCertSign
| `PATH_LEN_EXCEEDED`        | Превышена длина пути pathLenConstraint
| `ALG_MISMATCH`             | Несовместимость алгоритмов
| `POLICY_VIOLATION`         | Нарушение политики сертификата (CertificatePolicies)
| `UNKNOWN_CRITICAL_EXTENSION` | Неизвестное критическое расширение
| `SIGNATURE_INVALID`        | Недействительная подпись
| `PARSE_ERROR`              | Ошибка разбора DER / ASN.1
| `THIS_UPDATE_FUTURE`       | thisUpdate в будущем (CRL/OCSP)
| `IDP_NOT_SUPPORTED`        | Неподдерживаемый issuingDistributionPoint
| `DELTA_CRL_NOT_SUPPORTED`  | Delta CRL без базового CRL
| `REVOKED`                  | Сертификат отозван

| `CHAIN_LOOP`               | Зацикливание DN в цепочке
| `CHAIN_TOO_LONG`           | Превышена максимальная глубина цепочки

=== Типовые сценарии

Сквозные примеры для распространённых задач — от начала до конца.
Все переменные (`cert`, `caCert`, `caPrivateKey` и др.) создаются как в <<Быстрый старт,Быстром старте>>.

==== Создание инфраструктуры CA

Полный цикл: root CA -> промежуточный CA -> конечный сертификат.

[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificateBuilder;
import org.rssys.gost.pkix.cert.ChainValidator;
import org.rssys.gost.api.KeyGenerator;
import org.rssys.gost.signature.ECParameters;
import java.math.BigInteger;
import java.util.List;

ECParameters params = ECParameters.tc26a256();

// 1. Корневой CA (самоподписанный)
var rootKp = KeyGenerator.generateKeyPair(params);
GostCertificate rootCert = GostCertificateBuilder.create(params, "CN=Root CA,O=MyOrg,C=RU")
        .publicKey(rootKp.getPublic())
        // Удобный способ: .notBeforeNow().validForYears(20)
        .notBefore("20260101000000Z")
        .notAfter("20460101000000Z")
        .basicConstraints(true, null)          // CA без ограничения pathLen
        .keyUsage(GostCertificateBuilder.KeyUsage.KEY_CERT_SIGN,
                  GostCertificateBuilder.KeyUsage.CRL_SIGN)
        .randomSerial()
        .sign(rootKp.getPrivate());

// 2. Промежуточный CA
var interKp = KeyGenerator.generateKeyPair(params);
GostCertificate interCert = GostCertificateBuilder.create(params, "CN=Intermediate CA,O=MyOrg,C=RU")
        .publicKey(interKp.getPublic())
        .issuerDn("CN=Root CA,O=MyOrg,C=RU")   // <1>
        .notBefore("20260101000000Z")
        .notAfter("20360101000000Z")
        .basicConstraints(true, 0)             // CA, pathLen=0
        .keyUsage(GostCertificateBuilder.KeyUsage.KEY_CERT_SIGN,
                  GostCertificateBuilder.KeyUsage.CRL_SIGN)
        .randomSerial()
        .sign(rootKp.getPrivate());     // подписан корневым CA

// 3. Конечный сертификат (end-entity)
var leafKp = KeyGenerator.generateKeyPair(params);
GostCertificate leafCert = GostCertificateBuilder.create(params, "CN=server.example.com,O=MyOrg,C=RU")
        .publicKey(leafKp.getPublic())
        .issuerDn("CN=Intermediate CA,O=MyOrg,C=RU")
        .notBefore("20260101000000Z")
        .notAfter("20270101000000Z")
        .sanDns("server.example.com", "www.example.com")
        .basicConstraints(false, null)         // не CA
        .keyUsage(GostCertificateBuilder.KeyUsage.DIGITAL_SIGNATURE)
        .extendedKeyUsage(GostOids.EXT_SERVER_AUTH)
        .randomSerial()
        .sign(interKp.getPrivate());    // подписан промежуточным CA

// 4. Валидация цепочки
List<GostCertificate> chain = List.of(leafCert, interCert);
ChainValidator.validateChain(chain, List.of(rootCert.getPublicKey()));
----
<1> `issuerDn(String)` — String-перегрузка, не требует `GostDnParser.encodeDn()`.
+
`.randomSerial()` задаёт криптографически случайный серийный номер (128 бит) —
рекомендуемый способ для продакшена. Серийный номер обязателен: без явного
`.serial(...)` или `.randomSerial()` сборка отвергается (RFC 5280 §4.1.2.2,
CA/Browser Forum BR §7.1).

==== AIA-расширение в сертификате

Authority Information Access (RFC 5280 §4.2.2.1) — указание URI для OCSP-ответчика
и/или скачивания сертификата издателя (caIssuers). Оба URI можно задать одновременно —
построитель поместит их в одно AIA-расширение.

[source,java]
----
GostCertificate leafCert = GostCertificateBuilder.create(params, "CN=server.example.com,O=MyOrg,C=RU")
        .publicKey(leafKp.getPublic())
        .issuerDn("CN=Intermediate CA,O=MyOrg,C=RU")
        .notBefore("20260101000000Z")
        .notAfter("20270101000000Z")
        .sanDns("server.example.com")
        .keyUsage(GostCertificateBuilder.KeyUsage.DIGITAL_SIGNATURE)
        .randomSerial()
        .ocspResponder("http://ocsp.example.com")          // id-ad-ocsp
        .caIssuer("http://ca.example.com/cert.p7c")        // id-ad-caIssuers
        .crlDistributionPoints("http://crl.example.com/crl.crl")
        .freshestCrl("http://ca.example/delta.crl")   // delta CRL (FreshestCRL)
        .sign(interKp.getPrivate());
----

URI из AIA-расширения доступны через `GostCertificate`:
- `leafCert.getOcspUris()` — массив URI OCSP-ответчиков (или null);
- `leafCert.getCaIssuersUris()` — массив URI caIssuers (или null);
- `leafCert.getAiaUris()` — все AIA URI (OCSP + caIssuers);
- `leafCert.getCdpUris()` — URI точек распространения CRL;
- `leafCert.getFreshestCrlUris()` — URI для получения delta CRL (FreshestCRL).

Статический метод `GostCertificateBuilder.buildAiaExtension(ocspUri, caIssuersUri)`
позволяет собрать AIA-расширение отдельно (например, для `additionalExtensions`).

==== Полный цикл OCSP

Построение запроса, разбор ответа, проверка nonce.

[source,java]
----
import org.rssys.gost.pkix.cert.*;

// 1. Строим OCSP-запрос
GostOcspRequestBuilder reqBuilder = GostOcspRequestBuilder.create()
        .targetCert(leafCert.getEncoded())
        .issuerCert(interCert.getEncoded());
byte[] requestDer = reqBuilder.build();
byte[] expectedNonce = reqBuilder.getNonce();

// 2. ... передача requestDer на OCSP-responder по HTTP ...

// 3. Строим OCSP-ответ (на стороне CA)
byte[] ocspDer = GostOcspResponseBuilder.create(leafCert.getSerialNumber())
        .issuerDn("CN=Intermediate CA,O=MyOrg,C=RU")
        .nonce(expectedNonce)                    // вернём nonce из запроса
        .good()
        .sign(caPrivateKey);

// 4. Проверяем ответ (nonce проверяется внутри OcspVerifier)
OcspVerifier.verify(ocspDer, leafCert.getSerialNumber(), interCert, expectedNonce);

// 5. Разбираем ответ для деталей
GostOcspResponse response = GostOcspResponse.fromDer(ocspDer);
System.out.println("Produced at: " + response.getProducedAt());
for (SingleOcspResponse sr : response.getResponses()) {
    System.out.println("Status: " + (sr.isGood() ? "good" : sr.isRevoked() ? "revoked" : "unknown"));
}
----

==== Безопасная передача ключей через PKCS#12

Создание PFX-контейнера, сохранение, передача и загрузка.

[source,java]
----
import org.rssys.gost.pkix.cert.GostPkcs12Builder;
import org.rssys.gost.pkix.cert.GostPkcs12Loader;
import java.nio.file.Path;

// 1. Создать и сразу записать в файл (один вызов)
GostPkcs12Builder.create()
        .key(leafKp.getPrivate())
        .certificate(leafCert)
        .caCertificate(interCert)
        .caCertificate(rootCert)
        .password("changeit".toCharArray())
        .friendlyName("server-key")
        .iterations(100_000)
        .buildAndWriteTo(Path.of("keystore.pfx"));  // <1>

// Альтернатива: получить byte[] и распорядиться самостоятельно
byte[] pfx = GostPkcs12Builder.create()
        .key(leafKp.getPrivate())
        .certificate(leafCert)
        .password("changeit".toCharArray())
        .build();

// 2. Загрузка на другой стороне
GostPkcs12Loader.Result result = GostPkcs12Loader.load(
        pfx,
        "changeit".toCharArray(), true);

PrivateKeyParameters loadedKey = result.getPrivateKey();
List<GostCertificate> chain = result.getCertificateChain();
// chain.get(0) — конечный сертификат, chain.get(1) — inter, chain.get(2) — root
----
<1> `buildAndWriteTo()` — записывает PFX напрямую в файл, без промежуточного `byte[]`.
PFX можно передавать по сети — без пароля бесполезен.

==== Долговременная подпись CAdES-T

Полный цикл: подписать с CAdES-BES, запросить метку времени у TSA, проверить.

[source,java]
----
import org.rssys.gost.pkix.cms.CAdESExtender;
import org.rssys.gost.pkix.cms.CmsSignedDataBuilder;
import org.rssys.gost.pkix.tsp.JdkHttpTspTransport;

byte[] data = "Годовой отчёт".getBytes(StandardCharsets.UTF_8);

// 1. Создаём CAdES-BES
byte[] cadesBes = CmsSignedDataBuilder.create()
        .data(data)
        .addSigner(signerPrivateKey, signerCert)
        .withCAdES()
        .build();

// 2. Добавляем метку времени от TSA
byte[] cadesT = CAdESExtender.addTimestamp(
        cadesBes,
        "http://tsa.example.com/tsa",
        new JdkHttpTspTransport(),
        tsaTrustedCert);

// 3. Сохраняем cadesT. Проверить можно через месяц или год:
VerifiedCAdESData verified = CAdESExtender.verifyCAdEST(cadesT, tsaTrustedCert);

byte[] originalData = verified.data();
CAdESSignerResult signer = verified.signers().get(0);
System.out.println("Подписант: " + signer.signerCertificate().getSubjectDn());
System.out.println("Меток времени: " + signer.timestamps().size());
for (TstInfo t : signer.timestamps()) {
    System.out.println("  Время метки: " + t.genTime());
}
----

Если TSA недоступен, но токен уже получен — используйте `embedTimestamp()`:
----
byte[] cadesT = CAdESExtender.embedTimestamp(cadesBesDer, timeStampTokenDer);
----

==== Обработка ошибок верификации

Все методы верификации бросают `PkixException` (checked).
Рекомендуемый паттерн обработки:

[source,java]
----
import org.rssys.gost.pkix.cert.PkixException;

try {
    ChainValidator.validateChain(chain, trustedKeys);
    // цепочка валидна
} catch (PkixException e) {
    switch (e.reason()) {
        case EXPIRED -> log.warn("Сертификат просрочен: {}", e.getMessage());
        case REVOKED -> log.error("Сертификат отозван: {}", e.getMessage());
        case SIGNATURE_INVALID -> log.error("Подпись недействительна: {}", e.getMessage());
        case NOT_CA -> log.error("Сертификат не является CA: {}", e.getMessage());
        case INCOMPLETE_CHAIN -> log.warn("Не удалось построить цепочку: {}", e.getMessage());
        default -> log.error("Ошибка верификации: {}", e.getMessage());
    }
    throw e; // fail-closed — дальше не идём
}
----

=== Кросс-валидация

Для модуля `crypto-gost-pkix` выполнена кросс-валидация:

*SignedData — с КриптоПРО:*
подпись, созданная `CmsSignedDataBuilder`,
успешно верифицируется cryptcp (`[ErrorCode: 0x00000000]`). Подпись, созданная
cryptcp, успешно верифицируется `CmsSignedDataVerifier` (`valid: true`).
Двусторонняя совместимость подтверждена.

*CAdES-T — с BouncyCastle:*
CAdES-T подпись, созданная библиотекой, успешно верифицируется BouncyCastle.
TimeStampResp, созданный `TspResponseBuilder`, разбирается и верифицируется
BouncyCastle (nonce-echo, rejected, детекция неверного imprint).
Двусторонняя совместимость подтверждена.

*CSR (PKCS#10) — с OpenSSL:*
CSR, созданный библиотекой, успешно верифицируется `openssl req -verify`.
CSR, созданный `openssl req -new`, успешно разбирается и верифицируется
`GostCsrParser` (proof-of-possession). Двусторонняя совместимость подтверждена.

*EnvelopedData:*
КриптоПРО использует KeyTransRecipientInfo с ГОСТ 28147-89.
Наш формат — KeyAgreeRecipientInfo с VKO + KExp15 + Кузнечик CTR-ACPKM.
Несовместимы по дизайну.
