.Модуль `crypto-gost-tls13` содержит реализацию *TLS 1.3* (RFC 8446 + RFC 9367) с ГОСТ-криптографией:
.. *Протоколы:*
* *Handshake*: полный (client/server), сокращённый (`PSK`), взаимный (`mTLS`, режимы `need`/`want`).
* *ALPN (RFC 7301)* — согласование протокола прикладного уровня (HTTP/2, HTTP/1.1).
* *SNI (RFC 6066)* — имя сервера в ClientHello и выбор учётных данных для нескольких доменов.
* *KeyUpdate (RFC 8446 §4.6.3)* — обновление ключей шифрования трафика.
* *Cipher suites*: `TLS_GOSTR341112_256_WITH_KUZNYECHIK_MGM_L/S` (`TlsCiphersuite.TLS_GOST_2012_KUZNYECHIK_MGM_STREEBOG_256_L/S`, RFC 9367 §3.1.2).
* *ECDHE*: GC256A/B/C/D (256 бит), GC512A/B/C (512 бит) — семь именованных групп по RFC 9367 §3.1; стартовая группа задаётся, по умолчанию GC256B.
* *Per-record TLSTREE re-keying* — свой ключ шифрования на каждую TLS-запись.
* *Фрагментация и сборка* рукопожатий и записей (RFC 8446 §5.1), согласование `max_fragment_length` (RFC 6066 §4).
* *Session resumption*: PSK через `NewSessionTicket`. `InMemoryPskStore` на сервере расходует билет (single-use), на клиенте хранит полученные.
* *OCSP stapling*: сервер прикладывает ответ к своему сертификату; сервер может запросить и проверить staple клиентского сертификата (`ClientOcspPolicy`).
* *Post-handshake messages*: `NewSessionTicket` и `KeyUpdate`.
* *HRR (RFC 8446 §4.1.3)* — смена ECDHE-группы через HelloRetryRequest, включая пересчёт PSK binder для второго ClientHello.
* *oid_filters (RFC 8446 §4.2.5)* — выбор клиентского сертификата по OID-фильтрам.
* *Экспорт ключевого материала (RFC 8446 §7.5)* — `TlsSession.exportKeyingMaterial` для привязки к каналу.
.. *Криптография:*
* *Key schedule*: `HKDF-Streebog` (RFC 5869) по схеме TLS 1.3 (RFC 8446 §7.1).
* *Защита записей*: `MGM-AEAD` (Kuznyechik) с nonce по RFC 8446 §5.3.
* Эфемерные ключи и трафик-ключи затираются после использования.
.. *Сертификаты:*
* Разбор X.509v3 (ГОСТ Р 34.10-2012) делегирован `GostCertificate` (модуль `crypto-gost-pkix`).
* Проверка цепочки: подписи, DN (issuer -> subject), `BasicConstraints`, `KeyUsage`, `ExtendedKeyUsage` (`serverAuth` / `clientAuth`), pathLen, `NameConstraints` якоря.
* Проверка имени: dNSName и iPAddress (RFC 6125), IDN приводится к A-label.
* Проверка OCSP-ответов (RFC 6960) и возраста ответа.
.. *Транспорт:*
* `TlsTransport` — интерфейс записи `[header(5) || body(length)]`.
* `InMemoryTlsTransport` — в памяти, для тестов и связи сессий в одной JVM.
* `SocketTlsTransport` — блокирующий ввод-вывод через `java.net.Socket`.
* `ChannelTlsTransport` — `SocketChannel` в блокирующем режиме, чтение прерывается `Thread.interrupt()`.
.. *Пошаговое рукопожатие:*
* `TlsHandshakeEngine` — состояние рукопожатия без ввода-вывода; `TlsSession` использует его как оркестратор, JSSE — для `SSLEngine`.
.. *ByteBuffer API:*
* `TlsRecord.protect/unprotect` — перегрузки для интеграции с NIO без промежуточных массивов.
.. *Загрузка ключей:*
* `GostPkcs12Loader` — чтение PFX с ГОСТ PBE (PBKDF2-HMAC-Streebog, Кузнечик CTR-ACPKM, RFC 9337/9548); откат на JDK KeyStore только при явном `allowJdkFallback=true`.
.. *Завершение сессии:*
* `close_notify` — закрытие по протоколу; `PeerClosedException` отличает его от обрыва транспорта.
* Затирание ключевого материала при закрытии и при ошибке.
* Fatal alert — немедленное закрытие и затирание.
.. *Безопасность реализации:*
* Сравнение verify_data и PSK binder без раннего выхода (constant-time).
* Затирание ключевого материала при close, fatal alert и ошибке рукопожатия.
* Пределы против исчерпания ресурсов: длина цепочки сертификатов (10), служебные сообщения после рукопожатия, размер записи, частота KeyUpdate от собеседника.
.. *Логирование:*
* `java.util.logging` под `org.rssys.gost.tls13.*`, метка соединения `[conn#N]`, имена alert и наборов шифров (раздел «Логирование»).
.. *Ограничения:*
* Только ГОСТ-наборы; non-GOST не поддерживаются.
* Только resumption PSK: 0-RTT и external PSK не поддерживаются.
* Только `psk_dhe_ke`: ECDHE выполняется всегда, pure PSK без ECDHE не поддерживается.
* mTLS и PSK несовместимы: при запросе клиентского сертификата тикет не выдаётся.
* Прямой путь не загружает CRL и OCSP по сети: сертификат сервера проверяется по присланному staple (обязательность — `withRequireOcspStapling`), клиентский — по staple и только при `withClientOcspPolicy`.
* DN сравнивается побайтно: семантическая нормализация RFC 5280 §7.1 не реализована.
* Экспорт ключевого материала — по схеме RFC 8446 с хэшем Стрибог; RFC 9367 его не определяет.
* Повторное рукопожатие в одной сессии не поддерживается.

+
Требования: Java 21, Android 14+. Сторонних зависимостей нет: модуль опирается только на `crypto-gost-core` и `crypto-gost-pkix`.

Примеры показывают приём, а не готовую программу: без `main`, объявлений и обработки
исключений. Импорты указаны там, где пакет класса не угадать. Условные обозначения:

[cols="2,5"]
|===
| `cs` | `TlsCiphersuite.TLS_GOST_2012_KUZNYECHIK_MGM_STREEBOG_256_L` или `..._S`
| `transport` | `TlsTransport`; в примерах с сокетом — `SocketTlsTransport`
| `serverConfig`, `clientConfig` | `TlsServerConfig`, `TlsClientConfig`
| `serverTransport`, `clientTransport` | транспорты сторон одного соединения
| `server`, `client`, `session` | `TlsSession`
| `chain` | `List<GostCertificate>`, лист первым, корень последним
| `key`, `privateKey` | `PrivateKeyParameters`
| `caCert` | `GostCertificate`-якорь доверия
| `anchors` | `TrustAnchors` с этим якорем
| `password` | `char[]` из хранилища секретов; в примерах не литерал, затирается после использования
| `data` | `byte[]` с данными приложения
| `certDer`, `certPem`, `pfx` | байты соответствующего файла
|===

==== Что выбрать

[cols="3,3,4",options="header"]
|===
| Задача | Класс | Чего избегать

| Одно соединение, блокирующий ввод-вывод | `TlsSession` + `SocketTlsTransport` или `ChannelTlsTransport` | собирать записи вручную
| Нестандартный транспорт, свой цикл, JSSE | `TlsHandshakeEngine` + `TlsRecord` | ждать от `TlsSession` неблокирующего ввода-вывода
| Тест без сокетов | `InMemoryTlsTransport.newPair()` | запускать сервер и клиент в одном потоке
| Проверка сервера | `TlsClientConfig` + `TrustAnchors` + `withServerHostname` | `createClientWithoutServerAuth` в боевом коде
| Несколько доменов на сервере | `TlsServerConfig.withSniSelector` | отдельный порт на каждый домен
| Возобновление по PSK | `InMemoryPskStore`, раздельные для клиента и сервера | общее хранилище на обе стороны
| Выбор клиентского сертификата | `ClientCertificateSelector` | цепочка в конфиге при включённых `oid_filters`
| Хранение ключа и цепочки | `GostPkcs12Loader.load(..., false)` | `allowJdkFallback=true` без причины
| Свой транспорт | реализация `TlsTransport` | возвращать из `receiveRecord()` больше одной записи
|===


=== Транспорт

TLS работает поверх готового соединения: модуль отправляет и принимает целые записи
`[header(5) || body(length)]` через интерфейс `TlsTransport`.

[source,java]
----
public interface TlsTransport extends AutoCloseable {
    /** Отправляет полную TLS-запись: [header(5) || body(length)]. */
    void sendRecord(byte[] record) throws IOException;
    /** Блокирующее чтение: [header(5) || body(length)]. */
    byte[] receiveRecord() throws IOException;
    /** Чтение в ByteBuffer; встроенные транспорты переопределяют без промежуточного массива. */
    default int receiveRecord(ByteBuffer dst) throws IOException {
        byte[] record = receiveRecord();
        dst.put(record);
        return record.length;
    }
    void close() throws IOException;
}
----

`TlsSession` транспорт не закрывает: владелец — вызывающий код. В try-with-resources транспорт
объявляется раньше сессии, тогда закрытие идёт в обратном порядке: сначала сессия отправляет
`close_notify`, затем закрывается соединение.

[source,java]
----
try (TlsTransport transport = new SocketTlsTransport(socket);
     TlsSession session = TlsSession.createClient(clientConfig, transport)) {
    session.handshakeAsClient();
    session.write(data);
}
----

==== Готовые реализации

.Сокет TCP
`SocketTlsTransport` работает поверх `java.net.Socket`:

[source,java]
----
import org.rssys.gost.tls13.transport.SocketTlsTransport;
import java.net.Socket;

Socket socket = new Socket("host", 443);
socket.setSoTimeout(5000);   // без таймаута чтение тела записи может ждать бесконечно
TlsTransport transport = new SocketTlsTransport(socket);
----

`receiveRecord()` читает заголовок и тело циклом и проверяет флаг закрытия на каждой итерации.
Транспорт не потокобезопасен: один экземпляр на одно TLS-соединение.

.Канал NIO
`ChannelTlsTransport` работает поверх `SocketChannel` в блокирующем режиме и прерывается
`Thread.interrupt()`:

[source,java]
----
import org.rssys.gost.tls13.transport.ChannelTlsTransport;
import java.net.InetSocketAddress;
import java.nio.channels.SocketChannel;

SocketChannel channel = SocketChannel.open(new InetSocketAddress("host", 443));
channel.configureBlocking(true);   // иначе конструктор бросит IllegalArgumentException
TlsTransport transport = new ChannelTlsTransport(channel);
----

CAUTION: у `SocketChannel` нет таймаута чтения: `setSoTimeout` не действует, а `Selector`
несовместим с обязательным блокирующим режимом. Ограничивайте ожидание `Thread.interrupt()`;
после него канал закрыт.

.В памяти
`InMemoryTlsTransport` соединяет сессии в одной JVM — в тестах и в приложениях без сокетов:

[source,java]
----
import org.rssys.gost.tls13.transport.InMemoryTlsTransport;

// Одна сторона: входящие записи кладёт inject(), исходящие — в ту же очередь
InMemoryTlsTransport transport = new InMemoryTlsTransport();
transport.inject(record);
byte[] recv = transport.receiveRecord();

// Пара «клиент — сервер»
InMemoryTlsTransport.Pair pair = InMemoryTlsTransport.newPair();
TlsTransport clientTransport = pair.getClientTransport();
TlsTransport serverTransport = pair.getServerTransport();
----

NOTE: Потокобезопасен; ожидание записи — до 10 с. `close()` закрывает пару целиком, уже
поставленные записи `receiveRecord()` отдаст до `IOException`. `inject()` после закрытия
даёт `IllegalStateException`.

==== Свой транспорт

Реализация должна вернуть из `receiveRecord()` ровно одну запись: 5-байтовый заголовок
(RFC 8446 §5), затем тело длиной из байт `[3..4]`. Длину больше `TlsConstants.MAX_CIPHERTEXT_LENGTH`
нужно отвергать до чтения тела, иначе заявленный размер займёт память. Для `InputStream` подойдёт
`readNBytes()`, но таймаут соединения обязателен: иначе ожидание тела может не закончиться.
Перегрузка `receiveRecord(ByteBuffer)` сдвигает позицию `dst`; вызывающий делает `flip()` перед
чтением. Потокобезопасность — на усмотрение реализации; встроенные `SocketTlsTransport` и
`ChannelTlsTransport` не потокобезопасны.


=== Загрузка ключей и сертификатов

Учётные данные — цепочка сертификатов (лист первым, корень последним) и закрытый ключ
для подписи `CertificateVerify`. Сертификаты читаются из DER или PEM, ключ — из PKCS#8
(незашифрованного или зашифрованного PBES2-ГОСТ), PFX хранит ключ и цепочку вместе.

.Сертификаты: DER и PEM
[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

GostCertificate cert = GostCertificate.fromPemOrDer(
        Files.readAllBytes(Path.of("server.pem")));          // формат определяется сам
List<GostCertificate> chain = GostCertificate.listFromPem(
        Files.readAllBytes(Path.of("chain.pem")));           // один или несколько блоков

String certPem = cert.toPem();
String chainPem = GostCertificate.chainToPem(chain);
----

`fromPemOrDer` принимает ровно один PEM-блок; для файла с цепочкой служит `listFromPem`.

.Закрытый ключ: PKCS#8
[source,java]
----
import org.rssys.gost.jca.spec.GostDerCodec;
import org.rssys.gost.pkix.cert.GostPemUtils;
import org.rssys.gost.pkix.cert.GostPkcs12Loader;
import org.rssys.gost.signature.PrivateKeyParameters;
import java.nio.file.Files;
import java.nio.file.Path;

// DER PrivateKeyInfo
PrivateKeyParameters key = GostDerCodec.decodePrivateKey(
        Files.readAllBytes(Path.of("server.key")));

// PEM -----BEGIN PRIVATE KEY-----
PrivateKeyParameters fromPem = GostDerCodec.decodePrivateKey(
        GostPemUtils.pemToDer(Files.readAllBytes(Path.of("server-key.pem"))));

// PEM -----BEGIN ENCRYPTED PRIVATE KEY----- (PBES2-ГОСТ)
PrivateKeyParameters decrypted = GostPkcs12Loader.decryptPrivateKey(
        GostPemUtils.pemToDer(Files.readAllBytes(Path.of("server-key-enc.pem"))), password);
----

.PFX: ключ и цепочка вместе
[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.GostPkcs12Loader;
import org.rssys.gost.signature.PrivateKeyParameters;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

GostPkcs12Loader.Result p12 = GostPkcs12Loader.load(
        Files.readAllBytes(Path.of("server.p12")), password, false);  // false: без отката на JDK KeyStore
PrivateKeyParameters key = p12.getPrivateKey();
List<GostCertificate> chain = p12.getCertificateChain();  // от листа до последнего CA в контейнере
List<GostCertificate> all = p12.getAllCertificates();     // все кандидаты, включая вне цепочки
int dropped = p12.getDroppedCertificateCount();
----

`allowJdkFallback=false` — только ГОСТ; `true` разрешает не-ГОСТ контейнеры через JDK `KeyStore`
(лишний путь доверия). MAC обязателен; `ALLOW_MISSING` — только для legacy из доверенного
источника. `getCertificateChain()` может не содержать корень. Пароль — `char[]`: загрузчик
затирает свою копию, свою затрите сами.

.Создание PFX
[source,java]
----
import org.rssys.gost.pkix.cert.GostPkcs12Builder;
import java.nio.file.Path;

byte[] pfx = GostPkcs12Builder.create()
        .key(key)
        .certificate(leafCert)
        .caCertificate(intermediateCert)
        .caCertificate(rootCert)
        .password(password)                 // char[], не литерал
        .friendlyName("server-cert")
        .build();

GostPkcs12Builder.create()
        .key(key)
        .certificate(leafCert)
        .password(password)
        .buildAndWriteTo(Path.of("server.p12"));   // временный файл и атомарное переименование
----

По умолчанию: Кузнечик CTR-ACPKM-OMAC, 2000 итераций PBKDF2, MAC HMAC-Streebog-512.
Билдер проверяет, что сертификат соответствует ключу. `build()` затирает свою копию пароля и
делает билдер непригодным для повторного использования; `buildAndWriteTo` делает то же и пишет
файл атомарно. Для совместимости с системами без OMAC — `.encScheme(GostOids.KUZ_CTR_ACPKM)`.

Выпуск сертификатов и цепочек — в README `crypto-gost-pkix` (разделы «Сертификаты» и
«PKCS#12 — хранение ключей и сертификатов»).


=== Быстрый старт

Сервер читает `server.p12` (ключ и цепочка), клиент проверяет сервер по `ca.pem`.
Сервер и клиент — разные процессы: каждый пример блокируется на рукопожатии.

.Сервер
[source,java]
----
import org.rssys.gost.pkix.cert.GostPkcs12Loader;
import org.rssys.gost.tls13.*;
import org.rssys.gost.tls13.config.TlsServerConfig;
import org.rssys.gost.tls13.transport.SocketTlsTransport;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Arrays;

byte[] pfx = Files.readAllBytes(Path.of("server.p12"));
// password — char[] из хранилища секретов (см. «Как читать примеры»)

GostPkcs12Loader.Result p12 = GostPkcs12Loader.load(pfx, password, false);
Arrays.fill(password, '\0');                         // загрузчик затирает только свою копию

try (ServerSocket listener = new ServerSocket(8443)) {
    listener.setSoTimeout(30_000);
    try (Socket socket = listener.accept();
         TlsTransport transport = new SocketTlsTransport(socket);
         TlsSession session = TlsSession.createServer(
                 new TlsServerConfig(cs, p12.getCertificateChain(), p12.getPrivateKey()),
                 transport)) {
        socket.setSoTimeout(5_000);                  // до чтения записей
        session.handshakeAsServer();
        byte[] request = session.read();
        session.write("Hello from GOST TLS 1.3".getBytes(StandardCharsets.UTF_8));
    }
}
----

.Клиент
[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.TrustAnchors;
import org.rssys.gost.tls13.*;
import org.rssys.gost.tls13.config.TlsClientConfig;
import org.rssys.gost.tls13.transport.SocketTlsTransport;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

GostCertificate ca = GostCertificate.fromPemOrDer(Files.readAllBytes(Path.of("ca.pem")));

try (Socket socket = new Socket("localhost", 8443);
     TlsTransport transport = new SocketTlsTransport(socket);
     TlsSession session = TlsSession.createClient(
             new TlsClientConfig(cs, TrustAnchors.ofCertificate(ca))
                     .withServerHostname("localhost"),   // имя должно быть в SAN сертификата
             transport)) {
    socket.setSoTimeout(5_000);
    session.handshakeAsClient();
    session.write("GET / HTTP/1.0".getBytes(StandardCharsets.UTF_8));
    System.out.println(new String(session.read(), StandardCharsets.UTF_8));
}
----

`TrustAnchors.ofCertificate(ca)` — закреплённый сертификат-якорь: цепочка не строится,
но срок, KeyUsage, EKU и имя проверяются. Если сервер прислал цепочку, передайте её через
`TrustAnchors.ofCertificates(List.of(rootCa))`; подробности — в разделе «Клиент».

NOTE: `socket.setSoTimeout()` вызывается до `handshakeAsServer()`/`handshakeAsClient()`:
без таймаута зависший собеседник остановит поток навсегда.


=== Сервер

`TlsServerConfig` задаёт набор шифров, цепочку сертификатов и закрытый ключ. Цепочка — лист
первым, затем промежуточные CA; корень можно не включать, если он есть у клиента. Сервер
собственную цепочку не проверяет: её проверяет клиент, а сервер проверяет клиентский
сертификат только при `needClientAuth`/`wantClientAuth` (раздел «Взаимная аутентификация»).

[source,java]
----
import org.rssys.gost.tls13.TlsSession;
import org.rssys.gost.tls13.config.TlsServerConfig;
import java.nio.charset.StandardCharsets;

TlsServerConfig config = new TlsServerConfig(cs, chain, key)
        .withOcspStaplingResponse(ocspDer);   // ответ уходит, если клиент запросил staple

try (TlsSession server = TlsSession.createServer(config, transport)) {
    server.handshakeAsServer();
    System.out.println("SNI: " + server.getRequestedServerName());
    server.write("Hello".getBytes(StandardCharsets.UTF_8));
}
----

Набор шифров в конфигурации — предпочтение сервера: клиент предлагает оба ГОСТ-набора,
сервер выбирает свой, если клиент его предложил, иначе другой из предложенных. Поэтому
`server.getCipherSuite()` после рукопожатия может отличаться от настроенного.
Non-GOST наборы не поддерживаются.

.OCSP stapling
Ответ — сырой `OCSPResponse` DER. Он уходит только если клиент запросил `status_request`;
`null` отключает stapling, пустой массив отвергается. Сервер ответ не проверяет
(проверяет клиент). Для каждого имени из SNI свой staple задаётся в `TlsServerCredentials`.

.SNI: несколько доменов
[source,java]
----
import org.rssys.gost.tls13.config.SniCertificateSelector;
import org.rssys.gost.tls13.config.TlsServerConfig;
import org.rssys.gost.tls13.config.TlsServerCredentials;

SniCertificateSelector byName = name -> {
    if ("foo.example.com".equals(name)) {
        return new TlsServerCredentials(fooChain, fooKey, fooOcspDer);
    }
    return null;   // учётные данные по умолчанию
};

TlsServerConfig config = new TlsServerConfig(cs, chain, key)
        .withSniSelector(byName);
----

Селектор получает нормализованное имя (lowercase, без точки) только при наличии
`server_name`; он работает внутри рукопожатия, поэтому должен быть потокобезопасным и
неблокирующим. `null` — учётные данные по умолчанию. Невалидное имя (длиннее 253, пустые
метки, управляющие символы) отвергается до селектора с `unrecognized_name`.

.Тикеты возобновления
[source,java]
----
TlsServerConfig config = new TlsServerConfig(cs, chain, key).withTicketsToSend(2);

TlsSession server = TlsSession.createServer(config, transport);
server.setPskStore(pskStore);   // до handshakeAsServer()
server.handshakeAsServer();
----

`withTicketsToSend(n)` — от 1 до `TlsConstants.MAX_TICKETS_TO_SEND` (5), по умолчанию 1.
Без `setPskStore` тикеты не выдаются; при `needClientAuth`/`wantClientAuth` — тоже
(возобновление обошло бы повторную проверку клиента). Подробности — в разделе «PSK».

.Состояние сервера
`getRequestedServerName()` — проверенное имя из SNI или `null`; `getCipherSuite()` —
согласованный набор; `isHandshakeDone()` и `isClosed()` — стадии; `hasPeerCertificate()` и
`getPeerCertificates()` заполняются только при mTLS, при PSK сертификатов нет.


=== Клиент

Клиент проверяет сервер по доверенным якорям и имени. Без `withServerHostname()` (и без
явного `withoutHostnameVerification()`) `TlsSession.createClient` бросает
`IllegalArgumentException`: забытое имя не должно молча отключать сверку.

[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.TrustAnchors;
import org.rssys.gost.tls13.TlsSession;
import org.rssys.gost.tls13.config.TlsClientConfig;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

GostCertificate ca = GostCertificate.fromPemOrDer(Files.readAllBytes(Path.of("ca.pem")));

TlsClientConfig config = new TlsClientConfig(cs, TrustAnchors.ofCertificate(ca))
        .withServerHostname("gost.example.com");   // SNI и сверка имени

try (TlsSession client = TlsSession.createClient(config, transport)) {
    client.handshakeAsClient();
    client.write("Hello".getBytes(StandardCharsets.UTF_8));
}
----

`withServerHostname` задаёт и SNI, и ожидаемое имя. Unicode-имя один раз приводится к A-label
и в этом виде уходит в SNI и сверяется с сертификатом; адреса с `ß`, `ς`, ZWNJ или ZWJ
отвергаются как неоднозначные для IDNA2003. IP-литерал проверяется по `iPAddress` SAN и
в SNI не отправляется — для соединения по адресу передавайте сам адрес, а не отключайте
проверку имени. Имя длиннее 253 символов, с пустыми метками или управляющими символами
отвергается `IllegalArgumentException`; сервер на такое имя отвечает `unrecognized_name`.

Если сверка имени не нужна (mesh, внутренние адреса), отключите её явно:
`withoutHostnameVerification()`. CA-проверка при этом остаётся; имя, заданное
`withServerHostname`, по-прежнему уходит в SNI. Для отладки без проверки цепочки есть
`createClientWithoutServerAuth(transport, cs, clientCertificate, clientKey)`: он не проверяет
цепочку и имя, но сохраняет проверки срока, KU, EKU и OCSP листа; клиентский сертификат в нём
передать можно, поэтому «анонимным» его называть нельзя.

.Якоря и срок
[source,java]
----
import org.rssys.gost.pkix.cert.AnchorExpiryPolicy;
import org.rssys.gost.pkix.cert.TrustAnchors;
import java.util.List;

TrustAnchors anchors = TrustAnchors.ofCertificates(List.of(rootCa))
        .withExpiryPolicy(AnchorExpiryPolicy.REJECT);   // истёкший якорь — отказ
----

Доверие — только сертификатами: `TlsClientConfig` или `withTrustAnchors`. Якорь
аутентифицирует `pathLen` и `NameConstraints` корня, даже если сервер его не прислал; цепочка
строится снизу вверх, поэтому перевыпущенный корень и закреплённый промежуточный CA
поддерживаются. Срок якоря при нескольких сертификатах не блокирует соединение (`WARN`);
`AnchorExpiryPolicy.REJECT` ужесточает. Одиночный закреплённый сертификат проверяется как лист.
DN сравнивается побайтно: нормализации RFC 5280 §7.1 нет.

.OCSP сервера
Присланный staple проверяется всегда; без него рукопожатие проходит, пока не задан
`withRequireOcspStapling(true)`. Возраст без `nextUpdate` — до 24 ч (`GostOids.MAX_OCSP_AGE_MS`).
Предел `thisUpdate` настраивается только в `TlsPeerPolicy` (проверка вне сессии и JSSE).

NOTE: ClientHello без `supported_versions` или без TLS 1.3 сервер отвергает алертом
`protocol_version`; ServerHello и HelloRetryRequest без `supported_versions` или с другой
версией клиент отвергает (`protocol_version`, `illegal_parameter`).

=== Проверка сертификата

В рукопожатии `TlsSession` проверяет сертификат собеседника сам: цепочку, срок, `KeyUsage`,
`ExtendedKeyUsage`, имя (на клиенте) и присланный OCSP-staple. Настройка — якоря и режим
(`TlsClientConfig`, `needClientAuth`/`wantClientAuth`); отдельного «включить проверку» нет.

* Цепочка: подпись каждого звена, `issuer -> subject` побайтно, `BasicConstraints`,
  `keyCertSign`, `pathLen`, `NameConstraints` якоря.
* Лист: срок, `KeyUsage` (если задан — нужен `digitalSignature`), `ExtendedKeyUsage`
  (`serverAuth`/`clientAuth`, если задан), имя сервера.
* Отзыв: присланный staple, если он есть; обязательность — `withRequireOcspStapling()` на
  клиенте и `withClientOcspPolicy()` на сервере.

Отказ приходит как `TlsException`, код — `getAlertCode()`:

* `certificate_expired` (45) — истёк лист или промежуточный сертификат;
* `certificate_revoked` (44) — отзыв по OCSP;
* `unknown_ca` (48) — якорь не найден или корень не подписан;
* `bad_certificate` (42) — подпись, KU, EKU, имя или формат.

.Проверка вне сессии
Тот же валидатор доступен напрямую — до рукопожатия или без него:

[source,java]
----
import org.rssys.gost.tls13.cert.TlsCertificateValidator;
import org.rssys.gost.tls13.cert.TlsPeerPolicy;
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.pkix.cert.TrustAnchors;
import java.util.List;

TlsPeerPolicy policy = TlsPeerPolicy.server("gost.example.com", anchors)
        .requireOcspStaple(true);
List<GostCertificate> effective =
        TlsCertificateValidator.validate(chain, policy);   // цепочка + лист + отзыв
----

`TlsPeerPolicy` — та же модель доверия: `server(hostname, anchors)`, `client(anchors)`,
явные `serverLeafOnly`/`clientLeafOnly` и `*WithoutHostnameVerification`. Имя обязательно;
`maxOcspAge`/`maxThisUpdateAge` — только здесь (`TlsClientConfig` их не выставляет).

.Базовые проверки `GostCertificate`
[source,java]
----
boolean expired = cert.isExpired();                       // notBefore и notAfter
boolean hostnameOk = cert.verifyHostname("gost.example.com");
boolean ipOk = cert.verifyAddress("192.168.1.1");          // iPAddress SAN
boolean kuValid = cert.isKeyUsageValid();
boolean ekuServer = cert.isEkuValidForServer();
boolean isCa = cert.isCA();
int pathLen = cert.getPathLen();                          // -1, если не задано
boolean sigValid = cert.verifySignature(ca.getPublicKey());
----

`KeyUsage`: если расширение задано, для TLS нужен `digitalSignature` (RFC 8446 §4.4.2.2);
отсутствие расширения означает отсутствие ограничений. То же для `ExtendedKeyUsage`:
отсутствие допускается, иначе нужен `serverAuth`/`clientAuth`.

Подробности полей, DN, SAN и расширений — в README `crypto-gost-pkix` (раздел «Сертификаты»).
Проверка ответа OCSP — `TlsCertUtils.verifyOcspResponse(cert, issuer)` и перегрузка с
`maxOcspAgeMs`/`maxThisUpdateAge`.


=== Согласование параметров

.Набор шифров
Клиент предлагает оба набора; сервер выбирает свой, если клиент его предложил, иначе другой.
`getCipherSuite()` после рукопожатия может отличаться от настроенного. L и S различаются
масками TLSTREE и SNMAX (RFC 9367 §3.1.2); `TlsCiphersuite.byId`/`byIanaName`/`values()` —
для разбора и перечисления.

.Группы ECDHE и HelloRetryRequest
Семь групп RFC 9367 §3.1; стартовая по умолчанию — GC256B. `withSelectedNamedGroup` задаёт
её на клиенте и сервере. Если `key_share` не совпал с группой сервера, сервер отвечает
HelloRetryRequest (лишний обмен); задайте одну группу с обеих сторон. Binder после HRR
пересчитывается (RFC 8446 §4.2.11.2).

.ALPN
[source,java]
----
TlsClientConfig clientConfig = new TlsClientConfig(cs, anchors)
        .withServerHostname("gost.example.com")
        .withAlpnProtocols(List.of("h2", "http/1.1"));

TlsServerConfig serverConfig = new TlsServerConfig(cs, chain, key)
        .withAlpnProtocols(List.of("http/1.1", "h2"));
----

Сервер выбирает первый свой протокол, который предложил клиент: порядок сервера важнее. Без
общего протокола — fatal `no_application_protocol` (120). Без ALPN у клиента
`getAlpnProtocol()` — `null`. Имена — байты ISO-8859-1.

.max_fragment_length
[source,java]
----
session.setMaxFragmentLengthRequest(TlsConstants.MAX_FRAG_LEN_512);  // до handshake
// после рукопожатия:
int code = session.getMaxFragmentLength();       // 1..4 или 0
int bytes = TlsUtils.maxFragmentLength(code);    // 512, 1024, 2048, 4096 или 16384
----

Коды: 1 — 512, 2 — 1024, 3 — 2048, 4 — 4096 (RFC 6066 §4); 0 — не запрашивать. Метод
принимает код, а не байты: `setMaxFragmentLengthRequest(512)` молча превращается в 0.
Вызывать до рукопожатия; после — `IllegalStateException`. Согласованный лимит действует
и на записи рукопожатия, и после KeyUpdate. Сервер может ограничить исходящий фрагмент
через `setMaxSendFragment(code)`; неверный код там тоже даёт значение по умолчанию.

.Interop с openssl-gost-provider
[source,java]
----
TlsServerConfig config = new TlsServerConfig(cs, chain, key)
        .withInteropAcceptGostBaseSigScheme(true);
----

openssl-gost-provider v3.6.0 присылает базовую схему (0x0709/0x070D) независимо от кривой;
RFC 9367 §5 требует точного соответствия, поэтому по умолчанию ответ отвергается. Флаг
принимает его для ключа того же размера — осознанное ослабление, WARNING один раз на процесс.
Есть на обеих сторонах.


=== Взаимная аутентификация (mTLS)

Сервер задаёт режим и якоря одним вызовом:

* `needClientAuth(anchors)` — сертификат обязателен; без него клиент получает
  `certificate_required`;
* `wantClientAuth(anchors)` — сертификат запрашивается, но не обязателен; предъявленный
  проверяется так же строго. Приложение обязано проверить `session.hasPeerCertificate()`.

Повторный вызов заменяет режим и якоря целиком; текущие значения — `getClientAuthMode()`
и `getTrustAnchors()`. Без вызова mTLS выключен (`ClientAuth.NONE`), отдельного
«выключателя» через `null` нет.

[source,java]
----
import org.rssys.gost.pkix.cert.TrustAnchors;
import org.rssys.gost.tls13.config.ClientOcspPolicy;
import org.rssys.gost.tls13.config.TlsClientConfig;
import org.rssys.gost.tls13.config.TlsServerConfig;

TlsServerConfig serverConfig = new TlsServerConfig(cs, chain, key)
        .needClientAuth(TrustAnchors.ofCertificate(caCert))
        .withClientOcspPolicy(ClientOcspPolicy.REQUIRE);

TlsClientConfig clientConfig = new TlsClientConfig(cs, TrustAnchors.ofCertificate(caCert))
        .withServerHostname("gost.example.com")
        .withClientCertificateChain(clientCert)      // или List.of(leaf, intermediate, root)
        .withClientPrivateKey(clientKey)
        .withOcspStaplingResponse(clientOcspDer);    // по запросу сервера
----

Клиент передаёт цепочку лист-первым и ключ; при нескольких сертификатах — перегрузкой
`withClientCertificateChain(List.of(...))`. Сервер после рукопожатия отдаёт проверенную
цепочку: `getPeerCertificates()` (лист первым) и `hasPeerCertificate()`.

IMPORTANT: mTLS и PSK несовместимы: при `need`/`want` тикет не выдаётся и PSK не принимается,
иначе возобновление обошло бы проверку клиента. При PSK сертификатов нет, и
`hasPeerCertificate()` даёт `false`.

.Отзыв клиентского сертификата
Прямой путь не загружает CRL и OCSP по сети. По умолчанию staple не запрашивается, а
присланный отвергается (`unsupported_extension`). `withClientOcspPolicy(REQUEST)` проверяет
ответ, если он прислан; `REQUIRE` требует его (`bad_certificate`). Чужой или просроченный
staple отвергается; политика без mTLS — `IllegalArgumentException`. CRL и сетевой OCSP — в JSSE.


==== oid_filters: выбор клиентского сертификата

Сервер может ограничить выбор расширением `oid_filters` (RFC 8446 §4.2.5). Типичный
ГОСТ-сценарий — сертификат с CertificatePolicies KC1 (`1.2.643.100.113.1`) или KC2.

[source,java]
----
import org.rssys.gost.pkix.GostOids;
import org.rssys.gost.tls13.config.OIDFilter;
import org.rssys.gost.util.DerCodec;

// extensionOid — OID расширения без тега и длины (CertificatePolicies 2.5.29.32)
byte[] cpOid = {0x55, 0x1D, 0x20};
byte[] kc1Values = DerCodec.encodeSequence(DerCodec.encodeOid(GostOids.POLICY_KC1));

OIDFilter kc1 = new OIDFilter(cpOid, kc1Values);

TlsServerConfig serverConfig = new TlsServerConfig(cs, chain, key)
        .needClientAuth(TrustAnchors.ofCertificate(caCert))
        .withOidFilters(List.of(kc1));
----

Значение фильтра — DER `extnValue`: для EKU и CertificatePolicies — `SEQUENCE` из OID, для
KeyUsage — `BIT STRING` (`DerCodec.encodeBitString`). Пустое значение требует лишь наличия
расширения; сертификат без расширения не подходит. Фабрик `OIDFilter` пока нет: OID
расширения — байтами, значения — `DerCodec`.

Клиент выбирает сертификат селектором:

[source,java]
----
import org.rssys.gost.pkix.cert.GostCertificate;
import org.rssys.gost.tls13.cert.TlsCertUtils;
import org.rssys.gost.tls13.config.ClientCertificateSelector;
import org.rssys.gost.tls13.config.TlsClientCredentials;
import java.util.List;
import java.util.Map;

ClientCertificateSelector selector = request -> {
    for (var entry : List.of(
            Map.entry(kc1Cert, kc1Key),
            Map.entry(simpleCert, simpleKey))) {
        GostCertificate cert = entry.getKey();
        boolean ok = request.oidFilters().stream()
                .allMatch(f -> TlsCertUtils.matchesOidFilter(cert, f));
        if (ok) return new TlsClientCredentials(List.of(cert), entry.getValue());
    }
    return null;   // подходящего нет — уйдёт пустой certificate_list
};

TlsClientConfig clientConfig = new TlsClientConfig(cs, TrustAnchors.ofCertificate(caCert))
        .withServerHostname("gost.example.com")
        .withClientCertificateSelector(selector);
----

Селектор вызывается на каждый `CertificateRequest` (в том числе без фильтров) и получает
его целиком. Он единственный источник учётных данных: `null` — пустой `certificate_list`,
цепочка из конфигурации не подставляется.

=== Возобновление сессии по PSK

После полного рукопожатия сервер с хранилищем (`setPskStore` до рукопожатия) отправляет
билет `NewSessionTicket`. При следующем подключении клиент предъявляет билет, и рукопожатие
идёт без сертификатов и `CertificateVerify`: владение PSK подтверждает имитовставка.
ECDHE выполняется всегда (`psk_dhe_ke`). mTLS и PSK несовместимы.

[source,java]
----
import org.rssys.gost.tls13.psk.InMemoryPskStore;

InMemoryPskStore serverStore = new InMemoryPskStore(1000);
InMemoryPskStore clientStore = new InMemoryPskStore(100);

// Первое подключение: сервер выдаёт билет, клиент сохраняет его при read()
TlsSession server = TlsSession.createServer(serverConfig, serverTransport);
server.setPskStore(serverStore);
TlsSession client = TlsSession.createClient(clientConfig, clientTransport);
client.setPskStore(clientStore);
server.write("ready".getBytes(StandardCharsets.UTF_8));
byte[] data = client.read();       // обрабатывает NewSessionTicket, затем отдаёт данные

// Второе подключение — по билету
TlsSession resumed = TlsSession.createClient(clientConfig, newClientTransport);
resumed.setPskStore(clientStore);
resumed.handshakeAsClient();
boolean wasResumed = resumed.wasResumed();
----

`read()` обрабатывает билет внутри: до первого `read()` клиентское хранилище пусто.
`wasResumed()` до завершения рукопожатия бросает `IllegalStateException`.

* Серверное хранилище расходует билет при предъявлении; клиентское хранит полученные.
* `getForResumption` берёт самый новый билет с подходящей привязкой.
* Без `read()` нового билета нет: старый сервер отвергнет, будет полное рукопожатие.
* RFC 8446, приложение C.4, не рекомендует переиспользовать билет — ограничивайте размер.

Билет привязан к SNI, якорям и их сроку, режиму проверки имени, требованию staple и набору
шифров. Билет сервера A не предлагается серверу B. Клиентское и серверное хранилища —
разные экземпляры; серверное — одно на одну идентичность.

NOTE: `PskStore` не должен удерживать массив `ticket` из `get`/`peek`/`remove`: стек
затирает его после возврата.

Граница доверия: запись несёт `validUntil` — наименьший `notAfter` среди сертификатов, по
которым сервер принят (срок якоря-корня не учитывается; в режиме «только leaf» — срок листа).
Срок тикета не выходит за границу; сервер так же ограничивает `ticket_lifetime` сроком цепочки.

Кросс-валидация: OpenSSL (gostprov) и КриптоПро CSP, наборы L и S, в обе стороны; работает и
через HelloRetryRequest (binder по RFC 8446 §4.2.11.2).

NOTE: `read()` — не более 8 служебных сообщений и ограниченный бюджет записей
(`MAX_POST_HANDSHAKE`, `MAX_POST_HANDSHAKE_RECORDS`); сверх — `ALERT_UNEXPECTED_MESSAGE`.
Повторный `read()` сбрасывает счётчики.

=== Обмен данными

`read()` и `write()` можно вызывать многократно. `write(data)` сам режет данные на записи
по `maxPayload` (16383 байта), `read()` возвращает данные одной записи. Пустой `write()`
ничего не отправляет.

.Серверный цикл
[source,java]
----
import org.rssys.gost.tls13.*;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

while (true) {
    try {
        byte[] request = server.read();
        server.write(process(request).getBytes(StandardCharsets.UTF_8));
    } catch (PeerClosedException e) {
        break;                                   // штатное close_notify
    } catch (TlsException e) {
        System.err.println("Отказ: " + TlsAlerts.forLog(e.getAlertCode()));
        break;
    } catch (IOException e) {
        break;                                   // обрыв транспорта
    }
}
----

`PeerClosedException` — штатное закрытие пиром. `TlsException` — протокольный отказ или
испорченная запись: `getAlertCode()` даёт `bad_record_mac`, причина — `AuthenticationException`.

.Передача файла
Клиент отправляет длину и файл; `write()` режет сам. Сервер накапливает данные до
`8 + длина`, поэтому границы записей не важны.

[source,java]
----
// Клиент
import java.nio.ByteBuffer;
import java.nio.file.Files;
import java.nio.file.Path;

byte[] file = Files.readAllBytes(Path.of("data.bin"));
client.write(ByteBuffer.allocate(8).putLong(file.length).array());
client.write(file);                              // нарезка внутри write()
----

[source,java]
----
// Сервер
import java.io.ByteArrayOutputStream;
import java.nio.ByteBuffer;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Arrays;

ByteArrayOutputStream received = new ByteArrayOutputStream();
long fileLength = -1;
while (fileLength < 0 || received.size() < 8 + fileLength) {
    received.write(server.read());
    if (fileLength < 0 && received.size() >= 8) {
        fileLength = ByteBuffer.wrap(received.toByteArray(), 0, 8).getLong();
    }
}
byte[] all = received.toByteArray();
Files.write(Path.of("received.bin"), Arrays.copyOfRange(all, 8, (int) (8 + fileLength)));
----

Пример копит файл в памяти; для больших файлов пишите в поток по мере чтения.

.Обновление ключей (KeyUpdate)
[source,java]
----
session.initiateKeyUpdate(true);   // просит собеседника тоже обновить ключи
session.write("data after key update".getBytes(StandardCharsets.UTF_8));
----

Сразу меняется ключ отправки; ключ приёма — после встречного KeyUpdate, который
обрабатывается при следующем `read()`. Повторный вызов до отправки объединяется с первым,
запрос ответного обновления не теряется. Вне рукопожатия — `TlsException`.

.Состояние сессии
* `isHandshakeDone()`, `isClosed()` — стадии;
* `getCipherSuite()`, `getProtocol()` — согласованный набор и `TLSv1.3`;
* `getPeerHostname()` — имя сервера у клиента, `getRequestedServerName()` — SNI у сервера;
* `hasPeerCertificate()`, `getPeerCertificates()` — сертификат пира при mTLS;
* `getAlpnProtocol()`, `getMaxFragmentLength()`, `wasResumed()`.

=== Экспорт ключевого материала

После рукопожатия обе стороны выводят одинаковые секретные байты (RFC 8446 §7.5) — для
привязки к каналу (`tls-exporter`, RFC 9266, SCRAM-PLUS), EAP-TLS 1.3, NTS. Значение
зависит только от этого рукопожатия.

[source,java]
----
import org.rssys.gost.tls13.TlsUtils;

byte[] binding = session.exportKeyingMaterial("EXPORTER-Channel-Binding", null, 32);
try {
    // передать в протокол аутентификации: та же метка и контекст на другой стороне
} finally {
    TlsUtils.wipeArray(binding);           // значение секретное
}
----

* Метка — непустая, до 249 байт UTF-8, чувствительна к регистру; для привязки берётся из
  реестра IANA «TLS Exporter Labels».
* Контекст — до 65535 байт; `null` и пустой массив дают одно значение.
* Длина — от 1 до 255 × длины хэша (8160 для Стрибога-256).
* До рукопожатия и после закрытия — `IllegalStateException`: секрет затирается с ключами.
* При PSK значение новое; `KeyUpdate` его не меняет.

NOTE: RFC 9367 экспорт для ГОСТ-наборов не определяет: схема взята из RFC 8446 с хэшем
Стрибог. Сверено с OpenSSL gost-provider (`-keymatexport`) в обе стороны; с другими
ГОСТ-реализациями не проверялось.

=== Ошибки и закрытие

`handshakeAsClient()`, `handshakeAsServer()`, `read()` и `write()` бросают `IOException`.

* `PeerClosedException` (наследник `EOFException`) — пир прислал `close_notify`; штатное закрытие.
* `TlsException` — протокольный отказ: `getAlertCode()` даёт код RFC 8446, `isFromPeer()` —
  пришёл ли alert от пира. Испорченная запись — `bad_record_mac` (20); неверные `Finished`,
  `CertificateVerify` и PSK binder — `decrypt_error` (51).
* Остальной `IOException` — сбой транспорта.

После ошибки, `close_notify` и fatal alert сессия непригодна: `read()` и `write()` дают
`IllegalStateException`, `isClosed()` — `true`. Локальный отказ отправляет пиру fatal alert;
на alert пира ответ не отправляется. `close()` идемпотентен и отправляет `close_notify`.

Зашифрованная запись — до `MAX_CIPHERTEXT_LENGTH` (16640), открытый текст — до 2¹⁴ (16384);
больше — `record_overflow`. Это предел против исчерпания памяти по поддельному заголовку.

[source,java]
----
try (TlsSession server = TlsSession.createServer(serverConfig, transport)) {
    server.handshakeAsServer();
    byte[] request = server.read();
    server.write("OK".getBytes(StandardCharsets.UTF_8));
} catch (PeerClosedException e) {
    // штатное закрытие пиром
} catch (TlsException e) {
    System.err.println("Отказ: " + TlsAlerts.forLog(e.getAlertCode()));
} catch (IOException e) {
    // обрыв транспорта
}
----


=== Логирование

Модуль пишет в `java.util.logging` под `org.rssys.gost.tls13.*` через `GostLogger`; записи
сессии и движка помечены `[conn#N]`. Уровни и настройка — в README `crypto-gost-core`,
раздел «Логирование».

На `DEBUG`: стадии рукопожатия, набор и группа, HRR, SNI, PSK (предложение, причина пропуска,
выдача билета), итог рукопожатия, отправленные и принятые alert, KeyUpdate. Отказы по данным
собеседника (binder, возраст билета, схемы подписи) выше `DEBUG` не поднимаются.

`WARNING`: чужая привязка и просроченная запись PSK, сбой вывода PSK или `onTicketReceived`,
включённый `interopAcceptGostBaseSigScheme`, неверная подпись `CertificateVerify` (серийный
номер; DN — на `DEBUG`), непредвиденный сбой библиотеки. Ключевой материал и тикеты в журнал
не попадают.

=== Потокобезопасность

`TlsSession` не потокобезопасен: один экземпляр — одно соединение и один поток. Для
параллельных соединений создавайте отдельную сессию на каждое.

Закрытие из другого потока во время рукопожатия не поддерживается: поля ключевого
материала не синхронизированы. Чтобы прервать зависшее рукопожатие, закройте транспорт
(у `InMemoryTlsTransport` ждущий `receiveRecord()` проснётся с `IOException`), дождитесь
потока-владельца и только затем вызовите `close()`.

`InMemoryPskStore` потокобезопасен и может разделяться между сессиями. `TlsTransport` —
по реализации: `InMemoryTlsTransport` потокобезопасен, `SocketTlsTransport` и
`ChannelTlsTransport` — нет. `SniCertificateSelector` и `ClientCertificateSelector`
вызываются из потока рукопожатия и должны быть потокобезопасными.

=== TlsHandshakeEngine (низкоуровневый API)

`TlsHandshakeEngine` — пошаговое рукопожатие без ввода-вывода: `start()`, `receive(frame)`,
`poll()`. `TlsSession` использует его внутри, JSSE — для `SSLEngine`.

Вызывающий сам:

* режет и собирает записи (`TlsRecord`), применяет смены ключей;
* проверяет сертификат пира (`needsCertificateValidation()`,
  `acknowledgeCertificateValidation()`);
* обрабатывает сообщения после рукопожатия (`receivePostHandshake`).

Для блокирующего соединения он не нужен — берите `TlsSession` (см. «Что выбрать»).

=== Запуск тестов производительности и устойчивости

Модуль включает два теста, помеченных `@Tag("stress")`, которые исключены
из обычного прогона `mvn test` (через `surefire.excludedGroups`).

==== Пропускная способность (throughput)

Однопоточный замер скорости передачи данных через `TlsSession`.

Описание методики: link:doc/tls-session-stress.md[Методика измерения throughput].

[source,sh]
----
# По умолчанию: 5 прогонов × ≈20 с ≈ 100 с
make test-stress-tlssession

# Управление временем (прогрев, замер, число прогонов)
make test-stress-tlssession ARGS="-Dstress.warmup=2 -Dstress.measure=10 -Dstress.iters=3"

# Через Maven напрямую
mvn test -pl crypto-gost-tls13 -am \
  -Dtest="org.rssys.gost.tls13.stress.TlsSessionStreamTest" \
  -Dsurefire.excludedGroups= \
  -Dsurefire.failIfNoSpecifiedTests=false
----

==== Смешанная нагрузка (стресс-тест)

`stressTest` — 5 минут смешанной нагрузки: короткие, средние и длинные соединения, обрывы;
следит за памятью и зависаниями. Отдельный `maxConcurrentSessions` ищет потолок
одновременных сессий.

Методика: link:doc/tls-session-stress-mixed.md[Методика измерения стабильности под смешанной нагрузкой].

[source,sh]
----
# Makefile: только stressTest, 5 минут
make test-stress-tlssession-mixed

# Тот же тест через Maven
mvn test -pl crypto-gost-tls13 -am \
  -Dtest="org.rssys.gost.tls13.stress.TlsSessionStressTest#stressTest" \
  -Dsurefire.excludedGroups= \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dstress.duration=5

# Потолок одновременных сессий
mvn test -pl crypto-gost-tls13 -am \
  -Dtest="org.rssys.gost.tls13.stress.TlsSessionStressTest#maxConcurrentSessions" \
  -Dsurefire.excludedGroups= \
  -Dsurefire.failIfNoSpecifiedTests=false
----

[cols="3,1,2",options="header"]
|===
| Свойство | По умолч. | Для чего

| `stress.duration` | 5 | Длительность `stressTest`, минут
| `stress.maxSessions` | 10000 | Потолок `maxConcurrentSessions`
| `stress.step` | 50 | Шаг наращивания `maxConcurrentSessions`

=== Кросс-валидация

==== TLS 1.3

Полное рукопожатие, возобновление по PSK, экспорт и ответные расширения проверяются
в обе стороны. `x-validation-tests/tls13` — OpenSSL 3.6 с gost-provider (4 класса);
`x-validation-tests/cryptopro` — `CryptoproTlsInteropTest` и
`CryptoproTlsResumptionTest`. Методика и предусловия:
link:../x-validation-tests/tls13/doc/tls13-cross-validation.md[Кросс-валидация TLS 1.3 ГОСТ].

[source,sh]
----
mvn -Pcrossval -pl x-validation-tests/tls13 -am test -Dexec.skip=true
----

==== PKCS#12

`GostPkcs12Loader` читает контейнеры OpenSSL; `GostPkcs12Builder` создаёт контейнеры,
которые OpenSSL валидирует, а затем перечитывает загрузчик. Покрыты пять наборов
параметров (256 A/B/C, 512 A/B). Подробности — в README `crypto-gost-pkix`,
раздел «Кросс-валидация».

[source,sh]
----
mvn -Pcrossval -pl x-validation-tests/pkcs12 -am test -Dexec.skip=true
----
