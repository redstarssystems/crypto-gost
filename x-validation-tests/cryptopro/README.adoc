= Интероп с КриптоПро CSP (модуль cryptopro)
:toc:
:toc-title: Содержание
:lang: ru

Тесты, которые запускают утилиты КриптоПро CSP во время прогона (`csptest`, `certmgr`,
`cryptcp`). Без установленного КриптоПро пропускаются, а не падают. Входят только в профиль
`crossval`. Готовые подписи КриптоПро, не требующие CSP, проверяются в модуле `crypto-gost-pkix`
(`CryptoproCreated*VectorTest`), а CAdES-векторы описаны в `x-validation-tests/cadest/README.adoc`.

== Что проверяется

`CryptoproTlsInteropTest`::
Сервер crypto-gost, клиент `csptest -tlsc` (TLS 1.3). Kuznyechik MGM L и S; кривые GC256A,
GC256B, GC256C, GC256D, GC512A, GC512B, GC512C. `csptest` кладёт в `key_share` только GC256A,
поэтому GC256A согласуется сразу, а остальные кривые идут через HelloRetryRequest. GC256A и
GC512C имеют кофактор 4: секрет ECDHE считается как `(h·d)·Q` (RFC 9367 §6.1.1), и эти два
случая ловят его отсутствие (`SEC_E_MESSAGE_ALTERED`, `0x8009030f`). Проверяются код возврата, `[ErrorCode: 0x00000000]` и
содержимое файла, который клиент сохранил из ответа (маркер `INTEROP_OK`), то есть и обмен
данными, а не только handshake.

`CryptoproTlsResumptionTest`::
Возобновление по PSK: сервер crypto-gost, клиент `csptest -tlsc -proto 7 -reconnects 3 -checkreuse
-checksessionticket`. Kuznyechik MGM L и S, кривая GC256A (`csptest` кладёт в `key_share` только её, поэтому
HelloRetryRequest нет). Сервер видит `[false, true, true]`: первое соединение полное, второе и третье
возобновлены по тикету. Тот же сценарий для сервера jsse (`GostSSLEngine`) описан в
`x-validation-tests/jsse/doc/jsse-cross-validation.adoc`. Возобновление, при котором само соединение
идёт через HelloRetryRequest, проверяет тест `serverResumesCryptoproClientThroughHrr` (кривая GC256B, в каждом
соединении два ClientHello, результат тот же: `[false, true, true]`). Binder второго ClientHello считается по
RFC 8446 §4.2.11.2, КриптоПро проверяет его независимо.

`CryptoproKeysetInteropTest`::
Хэш Стрибога 256 и 512 бит из `csptest -hash` совпадает с `Digest` побайтно. Сырая подпись
`csptest -keyset -sign` проверяется `Signature.verify` после полного разворота байтов блока:
у КриптоПро это `r‖s` в little-endian, у библиотеки `s‖r` в big-endian. Хэш при этом не
меняется.

`CryptoproCurvesInteropTest`::
Все 7 зарегистрированных кривых (TC26-A/B/C 256 и 512, CryptoPro-A/B/C): ключ создаётся
на кривой, выбранной явно через `csptest -signoid`. Проверяются два условия вместе: OID
в сертификате КриптоПро даёт именно зарегистрированный экземпляр кривой библиотеки, и сырая
подпись КриптоПро проверяется нашими параметрами (p, a, b, G, n). По отдельности они
недостаточны: совпадение OID не доказывает равенства констант, а удачная проверка подписи не
доказывает, что взята нужная кривая. На кривых с кофактором 4 (TC26-A-256, TC26-C-512)
открытый ключ КриптоПро проходит ещё и нашу проверку принадлежности подгруппе порядка n.
`CryptoproKeysetInteropTest` кривую не задаёт: провайдер берёт CryptoPro-A (тип 80) и
TC26-A-512 (тип 81), тест фиксирует именно их.

`CryptoproPkcs12InteropTest`::
PFX, экспортированный `certmgr -export -pfx`, шифрует ключ схемой PBE с OID
`1.2.840.113549.1.12.1.80` (в RFC 7292 её нет). `GostPkcs12Loader` её не читает и отвергает
fail-closed; тест фиксирует отказ. Позитивный сценарий (ключ и сертификат из PFX КриптоПро)
помечен `@Disabled` как известное ограничение.

== Окно датчика случайных чисел и флаг контейнеров

Тесты, которые создают контейнеры (`CryptoproKeysetInteropTest` -- подпись КриптоПро,
`CryptoproCurvesInteropTest`, `CryptoproPkcs12InteropTest`), по умолчанию пропускаются. Генерация ключа требует датчика
случайных чисел КриптоПро; если его хранилище пусто или исчерпано, КриптоПро открывает окно
«поводите мышью» и ждёт человека, а `csptest` без него упирается в таймаут (60 секунд) и
тест падает. Включаются тесты явно, когда оператор у машины:

[source,bash]
----
make crossval-full
# или
mvn -Pcrossval -pl x-validation-tests/cryptopro -am test -Dexec.skip=true \
    -Dcrossval.cryptopro.containers=true
# или переменной окружения CROSSVAL_CRYPTOPRO_CONTAINERS=true
----

Остальные тесты модуля (хэш `csptest -hash`, TLS `csptest -tlsc`) контейнеров не создают и
выполняются всегда. Перед релизом прогоняйте `make crossval-full`.

== Окно запроса пароля

Если параметр пароля не передан, КриптоПро открывает графическое окно и ждёт человека. Поэтому
у контейнеров пароль пустой, но задан явно (`-password ""`), а PFX получает собственный `-pin`.
Непустой пароль контейнера не годится: `certmgr -export -pfx` спрашивает его отдельно.

== Что не покрыто

* `csptest -tlss` (наш клиент, сервер КриптоПро) и mTLS с `-user`: сервер не стартует ни с одним
  сертификатом, проверенным пробами (2026-11-08). `AcquireCredentialsHandle` возвращает `0x80090307`
  (в плане 365 внутренняя причина `0x80092004`, в этой пробе её нет), до приёма соединения не доходит.
  Проба шла с сертификатом от одноразового УЦ со случайным ключом: `CA:FALSE`,
  `keyUsage` (`digitalSignature`, а также с `nonRepudiation`, `keyEncipherment`, `dataEncipherment`),
  EKU `serverAuth` (и с `clientAuth`), SAN `DNS:localhost`; ключ подписи (`-sg`) и ключ обмена
  (`-both`); привязка сертификата к контейнеру проверена; корень УЦ в `uRoot`, CRL УЦ в `uMy`;
  запуск по отпечатку, с `-silent`, без `-silent`; `-stcont NONE|AUTO`; `-proto 0|6|7`;
  `-algid GR3412_K|TLS_CIPHER_2012`; `-noreuse`. Контейнер исправен (ключ подписывает без окон,
  пароль сохранён), цепочка до корня строится, сертификат найден. Гипотезы «нет EKU и SAN»,
  «`CA:TRUE`», «пароль контейнера», «статус отзыва» опровергнуты. Не проверено: сертификат в
  хранилище компьютера (`-User`, нужны права администратора) и сертификат от УЦ КриптоПро.
  `-ciphers` завершается сразу без сообщения, `-credversion 5` не поддерживается. Отзыв как причина тоже
  опровергнут: с CDP в сертификате и установленным CRL цепочка проверяется полностью, а отказ прежний.
  Причина подтверждена системным журналом: `CPSSPCreateCredentials! TLS server license not
  found. Since CSP5R2 you need an exclusive TLS Server license!` (`journalctl`, строки `csptest`
  при каждом запуске `-tlss`). Для серверной стороны TLS нужна отдельная лицензия «TLS Server»;
  на машине клиентская (`cpconfig -license -view`: `License type: Client`). Исправить это нельзя,
  пока нет серверной лицензии; проверка лицензии идёт при создании учётных данных и от хранилища
  сертификатов не зависит, поэтому хранилище компьютера (`-User`) пробовать незачем.
* Magma: в `TlsCiphersuite` есть только Кузнечик.
* Направление «наша подпись -> проверка КриптоПро»: `csptest -verify` работает по
  импортированному ключу.
